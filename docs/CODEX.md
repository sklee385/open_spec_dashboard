# Codex 연결과 복구

## 업무 전용 실행 공간

구현 시작은 검토된 프로젝트의 독립 복사본과 기준 스냅샷을 만든다. `WORKSPACE_ROOT`가 없으면 운영체제 임시 폴더의 `openspec-workspaces`를 사용한다. 관리 폴더는 원본 프로젝트 밖에 있어야 하며 업무 ID·원본 경로 식별 정보를 확인한다. 의존성과 `.tools/node-runtime`도 별도 파일로 복사하고 원본 파일을 하드링크로 공유하지 않는다. 복사 실패는 실행하지 않고 오류를 반환한다. 실패한 복사본은 자동 삭제하지 않는다.

같은 Codex threadId를 유지하면서 구현 턴의 cwd와 workspaceWrite writableRoots를 업무 전용 경로로 지정한다. 재연결도 동일 업무 공간을 사용한다. 전용 폴더가 없거나 식별자가 다르면 복구 필요이며 원본 폴더로 대체 실행하지 않는다. 질문·승인 대기 중에는 세션 서버를 재시작하지 않는다.

계획 원본이 변경되면 기준과 대조해 실행을 막고 계획 비교·재검토를 요구한다. 검증은 전용 폴더에서 실행하며, 복사된 프로젝트 런타임이 있으면 이를 우선한다. 외부 CLI도 작업 디렉터리는 분리하지만 기존 제품과 마찬가지로 Codex 샌드박스를 제공하지 않는다.

공유 폴더에서 시작된 과거 업무는 전체 폴더 차이를 해당 업무 결과로 반환하지 않는다. 명시적 격리 전환 이후부터 새 기준을 수집한다. 재시작 시 진행 중 검증은 중단으로 기록한다. 원본 반영 중단은 경로별 백업·저널로 남기며 재시도 전에 충돌 여부를 다시 확인한다. 완료 기록과 작업 공간은 자동 정리하지 않으며 백업 시 DB와 함께 보존한다. 구버전으로 복귀하면 격리 실행과 고정 결과 조회를 보장하지 못한다.

확인한 로컬 CLI: `0.163.0-alpha.11.2`. app-server의 설치 버전 스키마를 `.tools/codex-schema/`에 생성해 계약을 확인했다.

- stdio JSON 연결: `initialize` → `initialized`.
- 최초 업무: `thread/start`, 이후 `turn/start`는 같은 `threadId` 사용.
- 웹 서버(13002)는 스트리밍 게이트웨이이고 Codex·SQLite·질문 소유자는 독립 상주 세션 서버(13003)다. 웹 서버 재시작은 이 소유자를 종료하지 않는다. SSE는 저장된 커서부터 재연결한다.
- 세션 서버 자체의 재시작은 저장한 ID로 `thread/resume`한다. ID 인덱스 조회 실패 시 session_meta의 ID·프로젝트 경로를 검증한 원본 파일로 resume한다. 새 대화나 이전 명령을 자동 생성·재실행하지 않는다.
- 세션 서버 재시작으로 표시된 업무는 화면에서 대화 연결만 자동 복구한다. 일반 네트워크 단절은 SSE·초기 업무 조회를 재시도하며 작성 중 대화와 질문 답변은 업무별 브라우저 저장소에 보존한다.
- 사용자 질문은 `item/tool/requestUserInput` 요청 ID에 `{answers}`로 응답한다.
- 기본 모드에서도 문답하기 위해 `--experimental`로 생성한 설치 버전 스키마를 확인했다. `thread/start.dynamicTools`에 `ask_user`를 등록하고 `item/tool/call`에는 `{success,contentItems:[{type:'inputText',text}]}`로 답한다. 기존 대화는 같은 ID로 복원하며 동적 도구 등록도 유지된다.
- 실행 경계는 `sandbox:workspace-write`, `approvalPolicy:on-request`, cwd는 등록 프로젝트다. `thread/start`, `thread/resume`, `turn/start`에 `approvalsReviewer:auto_review`를 전달하여 Codex의 ‘나 대신 승인’ 검토를 사용한다. Codex가 위험도에 따라 승인·거절하며, 대시보드가 일괄 승인 응답을 보내지 않는다. 모델명은 지정하지 않고 기존 Codex 기본 설정을 사용한다.
- 자동 권한 검토의 시작·결과는 실행 기록에 보존한다. Codex가 사용자에게 전달한 승인 요청은 기존 개별 승인 UI로 처리하며, 요구사항 질문·문서 검토·구현 시작·최종 완료 결정은 사용자에게 남긴다. 미지원 CLI나 검토 오류는 오류로 표시하며 권한 정책을 완화하지 않는다. 이미 대기 중인 요청은 소급 승인하지 않고 같은 대화를 재개한 다음 실행부터 적용한다.
- 요청 식별자는 프로세스 세대와 서버 요청 ID의 조합이다. 자식 프로세스가 다시 시작되면 세대도 바뀌며 이전 세대의 응답·알림은 적용하지 않는다.
- 질문 도구가 실패하거나 턴이 끝나 원래 요청이 종료되어도 질문을 폐기하지 않는다. 만료 질문은 같은 대화의 후속 메시지에 명시적으로 답변을 복구하며, 재시작이나 시간 경과는 요구사항 해결로 간주하지 않는다.
- 질문 응답과 파일·명령 실행 승인은 별도로 처리한다.
- 대화 생성 결과가 불명확하거나 복원에 실패하면 기존 연결을 보존하고 복구 필요 상태로 표시한다.
- `CODEX_BIN`으로 Codex 실행 파일을 지정할 수 있다. 기본값은 PATH의 `codex`다.
- 프로젝트 전용 `.tools/node-runtime`이 있으면 Codex 실행 환경과 `shell_environment_policy.set.PATH`의 첫 경로로 사용한다. 기본 node/npm/npx 검증 명령은 실제 Node와 npm CLI를 직접 실행한다. Windows PowerShell에서는 서명되지 않은 npm.ps1 대신 npm.cmd/npx.cmd를 사용하며 실행 정책은 변경하지 않는다. 재현한 Volta 폴더 쓰기 권한 오류 없이 실제 Codex workspace-write 샌드박스에서 세 명령의 버전 조회를 확인했다.
- 테스트 전용 `CODEX_ARGS`는 프로토콜 모의 프로세스를 사용한다. 실제 실행에서는 설정하지 않는다.

실제 CLI 연결과 `account/read` 결과로 기존 ChatGPT 인증을 사용할 수 있음을 확인했다. 모델 추론·전체 개발 흐름 검증은 별도이며 이 확인만으로 완료되었다고 간주하지 않는다.

실제 추론 검증에서 구조화 질문·답변, 문서 생성과 직접 수정 의견 반영, 구현과 Node.js 테스트 실행, 서버 재시작 뒤 같은 대화 재개를 확인했다. 구체적인 검증 기록은 `VERIFICATION.md`를 따른다. 지원되지 않는 프로토콜이나 CLI 기능은 오류로 표시하며 다른 AI 도구로 자동 전환하지 않는다.

## 앱 내부 업무 복구

업무 화면의 ‘업무 복구’는 기존 대화만 재연결한다. 격리 도입 전 업무는 등록된 원본 경로에서 복구하고, 격리 이력이 있으면 올바른 전용 폴더와 식별 파일이 있어야 한다. 업무 단계와 검토 기록은 바꾸지 않고 AI 메시지를 자동 전송하지 않는다. 다른 Codex가 같은 대화를 소유하면 해당 대화를 닫은 뒤 다시 시도한다. 앱이 다른 대화를 강제로 종료·보관하거나 새 대화로 대체하지 않는다.

복구 성공 시 대기 메시지는 내용과 함께 확인 필요 상태로 보존하며 자동 실행하지 않는다. 대화 인덱스 조회가 실패하면 검증된 업무 경로와 원래 프로젝트 경로에 속한 동일 ID의 rollout만 찾아 복원한다.
