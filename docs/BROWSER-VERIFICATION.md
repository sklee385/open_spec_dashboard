# 백그라운드 브라우저 검증

업무 화면의 **백그라운드 브라우저 검증**에서 시나리오를 저장하고 실행한다. PC의 마우스·키보드·개인 브라우저를 사용하지 않는다. 브라우저는 동시 한 개이며 화면 크기는 1280×800이다.

## 준비

```powershell
./scripts/npm.ps1 install
./scripts/setup-browser.ps1
./scripts/npm.ps1 run build --workspace backend
```

설치는 프로젝트 `.tools/browser-runtime`에만 수행한다. 배포 준비에서도 해당 Chromium을 `service/browser-runtime`에 복사한다. 런타임이 없으면 자동 다운로드하거나 개인 브라우저로 대체하지 않는다. 회사 보안 정책의 실행 차단은 우회하지 않는다.

Windows 전용 기능이다. 준비 명령은 Windows .NET Framework C# 컴파일러로 프로세스 가드를 함께 만든다. PowerShell 실행 정책을 낮추지 않는다. 회사 정책이 가드나 Chromium 실행을 막으면 준비 오류를 표시한다. Job Object가 실행기·호스트의 비정상 종료 때도 소유한 하위 프로세스를 종료한다.

## 시나리오 등록

구현을 시작해 업무 전용 공간이 준비된 뒤 등록할 수 있다. 실행 파일은 `node` 또는 `npm run`이며 cwd는 업무 전용 공간 아래의 상대 경로다. 신뢰하는 프로젝트의 **테스트 데이터 전용 서버**를 지정한다. 하드코딩된 운영 DB 연결을 자동으로 안전하게 바꾸지는 못하므로 운영 연결을 사용하는 명령은 등록하지 않는다.

```json
{
  "name": "이름 저장과 새로고침",
  "server": {
    "command": "npm",
    "args": ["run", "dev:test", "--", "--host", "127.0.0.1", "--port", "14321", "--strictPort"],
    "url": "http://127.0.0.1:14321"
  },
  "steps": [
    { "op": "goto", "path": "/" },
    { "op": "fill", "target": { "role": "textbox", "name": "이름" }, "value": "테스트" },
    { "op": "click", "target": { "role": "button", "name": "저장" } },
    { "op": "expectText", "target": { "role": "status", "name": "결과" }, "value": "저장됨" },
    { "op": "reload" },
    { "op": "expectValue", "target": { "role": "textbox", "name": "이름" }, "value": "테스트" }
  ]
}
```

`dev:test`는 해당 프로젝트에서 테스트 전용으로 준비한 스크립트여야 한다. `server.cwd`로 `frontend` 같은 하위 폴더를 지정할 수 있다. 실행기에서 PORT/HOST, NODE_ENV=test, OPENSPEC_VERIFICATION=1, 실행별 DATA_DIR/CONFIG_PATH를 제공한다. 서버는 이 설정을 존중하고 지정한 주소를 사용해야 한다. 개인 환경변수와 앱의 DESKTOP_TOKEN은 전달하지 않는다. 기존 개발 서버는 재사용하거나 종료하지 않는다. 포트 13001~13003은 금지한다.

컴파일된 파일을 제공하는 서버라면 `dev:test`에서 최신 빌드를 먼저 생성해야 한다. 실행기는 작업 경로와 코드 버전을 확인하지만, 프로젝트 스크립트가 오래된 산출물을 제공하는지까지 자동으로 증명하지는 못한다.

요소는 정확한 role/name 또는 `{ "testId": "save" }`로 찾는다. 하나의 요소만 일치해야 한다. `expectVisible`, `expectText`, `expectValue`, `expectURL` 중 최소 한 번의 검사가 필요하다. 비밀번호·파일·숨겨진 필드 입력은 지원하지 않는다. API·WebSocket도 같은 origin만 허용하므로 테스트 서버에서 필요한 API를 제공하거나 테스트 전용 프록시를 구성한다. 프록시는 프로젝트의 신뢰된 테스트 설정이며 외부 운영 API로 연결하지 않아야 한다.

## 결과와 복구

통과·실패·차단·중단·다시 검증 필요를 구분한다. 실행한 단계와 마지막 화면을 확인할 수 있다. 화면과 결과는 AI 진단에도 전달될 수 있으므로 실제 개인정보·비밀값 대신 테스트 값을 사용한다. 서버 원문 로그·인증 상태 파일은 저장하지 않는다. 화면과 단계에 입력한 테스트 데이터는 결과에 남을 수 있다.

코드 또는 시나리오가 변경되면 과거 통과를 완료 근거로 쓰지 않는다. 브라우저 통과는 작업 테스트·전체 테스트·사용자 최종 확인을 대체하지 않는다. 중단과 결과 불명 시 저장·제출을 자동 반복하지 않는다.

Windows에서 Chromium이 페이지·입력 생성 전 메모리 접근 위반(`0xC0000005`)으로 종료됐다고 확인한 경우에만 브라우저 시작을 한 번 다시 시도한다. 시간 초과·권한 오류·사용자 중단은 반복하지 않으며, 입력이나 실패한 시나리오 단계도 다시 실행하지 않는다. 회복한 실행은 결과의 `startupAttempts`와 `startupRecovery`에 기록하고 두 번째 시작도 실패하면 차단 상태로 남긴다. Chromium 샌드박스는 계속 활성화한다.

종료 시에는 Playwright의 정상 종료 및 소유 프로세스 정리 예산(30초)을 포함해 최대 60초 기다린다. 이 동안 통신 경계를 유지하며, 종료가 확인되지 않으면 기존 단계 결과와 관계없이 차단 상태로 남긴다.

새 대화의 AI에는 `browser_verification`의 run/status/cancel만 제공한다. 설치된 Codex 스키마에는 thread/resume의 동적 도구 갱신이 없어 기존 대화는 업무 폴더 `.tools/browser-verification/cli.cjs`를 통해 같은 동작을 요청한다. 프로젝트 Node 런타임으로 CLI를 실행하며 HTTP·네트워크 권한·별도 MCP를 사용하지 않는다. 요청은 해당 업무에 고정되며 등록 명령이나 시나리오를 바꾸지 못한다. 처리 중 요청은 재시작 후 자동 재실행하지 않는다. 대화 ID와 원본 대화 기록을 수정하지 않는다.

시나리오를 등록하면 CLI가 준비되고 AI의 다음 지시에 실제 실행 명령이 포함된다. 결과 JSON의 `imagePath`는 업무 폴더 아래의 화면 파일이다. 통로가 끊기면 업무 화면에서 결과를 확인하고 저장 요청을 자동 반복하지 않는다.

OS 알림·트레이·네이티브 파일 대화상자·실제 모바일·CAPTCHA·외부 로그인은 이 검증의 범위 밖이다. 현재 서버를 운영 반영하려면 모든 실행과 질문·승인이 끝난 뒤 `./scripts/restart.ps1 -Service session`을 명시적으로 수행한다.

## 검증 사본으로 실행하는 개발 변경

`add-git-worktree-workspaces`의 검증 사본 변경은 개발 브랜치에서 구현·검증 중이며 현재 설치본에 반영됐다는 의미가 아니다. 이 변경에서는 기존 대화·턴과 CLI `run/status/cancel`을 유지하고, 호스트 실행기가 업무 폴더 밖의 독점 사본에서 새 테스트 서버를 실행한다. 원본 AI 쓰기를 강제로 멈추거나 쓰기가 멈췄다고 판정하지 않는다.

복사 전후 원본과 사본의 파일 바이트·모드를 비교한다. 링크·공유 하드링크·다른 업무와 경로 겹침·복사 중 변경은 실행 전에 차단한다. `.git`, 운영 데이터·로그·개인 설정·비밀 파일·수정 가능한 CLI 통로는 복사하지 않는다. 검증 중 원본이나 사본 소스·시나리오·대화 실행이 바뀌면 결과를 `stale`로 남긴다. 큰 사본은 비동기 I/O로 준비하며 준비 중에도 중단할 수 있다. 종료가 확인된 소유 사본만 정리하고 불명확한 사본은 보존한다.

이 경계는 정상적인 파일·실행 분리이며 악성 프로젝트 코드의 모든 파일 접근을 막는 OS 샌드박스 보장은 아니다. 현재 단계는 복사한 의존성·산출물 변경도 보수적으로 무효화하므로 테스트 서버가 소스 폴더에 빌드·캐시를 쓰면 `stale`이 될 수 있다. 검토된 산출물 경로와 빌드 출처의 연결은 같은 변경의 그룹 7에서 검증한다. 새 서버의 실행 데이터는 별도 `DATA_DIR`를 사용해야 한다.

## 새 빌드와 실제 응답의 출처 계약 (개발 변경)

그룹7의 개발 변경은 기존 시나리오 JSON을 유지하면서 프로젝트의 `openspec/browser-build.json`을 추가로 요구한다. 계약이 없거나 지원하지 않는 방식이면 실행 결과를 `blocked`로 남긴다. 서버의 health 응답이나 환경 식별값을 되돌려 주는 응답만으로 통과하지 않는다. 현재 설치본 반영과 후보 검증 최신성·CLI 연결·종료 복구 완료는 별도 단계다.

```json
{
  "version": 1,
  "build": { "command": "node", "args": ["build-test.cjs"] },
  "artifacts": [
    { "path": "dist/app.js", "urlPath": "/app.js" }
  ],
  "identity": {
    "path": "dist/.openspec-verification.json",
    "urlPath": "/.openspec-verification.json"
  }
}
```

`build`는 상대 Node 스크립트 또는 인자 두 개의 `npm run <등록 스크립트>`를 지정한다. 산출물과 identity는 `dist/` 또는 `build/` 아래의 고정 상대 일반파일이어야 하며 서로의 경로·URL과 충돌할 수 없다. 링크·공유 파일·비밀/관리 경로와 읽기 한도 초과는 거부한다. 프로젝트는 이 고정 출력 파일을 만드는 테스트 전용 빌드를 준비해야 하며, 기존 산출물만 남기고 성공 종료하는 명령은 준비 완료로 인정하지 않는다. 새 소프트웨어나 의존성을 자동 설치하지 않는다.

호스트가 확인한 독립 사본에서만 선언된 기존 출력 파일을 제거하고 새 빌드를 실행한다. 성공 후 실제 산출물 바이트와 모드를 확인하고 호스트가 identity 파일을 작성한다. 이 파일에는 environmentId·buildId·sourceRevision·계약 버전과 산출물별 URL·SHA256·크기가 들어간다. 등록한 테스트 서버는 identity와 각 산출물의 실제 파일 바이트를 해당 단일 origin의 URL에서 제공해야 한다. 프로젝트 빌드가 identity를 임의로 만들어 환경값만 echo하는 방식으로 대체하지 않는다.

실행기는 브라우저 입력 전에 HTTP 응답과 실제 빌드 파일의 바이트를 대조하고, 통과 확정 직전에도 다시 대조한다. 다른 환경 identity, 오래된/없는 산출물, 응답 변경은 통과하지 않는다. 원본 입력은 그대로 비교하며 독립 사본에서는 정확히 검증한 출력/identity 파일과 필요한 새 부모 디렉터리만 허용한다. 그 외 사본·원본 변경을 디렉터리 전체 제외로 숨기지 않는다. 실행 데이터와 화면 증거는 환경별 호스트 경로에 분리하여 보존하며 정리는 별도 소유 확인 절차를 따른다.
## 대상별 통과 결과의 재확인 (개발 변경)

기본 `GET /api/work/:id/browser`와 `GET /api/work/:id/integration/:candidateId/browser`는 해당 대상의 최근 10개 기록과 현재 실행 상태만 읽는다. 파일·Git을 다시 검사하지 않으며 `observation.state=not-checked`, `fresh=false`는 아직 재확인하지 않았다는 뜻이다. 저장된 passed 이력과 현재 유효 판정을 구분한다. 실제 재확인은 같은 주소의 `?inspect=1`로 요청한다. 다른 query는 허용하지 않는다.

업무 통과는 후보 통과로 사용하지 않는다. 최신 후보 CLI와 같은 후보의 브라우저 통과가 모두 있어야 반영 근거가 된다. 환경·새 빌드 출처·부모가 확인한 실행 종료·입력·계획·설정의 연결 근거가 없는 구형 passed는 재검증해야 한다. 후보 ID/세대/commit과 실제 원본 대상 ref가 달라져도 기존 후보 근거는 사용할 수 없다. 늦은 상태 조회는 새 후보 세대나 새 실행 결과를 덮지 않는다.

실제 입력이 같은 업무의 결과 commit만 바뀌면 실행 당시 commit 이력을 그대로 보존하며 통과 근거를 다시 사용할 수 있다. 기본 정책은 tasks 체크 표시 변경도 입력 변경으로 본다. 프로젝트가 테스트 빌드와 서버에 체크 표시가 영향을 주지 않는다고 명시적으로 선언할 때만 companion 계약에 `"freshness": { "tasksCheckboxes": "independent-plan-metadata-v1" }`을 추가한다. 해당 업무 tasks.md의 체크 표시만 정규화하며 본문·AGENTS·코드·설정·의존성은 계속 판정 입력이다. 출력 제외도 계약에 고정된 artifact/identity 파일과 필요한 부모 디렉터리에만 적용한다. 별도 CLI 검증 정책과 자동으로 공유하지 않는다.
개발 브랜치 화면의 **결과 새로고침**은 기록만 읽고, **검증 결과 최신성 확인**만 현재 파일·Git 기준을 명시적으로 검사한다. 자동 조회의 **최신성 미확인**은 실패나 stale 확정과 구분한다. 결과에서 업무/후보, 실행 환경, 확인된 실제 빌드와 실행 당시 커밋을 볼 수 있다. 실행 POST 응답을 기다리는 중에도 조회를 사용할 수 있지만 결과 불명인 변경 요청을 자동 중단·반복하지 않는다. 현재 화면 연결만으로 운영 설치본이나 전체 후보 실행 UI 검증이 완료된 것은 아니다.
## 기존 대화 CLI의 실행 컨텍스트 (개발 변경)

CLI의 `run/status/cancel` 명령 형식은 유지한다. 호스트가 확인한 업무 통로에 배치한 context.json의 contextId를 CLI가 자동 동봉하고, 서버는 업무·대화·턴·실행 세대·시나리오 및 사용자 선택 대상을 대조한다. contextId는 오래된 요청을 구분하는 표식이며 신뢰된 실행기·쓰기 중지·사본 소유를 증명하지 않는다. 실제 run은 공통 resolver와 호스트 독립 사본 검사를 새로 통과해야 한다. AI가 임의 경로·명령·업무·후보를 선택할 수 없다.

요청 ID와 처리 결과는 호스트 DB에 보존한다. run 응답은 시작한 정확한 run ID와 완료 promise에 연결하고 status/cancel은 같은 대상·컨텍스트에 한정한다. 대상이나 대화 세대가 바뀌면 과거 queued run은 거부하며 자동 전환·재실행하지 않는다. 기존 상태와 소유 실행의 중단 통로는 경계 확인 실패 시에도 유지한다. 실제 통로의 소유/링크/공유 파일이 바뀌면 그 위치로 쓰지 않고 호스트 기록을 보존한다.

재시작 때 남은 processing은 같은 requestId의 interrupted 응답으로 남기며 알려진 runId·관측 상태·종료 미확인 정보도 보존한다. 이를 프로세스의 실제 종료나 원래 검증 성공으로 바꾸지 않는다. 남은 요청은 한 번에64개씩 다음 poll에서 이어서 처리하며 실행을 다시 시작하지 않는다. 이 한도는 디렉터리 전체 열거나 모든 호스트 기록을 읽는 비용까지 일정하게 만든다는 보장이 아니다.

화면 원본은 환경별 호스트 evidence 경로에 보존한다. CLI imagePath는 확인한 원본 바이트와 일치하는 업무 통로 복제본이며 다른 업무의 자료나 임의 경로는 제공하지 않는다. 통로가 유실돼도 호스트 결과를 덮거나 검증을 자동 반복하지 않는다.
