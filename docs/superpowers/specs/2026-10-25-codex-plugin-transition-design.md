# Codex 전용 OpenSpec 플러그인 전환 설계

작성일: 2026-10-25
상태: 설계 검토 대기 — 구현 전

## 목적과 결정

사용자는 Codex만 지원하는 구성을 선택했다. 아이디어, 요구사항 문답, OpenSpec 문서 작성, 구현, 검증, 보관을 Codex 대화에서 진행한다. 별도 앱의 대화·승인·실행 기능 유지보수를 줄인다.

추천 구조는 OpenSpec 스킬 플러그인과 선택적인 조회용 대시보드다. Codex 자체에 임의의 메뉴나 사이드바를 추가할 수 있다는 전제를 두지 않는다. 전용 MCP Apps UI가 이 Codex 환경에서 표시되는지도 아직 검증하지 않았다.

## 비교한 접근

1. 스킬만 배포: 가장 작고 로컬 CLI·파일로 동작하지만 변경 현황과 문서 비교가 불편하다.
2. 스킬 플러그인 + 조회 화면: 권장안. 개발은 Codex에서 진행하고 기존 보드·문서 뷰어를 선택적으로 재사용한다.
3. 기존 독립 앱 유지: 기존 기능을 유지할 수 있지만 대화 복구·승인·실행 관리 비용이 계속 발생한다.

## 역할

- Codex: 사용자 대화, 질문, 승인, 코드 수정, 명령 실행, 중단, 변경 검토, Git 작업.
- 플러그인 스킬: OpenSpec 절차, 산출물 작성 순서, 검증 및 보관 기준.
- OpenSpec CLI와 프로젝트 파일: 명세·변경 문서·작업 체크리스트의 기준 데이터.
- 선택적인 대시보드: 아이디어, 변경 목록, 문서, 명세, 파일에서 확인 가능한 진행 상태를 조회한다.

단계별 의도는 스킬로 전달한다. 스킬의 지침만으로 기술적인 실행 차단이나 강제 승인이 보장된다고 주장하지 않는다.

## 1차 구현 범위

- 기존 .agents/skills의 explore, propose, update-change, apply-change, sync-specs, archive-change 6개를 설치 가능한 로컬 Codex 플러그인으로 패키징한다.
- 현재 설치된 Codex의 로컬 플러그인 매니페스트와 설치 방식을 확인한 뒤 호환되는 형식을 사용한다. 공개 디렉터리 등록은 범위에 포함하지 않는다.
- 기존 스킬과 패키지의 스킬이 동시에 실행 후보로 중복 등록되지 않도록 설치·활성화 방식을 검증한다. 검증 전 기존 스킬을 삭제하지 않는다.
- 현재 프로젝트 폴더에서 OpenSpec CLI와 파일을 직접 사용한다. 1차에는 별도 MCP 서버를 만들지 않는다.
- 요구사항 정리 → 계획 문서 검토 → 구현 → 검증 → 보관의 기본 흐름을 정의한다. 사용자가 명시적으로 요청한 범위와 승인 경계를 따른다.
- 샘플 변경 하나로 플러그인 인식과 전체 흐름을 확인한다. 실제 프로젝트 변경을 검증용으로 자동 보관하지 않는다.

## 2차 범위: 조회 화면

- 1차가 검증된 뒤 기존 보드와 문서 뷰어의 재사용 범위를 확정한다.
- 첫 화면 연동 실험은 기존 로컬 웹 화면을 Codex의 브라우저 패널에서 열어 확인한다. 실패하면 제한을 명시한다.
- 조회 화면에서 별도 Codex 대화를 만들거나 프롬프트를 실행하지 않는다.
- 업무 수행은 사용자가 현재 Codex 대화에 요청한다. 화면의 버튼이 현재 대화로 명령을 보낼 수 있다고 가정하지 않는다.
- OpenSpec 파일에서 확인 가능한 상태만 표시한다. CLI 또는 파일 조회 실패를 완료 상태로 바꾸지 않는다.
- 기존 전용 대화 관리·승인 중계·실행 서비스는 대체 흐름을 검증한 후 사용 중단한다. 이번 전환 설계 단계에서 제거하지 않는다.

## 데이터와 호환

- 각 프로젝트의 openspec/가 문서와 작업 상태의 기준이다.
- config.local.json, .data/work.sqlite 및 기존 이력은 보존한다. 기존 DB 이력을 자동으로 Codex 대화 이력으로 이전한다고 약속하지 않는다.
- 기존 프로젝트 등록 설정은 조회 화면이 필요할 때 재사용한다.
- 진행 중인 프런트엔드 다국어 작업과 OpenSpec 변경 문서는 별도 변경으로 보존한다.
- GitHub 저장소는 비공개를 유지한다. 플러그인 공유·공개 게시·외부 서버 배포는 포함하지 않는다.

## 오류와 경계

- 플러그인을 인식하지 못하면 설치 위치·매니페스트·지원 버전을 진단하고 실패를 보고한다.
- OpenSpec CLI가 없거나 해당 명령을 지원하지 않으면 실제 오류를 보고하며 다른 AI 도구로 전환하지 않는다.
- 문서 파일의 변경을 곧바로 구현 완료나 검증 통과로 간주하지 않는다.
- 실행 권한은 Codex의 승인 정책을 따른다. 별도 서비스에서 일괄 승인하지 않는다.
- 문서 검증과 코드 테스트 결과는 구분한다. 테스트 결과에는 실행 명령과 실제 결과를 남긴다.

## 검증과 완료 기준

1. 로컬 Codex가 플러그인을 발견하고 6개 스킬을 사용할 수 있다.
2. 검증용 프로젝트에서 제안, 수정, 구현, 검증, 보관 흐름을 수행하고 파일 산출물을 확인한다.
3. 이 흐름에 기존 backend/src/codex의 app-server 중계가 필요하지 않다.
4. 명령 실패와 검증 실패를 성공으로 표시하지 않는다.
5. 기존 미커밋 변경과 데이터가 보존된다.
6. 화면 테스트는 사용자 설치 ChatGPT 확장을 통한 Microsoft Edge에서 수행한다. 확장 접근이 불가능하면 브라우저 검증을 미실시로 보고한다.
7. Codex 내부 패널 표시와 Edge 브라우저 검증은 별개로 기록한다.

## 후속 작업 순서

설계 검토 → 설치 방식 확인 및 구현 계획 → 스킬 플러그인 패키징 → 샘플 흐름 검증 → 조회 화면 연결 실험 → 기존 서비스 축소 범위 확정.
