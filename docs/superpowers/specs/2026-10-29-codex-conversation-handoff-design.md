# OpenSpecBoard 점유 충돌 복구와 모바일 Codex 원격 제어 설계안

상태: 2026-10-29 사용자 구현·커밋·배포 승인. 우선 범위는 아래 1~3항이며, 동일 대화 왕복은 후속 검토다. 실제 모바일 연결 검증은 별도 필요하다.

## 2026-10-29 사용자 요구에 따른 방향 수정

최우선 목적은 같은 대화 ID의 왕복 자체가 아니다. 다른 프로세스의 대화 점유로 Board에서 업무를 진행하지도 종료하지도 못하는 상황을 방지하고, 모바일 Codex를 통해 PC의 Board 업무를 원격으로 지시하는 것이다. 아래 기존 왕복 설계는 선택적 후속 기능으로 두며, 우선 구현 범위를 다음 세 항목으로 변경한다.

### 1. 외부 점유 충돌로 인한 Board 잠김 방지

- 외부 점유 오류와 Board가 시작한 실행의 종료 여부 미확인을 구별한다. 외부 점유만 확인된 업무는 Board의 실행 중인 프로세스로 취급하지 않는다.
- 업무별 연결·요청을 격리하고 연결 시도에 제한 시간을 둔다. 실패 시 화면과 조작을 복원하며, 다른 업무의 실행·문서 열람·Board 종료를 막지 않는다.
- 외부 점유 업무에는 상태 재확인과 재연결을 제공한다. 상대 프로세스의 실제 실행 여부를 확인할 수 없으면 모른다고 표시한다.
- 외부 점유가 계속되면 아래 3항의 `복구용 새 세션으로 이어하기`를 제공한다. 미확인 실행이 있으면 같은 폴더에서 새 변경 작업을 시작하지 않는다.
- 외부 Codex 프로세스 전체 강제 종료, 잠금 파일 삭제, 근거 없는 정상 상태 덮어쓰기를 복구 수단으로 사용하지 않는다.

### 2. 모바일 Codex를 Board의 원격 조종 창으로 사용

권장 흐름은 `모바일 Codex → 연결된 PC의 Codex → Board 전용 로컬 연결 도구 → Board 업무 실행기`이다. 모바일 Codex의 조종 대화와 Board의 업무 대화는 별개로 둔다. Board 업무 실행기는 계속 한 곳에서만 실행을 소유하므로, 원격 제어 때문에 같은 대화의 writer lock을 서로 가져갈 필요가 없다.

- Board 전용 연결 도구는 PC에서 사용할 수 있는 로컬 CLI 또는 MCP 인터페이스로 제공한다. 모바일 Codex에서 해당 도구를 실제로 호출할 수 있는지는 설치된 원격 환경에서 검증한다.
- 최초 범위는 업무 목록·상태 조회, 사용자 지시 전송, 질문·승인 조회 및 명시적 응답, 해당 업무 실행 중단 요청, 결과 조회이다. 중단 요청과 중단 완료는 구별한다.
- 원격 지시는 Board의 기존 검토·승인·작업 폴더 제한을 그대로 통과한다. Codex에 별도 파일 수정 작업을 시키면서 Board 실행기를 동시에 가동하는 구조로 만들지 않는다.
- 상태 조회 등 읽기 요청은 실행 점유와 분리한다. 실행 요청은 즉시 명령 ID를 돌려주고 상태를 후속 조회하여, 긴 실행 때문에 원격 연결 전체가 묶이지 않도록 한다.
- 명령 ID로 중복 전송을 막고 업무별 실행 순서를 지킨다. 통신 시간 초과 시 실행을 자동 재전송하지 않고 기존 명령 상태를 조회한다.
- 사용자에게 표시된 질문·승인의 ID와 버전을 검증한다. 만료되거나 이미 처리된 요청에 답하지 않고, 원격 도구가 승인을 임의로 생성하지 않는다.
- Board API를 인터넷에 직접 공개하지 않는다. 로컬 인증과 접근 범위를 적용하며 인증 정보는 대화나 도구 출력에 포함하지 않는다. 모바일 연결은 공식 Codex 원격 기능을 이용한다.
- 사용자가 현재 이용할 계정·기기에서 원격 기능을 사용할 수 있는지, PC가 온라인 상태인지, 모바일에서 연결 도구를 호출할 수 있는지 실제로 확인한다. 아직 확인되지 않은 기능을 사용 가능으로 표시하지 않는다.

### 3. 잠금 지속 시 복구용 새 세션으로 이어하기

같은 대화 재연결이 제한된 횟수와 시간 안에 실패하면 `복구용 새 세션으로 이어하기`를 제공한다. 새 세션이 기존 네이티브 대화를 그대로 계승하는 것은 아니며, 별도의 대화 ID로 문맥과 실제 파일 상태를 복원하는 방식임을 표시한다. 기본은 사용자가 복구를 선택하는 방식이다. 향후 자동 복구를 제공하더라도 별도 설정과 아래 실행 확인 조건을 동일하게 적용한다.

복구 절차:

1. 원래 대화 ID, 마지막 확인한 실행 ID와 상태, 잠금 원인, 재연결 시도 결과를 보존한다. 실패한 재연결을 무한 반복하지 않는다.
2. 해당 업무에 복구 잠금을 걸고 이전 실행과 자식 작업의 종료 여부를 확인한다. 연결 해제, 응답 시간 초과, 프로세스 ID 소멸만으로 실행 종료를 단정하지 않는다.
3. 기존 대화에서 목표·결정 사항·사용자 제약·완료 작업·미완료 작업·마지막 확인 결과를 정리한다. 대화 조회가 불가능하면 Board 보관 기록을 사용하고, 누락된 범위와 출처를 명시한다. 과거 대화나 파일 내용은 참고 자료로 구분하며 현재 사용자 지시나 승인으로 취급하지 않는다.
4. 현재 작업 폴더와 Git 변경 사항, OpenSpec 문서·작업 목록을 읽어 인계 자료에 기록한다. 파일의 실제 상태를 기준으로 완료 여부를 재검토하며, 요약만 믿고 완료 처리하지 않는다. Git 미사용 폴더는 파일 변경 정보로 대신하고 그 한계를 표시한다. 임의 reset·checkout·stash·파일 덮어쓰기는 하지 않는다.
5. 인계 자료를 먼저 저장하고 새 세션을 만든다. 원래 업무 ID와 executionPath는 유지하며, 이전/새 대화 ID·복구 ID·시각·이유·인계 자료 위치를 기록한다. 이전 기록을 새 기록으로 덮어쓰지 않는다.
6. 이전 실행의 종료가 확인된 경우에만 새 세션에 변경 작업을 허용한다. 종료를 확인하지 못하면 새 세션은 보존된 자료의 조회·계획만 허용한다. 이 제한은 프롬프트뿐 아니라 도구·파일 접근 권한에서도 적용하며 기존 작업 폴더 쓰기와 임의 명령 실행을 허용하지 않는다. 필요하면 별도 스냅샷을 사용하고, 원본 접근까지 안전하게 제한할 수 없으면 세션 시작을 보류한다.
7. 새 세션은 인계 자료와 현재 파일을 대조해 재개 지점을 제시한다. 기존 지시·대기 메시지·명령을 자동 재전송하지 않는다. 기존 검토·승인 규칙을 통과한 작업만 이어간다.

복구 실패와 재시작 처리:

- 업무별 복구 ID와 단계 상태를 영속 저장한다. 중복 클릭·원격 재전송·Board 재시작 후에도 같은 복구 요청으로 세션을 여러 개 만들지 않는다.
- 새 세션 생성 요청의 결과가 불명확하면 생성 여부를 먼저 확인한다. 새 세션을 무작정 다시 만들지 않고 `복구 결과 확인 필요`로 표시한다.
- 복구가 실패해도 원래 대화·초안·파일·인계 자료를 유지한다. 업무 화면에는 진행 단계, 차단 이유, 재확인·재시도 방법을 제공한다.
- 이전 세션이 뒤늦게 응답해도 새 세션의 실행 상태나 현재 대화 ID를 덮어쓰지 않도록 대화 ID와 연결 세대를 검증한다. 늦은 기록은 원래 세션 이력으로만 보존한다.
- 이전 세션의 질문·승인을 새 세션의 요청으로 옮기거나 자동 승인하지 않는다. 세션별 대기 요청을 구분하고, 정리 여부가 불명확하면 변경 작업 재개를 보류한다.
- 원격 연결 도구에서도 동일한 복구 상태 조회와 명시적 복구 요청을 제공한다. 모바일 연결 자체는 복구 실행 권한이나 승인 요건을 우회하지 않는다.

### 수정된 완료 기준

외부 점유 충돌 상태에서도 Board의 조회·다른 업무·정상 종료가 가능해야 한다. 모바일에서 시험 업무의 상태 확인 → 지시 → 필요한 질문·승인 응답 → 결과 확인 → 실행 중단을 검증한다. 연결 끊김과 중복 전송 상황에서도 같은 명령을 두 번 실행하지 않아야 한다. 기존 사용자 대화와 실행 중인 세션을 시험용으로 변경하지 않는다.

새 세션 복구에 대해서는 잠금 지속 → 제한된 재연결 → 실행 상태 확인 → 인계 자료 저장 → 새 세션 생성 → 파일 대조 → 재개를 검증한다. 이전 실행 미확인 시 파일 쓰기 차단, 대화 조회 실패 시 누락 표시, 중복 요청 및 생성 결과 불명확 시 중복 세션 방지, 복구 도중 재시작, 이전 세션의 늦은 알림, 과거 승인 재사용 방지를 각각 검증한다. 이전 실행 종료가 확인된 복구에서는 새 대화 ID와 원래 작업 폴더를 유지하면서 완료 작업의 중복 실행 없이 계속할 수 있어야 한다.

이하 내용은 우선 범위에서 제외된 동일 대화 왕복의 참고 설계다.

## 목적과 권장 방식

OpenSpecBoard에서 진행하던 OpenSpec 업무를 Codex 데스크톱의 같은 대화에서 이어가고, 이후 OpenSpecBoard로 돌아와 계속한다. 대화 ID, 실제 작업 폴더, OpenSpec 변경 이름을 유지한다.

방식 비교:

| 방식 | 장점 | 제약 |
| --- | --- | --- |
| 같은 대화로 전환 — 권장 | 기존 문맥과 대화 ID 유지 | 실행 소유권 이전 및 기존 도구의 호환성 검증 필요 |
| 새 대화에 요약 인계 | 앱별 도구 차이에 대응하기 쉬움 | 원래 대화와 분리되며 생략된 문맥 발생 가능 |
| 두 앱에서 동시에 실행 | 전환 동작 최소화 | 파일 수정과 답변 생성 충돌 위험 때문에 채택하지 않음 |

## 사용자 동작

1. Codex 기반 업무에 `Codex에서 이어하기`를 제공한다. 기존 대화가 없는 업무는 전환할 수 없다.
2. 입력 초안을 먼저 로컬에 보존한다. 초안을 자동 전송하지 않는다.
3. 실행·검증·질문·승인·전송 대기 상태를 확인한다. 상태가 불명확하면 전환하지 않고 이유와 복구 방법을 표시한다.
4. 해당 업무의 OpenSpecBoard 연결이 해제된 사실을 확인한 뒤 `codex://threads/<thread-id>`로 기존 대화를 연다.
5. 외부 전환 중인 업무에는 `Codex에서 작업 중` 상태와 `OpenSpecBoard로 돌아오기`를 표시한다. Board에서는 해당 업무의 AI 실행과 문서를 변경하는 작업을 막는다. 다른 업무는 계속 사용할 수 있다.
6. 돌아올 때 같은 대화의 새 사용자 메시지와 답변, 실제 문서 변경을 가져온다. Codex가 아직 실행 소유권을 갖고 있으면 복귀를 보류하고 해당 대화를 종료하거나 실행을 마치도록 안내한다.

Codex 링크 열기에 실패하면 전환 상태와 재시도 방법을 표시한다. 상태가 확정되지 않은 상황에서 자동 재전송하거나 새로운 대화를 만들지 않는다.

## 실행 소유권과 장애 처리

- 저장 상태는 `board`, `transferring`, `codex`, `returning`으로 구분한다. 실패 이유와 마지막 확인 시각을 함께 저장한다.
- 전환과 복귀는 업무 단위의 중복 방지 잠금 및 영속 상태로 보호한다. 같은 버튼을 여러 번 누르거나 앱이 재시작되어도 실행이 중복되지 않아야 한다.
- 현재 여러 업무가 하나의 Codex app-server 프로세스를 공유한다. 특정 업무를 넘기기 위해 공유 프로세스를 종료하지 않는다. 업무별 연결로 격리하거나, 검증된 동등한 연결 해제 방식을 구현한다.
- `thread/unsubscribe` 성공만으로 실행 소유권 해제가 완료되었다고 판단하지 않는다. 실제 재개 가능 여부를 검증한다.
- 복귀 중 소유권 충돌 또는 통신 실패가 발생하면 외부 전환 상태를 유지한다. 강제 종료로 Codex 데스크톱이나 다른 업무를 중단하지 않는다.
- 외부 전환 상태는 Board 자체의 실행 중인 작업으로 계산하지 않는다. 기존 질문·승인·알 수 없는 실행을 감추는 수단으로 사용하지 않는다.

## 대화와 문서 동기화

- 공식 대화 조회 API와 페이지별 turn/item 조회를 사용한다. rollout 파일을 수정하거나 잠금 파일을 삭제하지 않는다.
- thread/turn/item ID와 메시지 종류를 기준으로 가져온 기록을 식별하고 중복을 방지한다. 여러 번 복귀를 시도해도 메시지가 늘어나지 않아야 한다.
- 완료된 사용자·AI 메시지를 가져오며, 과거 승인·질문·도구 실행을 현재 처리 대기 요청으로 재생하지 않는다. 미완료 실행은 복귀 가능한 상태로 간주하지 않는다.
- 업무에 고정된 executionPath를 유지한다. Git worktree 업무를 프로젝트 원본 폴더로 바꾸지 않는다.
- Codex에서 바뀐 OpenSpec 문서를 다시 읽고, 기존 문서 검토·승인 규칙에 따라 재검토 여부를 갱신한다. 대화 복귀만으로 업무 단계를 완료하거나 배포하지 않는다.
- 대화가 없거나 경로가 맞지 않거나 계정의 대화 저장소에 접근할 수 없으면 이유를 표시한다. 요약 방식으로 조용히 바꾸지 않는다.

## 데스크톱 연결 보안

선택한 업무 ID만 받는 전용 IPC를 사용한다. 메인 프로세스가 서버에서 전환 가능한 업무와 유효한 Codex 대화 ID를 확인한 다음 고정된 Codex 링크를 만든다. 렌더러가 임의 URL이나 실행 명령을 넘길 수 없게 한다. 기존 소유 창·main frame·origin 검사를 유지한다.

## 구현 전에 확인해야 할 호환성

공식 문서는 기존 대화 열기와 조회·재개 API를 제공하지만, 현재 설치 버전에서 다음 왕복 동작은 아직 검증하지 않았다.

1. Board의 연결 해제 후 Codex 데스크톱이 동일 대화를 즉시 열어 재개할 수 있는가.
2. Board 대화에 저장된 사용자 질문·브라우저 검증 등의 사용자 정의 도구를 Codex 데스크톱에서 처리할 수 있는가.
3. Codex에서 작업을 마친 후 Board가 안전하게 소유권을 다시 얻고 기록을 가져올 수 있는가.

먼저 격리된 테스트 대화와 작업 폴더에서 확인한다. 기존 사용자 대화를 시험 삼아 변경하거나 현재 Codex 프로세스·세션 서버를 재시작하지 않는다. 호환되지 않는 항목이 있으면 같은 대화 방식의 한계를 명시하고 해결안을 확정한 뒤 사용자 기능을 활성화한다.

## 검증 및 완료 기준

- Board → Codex → Board 왕복 후 대화 ID와 실제 작업 폴더가 같다.
- 두 방향에서 작성한 사용자·AI 메시지를 Board에서 정확히 한 번씩 볼 수 있다.
- 두 앱에서 동시에 같은 업무를 실행할 수 없다.
- 다른 업무 실행은 전환의 영향을 받지 않는다.
- 대기 질문·승인·검증·알 수 없는 실행·전송 중 요청은 전환을 차단한다.
- 재시작, 링크 열기 실패, API 시간 초과, 소유권 충돌, 중복 클릭 시 초안과 대화가 보존된다.
- 위 상태 전이와 기록 중복 방지를 자동 검증하고, Codex 데스크톱 실제 왕복 결과를 별도로 기록한다. 수행하지 못한 검증을 통과로 보고하지 않는다.
