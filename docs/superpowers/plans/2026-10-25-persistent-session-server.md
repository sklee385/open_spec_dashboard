# 서버 재시작 중 대화 유지

원인: Nest 웹 API가 Codex 자식 프로세스·질문 요청·업무 실행을 함께 소유하며 종료 시 Codex도 닫는다. 프런트엔드 SSE는 재연결하지만 종료된 실행과 질문을 살릴 수 없다.

설계: 기존 Nest 업무 API를 별도 상주 세션 서버(127.0.0.1:13003)로 실행하고 공개 로컬 API 주소 13002는 스트리밍 프록시로 둔다. UI 주소 13001과 API 계약은 유지한다. 프록시 재시작은 세션 서버·Codex·질문·SQLite에 영향을 주지 않는다. 두 프로세스는 시작 스크립트에서 각각 독립 실행한다. 개발 watch는 프록시만 대상으로 하며 세션 서버는 자동 교체하지 않는다. 세션 코드 교체는 진행 업무가 없을 때 명시적으로 수행한다.

냉간 복구: 세션 서버 자체가 종료된 경우 원래 대화 ID를 유지한다. ID 조회에서 원본 기록을 찾지 못할 때만 Codex 홈의 세션 파일을 탐색하여 session_meta ID와 프로젝트 경로를 검증한 뒤 path로 resume한다. 새 대화나 새 메시지를 자동 생성하지 않는다.

검증 순서:
1. 실행 중·질문 대기 중 프록시를 종료하고 다시 만들어도 같은 threadId·질문 requestId가 유지되는 통합 테스트.
2. 세션 서버의 SSE에 프록시를 재연결하여 저장된 이벤트를 다시 수신하는 테스트.
3. 세션 서버 미기동 시 안전한 503 응답을 확인한다.
4. 대화 파일 ID 조회 실패와 검증된 path 복구 및 불일치 파일 거부를 테스트한다.
5. 기존 Codex·업무 테스트, 백엔드 빌드를 수행한다. 실제 서버에 반영 시 진행 업무는 임의 재시작하지 않고 상태를 확인한다.

제약: 세션 서버 자체의 크래시·OS 종료까지 진행 중인 모델 호출을 계속 유지할 수는 없다. 이 경우 기록·작성 답변·대화 ID를 보존하고 연결만 복구한다. 불확실한 명령·메시지는 자동 재전송하지 않는다.

추가 원인: 실제 오류 로그에 보관된 변경의 이전 문서 경로를 완료 알림이 읽다가 ENOENT로 프로세스가 종료된 기록이 있었다. 보관 경로 조회 및 알림 처리 오류 경계를 추가하고 해당 상황을 재현한 테스트를 통과했다.

검증 결과: 백엔드 전체 66개, 프런트엔드 복구·비교 7개 테스트 통과. 백엔드 빌드 및 프런트엔드 번들 빌드 통과. 전체 프런트엔드 타입 검사에는 기존 ApprovalRequest 및 작성 중인 MarkdownDocument/MermaidBlock 테스트 등의 오류가 남아 있다.

실제 전환: 실행 중 업무가 없음을 확인한 뒤 13003 세션 서버와 13002 게이트웨이를 독립 실행했다. 기존 업무 대화 `01a170fc-033f-7823-8285-5b84aaa6436e`를 검증된 원본 기록으로 복구했다. 실제 웹 서버 재시작 전후 세션 PID 467148 및 저장 이벤트 8082개, 같은 threadId, idle 상태와 오류 해제 상태가 유지됨을 확인했다. 기록은 `.data/e2e/session-restart-proof.json`에 저장했다.

최종 확인: 사용자가 같은 업무 구현을 재개한 뒤 웹 게이트웨이를 다시 교체했다. 세션 PID 467148과 같은 threadId가 유지됐고 실행 상태는 running, 오류는 없었다. Edge 확장에서도 실시간 연결과 새 AI 메시지 도착을 확인했다. 화면은 `.data/e2e/session-continuity.png`에 기록했다. 초기 화면 요청이 503으로 실패한 경우에도 1~5초 간격으로 업무 조회를 재시도하며 AI 메시지는 재전송하지 않는다.
