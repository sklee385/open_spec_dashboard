> 현재 유효 결정(2026-10-29): 사용자가 “검증 사본 방식으로 변경하고 개발 진행 (권장)”을 명시적으로 선택했다. 원본 쓰기 강제 중지·점유 양도 요구를 검증 사본 격리·원본 변경 시 결과 무효화로 대체한다. 아래 과거 승인·재검토·구현 대기 기록은 이 결정 이전의 이력이며 새 승인 요구가 아니다. 같은 대화·턴과 status/cancel을 유지하고 자동 턴 중단·새 대화·운영 재시작을 하지 않는다.

# Design

## Context

2026-10-27 계획 초안이다. `source-ideas/idea-1793027147666-7c112b24.md`와 `docs/superpowers/specs/2026-10-26-worktree-workspaces-design.md`를 읽고 실질 설계를 옮겼다. 원문의 과거 검토 상태를 소급 승인 처리하지 않는다. 동기는 proposal.md를 따른다.

현재 `FileResults`는 프로젝트 복사, 시작 스냅샷, 해시 기반 원본 반영을 제공한다. `Work.executionPath`와 복구 로직은 공간 식별을 확인한다. coordinator는 경로와 Git common-dir를 함께 잠그고 질문·승인 대기 업무까지 검사하여 linked worktree 간 실행을 과도하게 차단할 수 있다. resolver는 원본/업무 공간과 linked worktree를 이미 구분한다.

`browser.service.ts`는 `FileResults.path()`에 직접 의존하고 소스 revision·시나리오·mutation 버전으로 최신성을 판정한다. runner는 등록한 단일 origin, 새 서버, 실행별 임시 데이터, 전용 런타임과 Job Object를 사용한다. 동시 브라우저 요청은 현재 거부한다. mailbox는 `.tools/browser-verification/cli.cjs`와 업무별 요청/결과를 사용한다. 이 코드와 관련 테스트가 존재하며 source-ideas에는 구현·분할 회귀 검증 완료 보고가 보존돼 있다. 이번 계획에서 그 테스트를 다시 수행하거나 실행 중인 13003 서버에 반영됐다고 확인한 것은 아니다.

현재 설정은 `LegacyService.configPath`의 프로젝트 설정과 인접한 `ai-tools.json` 등으로 나뉜다. 새 공간 설정은 기존 프로젝트 설정에 별도 키를 추가하고, 모든 해당 파일 저장 호출이 알 수 없는 키를 보존하도록 함께 수정한다. 독립적인 두 번째 공간 설정 파일은 만들지 않는다.

## Goals / Non-Goals

- 공간 선택·생성·실행·검증·통합·정리를 동일한 소유 식별과 버전 근거로 연결한다.
- 기능 도입은 초기 설정부터 순차 진행하고, 안전한 통합 경로가 검증되기 전 신규 워크트리를 일반 기본값으로 활성화하지 않는다.
- 자동 기존 공간 이동, 원격 push, dirty 원본 전체 수입, 자동 stash/reset/강제 제거, 범용 개발 서버 관리 및 전용 병합 편집기는 제외한다.

## Decisions

사용자는 이 채팅에서 “추천하는데로 진행해”라고 답변했으며, 연결 종료로 만료된 질문의 복구 답변에서 Q1~Q6 모두 권장안으로 확정했다. 아래 설계와 차이 명세에 그 결정을 반영한다. 이후 사용자의 명시적 문서 검토 완료·구현 시작 지시로 초기 구현을 진행했다. ‘검증 환경 준비 후 계속’을 반영한 문서의 사용자 검토와 기록 반영본 재검토 완료는 각각 복구된 명시적 답변으로 확인했다. 2026-10-27 사용자의 “검토 완료 다시 구현 시작해라”라는 별도 지시로 구현을 재개했으며, 먼저 검증 환경 준비와 1.6 실제 검증을 수행한다. 정책 결정 승인·과거 구현 허가·문서 검토 완료만을 구현 재개 지시로 처리한 것이 아니다.

### 1. 도입 방식과 구성 요소

| 대안 | 이점 | 비용 |
| --- | --- | --- |
| 복사 격리만 강화 | 변경 범위가 작음 | 이력·병합 기능을 직접 구현해야 함 |
| 새 Git 업무에 워크트리 도입 — 권장 | 기존 업무 보존과 Git 통합 활용 | 두 공간 종류의 공존 필요 |
| 기존 업무까지 일괄 전환 | 모델 통일 | 실행·대화·검증 근거 이전 위험 |

신규 `workspace.service.ts`는 공통 경로·소유 식별을 제공하고 copy는 기존 FileResults 구현에 위임한다. `worktree-manager.ts`는 검증된 인자 배열로 Git 생성·조회·정리를 담당한다. `integration.service.ts`는 후보·검증·반영 상태를 소유한다. `workspace-settings.service.ts`/controller는 기존 설정 저장 경로·원자 쓰기를 공유한다. 용량 집계와 검증 환경 관리도 독립 모듈로 분리하여 실행·정리 정책이 같은 경로 판정을 사용하게 한다.

### 2. 초기 위치 설정과 경로 유지

- 우선순위는 명시적 `WORKSPACE_ROOT` → 저장 설정 → 최초 안내다. 환경 고정 시 출처와 편집 제한을 표시한다. 신규 공간은 검사된 경로를 사용자가 확인한 뒤 생성한다. 환경값도 최초 사용 전에 검사·확인을 거친다.
- 기존 설정 화면에 현재 경로·출처·가용성·잔여 공간과 검사/저장을 제공한다. 데스크톱은 폴더 선택, 그 밖은 실행 호스트의 절대 경로 입력을 제공한다. 실제 작업 전용 폴더는 기능 구현 후 설정 화면에서 사용자가 선택한다.
- 서버는 절대 로컬 경로만 받는다. UNC, 드라이브 루트, 원본·Git 관리·운영 DB·설정·설치 영역과 양방향 포함 관계를 거부한다. 기존 부모부터 realpath·대소문자·reparse point를 검사하고 생성/정리 직전 재검사한다. 고유 probe 파일의 읽기/쓰기/삭제만 확인하고 ACL을 변경하지 않는다.
- 기존 폴더 내용은 보존하고 `openspecboard-<profileId>` 관리 하위 공간을 만든다. 루트별 `rootId`와 profile 소유권, 설정 버전 토큰을 저장한다. 오래된 저장을 거부하고 설정을 원자 교체한다. 프로젝트/도구 설정 저장이 공간 설정을 유실하지 않도록 회귀 검증한다.
- 업무·후보는 생성 당시 `rootId`, `workspaceId`, 절대 경로를 고정 저장한다. 루트 변경은 다음 신규 공간에만 적용한다. 이전 루트는 조회·용량·정리를 위해 남기며 질문·승인·대화·테스트 서버 경로를 변경하지 않는다. 루트 등록 해제는 업무·후보 참조가 없을 때만 허용한다.
- 시작 스크립트·데스크톱·세션 환경값을 일치시킨다. 저장 설정은 다음 생성 시 읽어 서버 재시작 없이 적용한다. 이미 존재하는 업무는 설정 안내가 끝나지 않았어도 고정 경로로 계속 사용한다.

```text
<root>/openspecboard-<profileId>/identity.json
  projects/<projectId>/works/<workspaceId>/
    identity.json
    project/          # 실제 Git worktree 또는 copy
    runtime-data/     # 테스트 DB·캐시
    artifacts/<runId>/
  projects/<projectId>/integrations/<candidateId>/
    identity.json
    project/
    runtime-data/
    artifacts/<runId>/
```

운영 업무 DB·설정·장기 보존 완료 기록은 기존 앱 데이터 위치에 둔다. 브라우저 바이너리는 기존 공통 버전별 런타임을 재사용하고 업무 데이터·컨텍스트·증거만 격리한다. 기존 공간의 경로 구조를 새 구조로 재계산하지 않는다.

### 3. 안전한 생성과 기준

- 공간 종류는 `copy | git-worktree`다. 기존 복사 업무는 그대로 유지하며 비Git/HEAD 없음은 copy임을 표시한다. Git 설치·권한·생성 오류는 원인을 표시하고 조용히 copy로 전환하지 않는다. 등록 루트와 Git 최상위가 일치하는 저장소부터 지원한다.
- 구현 시작 화면은 선택 로컬 브랜치·커밋, staged/unstaged/untracked 목록과 제외 범위를 제시한다. 현재 브랜치를 초기 후보로 제안하되 detached HEAD는 선택을 요구한다. 원본 파일·index를 수정하지 않는다.
- 기준 커밋 `baseCommit`에서 고유 `codex/work-<workId>`를 생성한다. 기존 이름·경로는 소유권을 확인하지 않고 재사용하거나 덮어쓰지 않는다. 명령 전에 생성 의도·요청 키를 영속 저장한다.
- 해당 변경의 검토된 proposal/design/specs/tasks와 `.openspec.yaml`, 보존 source-ideas만 경계 검사 후 가져온다. 다른 업무의 미커밋 문서는 가져오지 않는다. 복사 전후 HEAD·선택 브랜치 tip·문서 manifest를 비교하고 변경되면 중단·재검토한다.
- 문서만 명시적으로 stage해 `workspaceBaselineCommit`을 만든다. 업무 제품 diff는 이 기준 대비, 통합 diff는 원래 baseCommit 이후 문서 변경까지 포함한다. 문서 검토 revision과 원문 manifest를 별도 기록하여 tasks 체크 진행과 계획 내용 변경을 구분한다.
- 미커밋 제품 코드는 제외 목록을 사용자가 확인한 뒤 제외하고 진행한다. 미커밋 코드의 존재만으로 공간 생성을 일괄 차단하지 않는다. 필요한 코드가 기준 커밋에 없으면 사용자가 별도로 보존·정리한 뒤 기준을 다시 확인하며 자동 커밋·stash·전체 수입하지 않는다. `.env` 등 로컬 준비 파일은 사용자가 검토한 프로젝트별 allowlist만 독립 복사한다. 비밀값을 커밋·응답에 넣지 않고 운영 DB·로그·다른 업무 데이터를 제외한다. 의존성을 writable junction/hardlink로 공유하지 않는다.
- Git 등록·common-dir·브랜치·소유 식별·문서 revision·런타임/의존성 준비를 모두 확인해야 AI를 시작한다. 실패한 공간은 실패 기록과 잔여 파일을 표시하고 새 경로 자동 재시도나 원본 실행을 하지 않는다.

### 4. 저장 모델·실행 경로·API

| 기록 | 주요 필드 |
| --- | --- |
| 루트 설정 | profileId, rootId, path, source, confirmedAt, version, 이전 루트 목록, 용량 정책 |
| 업무 공간 | kind, workId, workspaceId, rootId, executionPath, commonDir, branch, baseCommit, workspaceBaselineCommit, sourcePlanRevision, preparationPolicyVersion, status |
| 통합 | requestId/key, workId, targetBranch, targetHead, workHead, reviewedRevision, candidateId/path/commit, state, conflicts, verificationRefs, appliedCommit |
| 검증 환경 | environmentId, workId, workspaceId/candidateId, targetKind, sourceRevision, commit, planRevision, buildId, configVersion, origin, ownedProcess, dataId, readiness |

필드 없는 과거 업무는 기존 baseline·isolated-baseline로 판별하고 경로·threadId를 유지한다. `.git` 파일 존재만으로 신뢰하지 않으며 common-dir, 실제 worktree 목록, 정규화 경로, 브랜치, 식별 파일을 대조한다.

계획 쓰기는 해당 변경 폴더만, 구현·추가 지시·수동 편집·OpenSpec 조회·명령 검증은 고정 업무 공간을 사용한다. 브라우저 검증의 원본은 고정 업무/후보 공간이며 실제 실행은 호스트 전용 사본을 사용한다. 후보 편집은 candidateId로 서버가 경로를 해석한다. Codex와 외부 CLI 모두 경로/범위 제한을 전달한다. 제한을 보장할 수 없는 계획 도구는 공유 원본에서 실행하지 않고 차단 사유를 표시한다. 같은 대화 ID와 질문 통로를 유지한다.

설정 API는 검사 토큰과 저장 버전을, `/api/work/:id` 하위 공간/통합 API는 요청 키·검토 revision을 받는다. 후보 소스/Git 접근은 등록 projectId/workId/candidateId의 관계를 검사한다. 임의 절대 실행 경로나 Git 명령을 입력으로 받지 않는다. 같은 요청 키와 다른 내용은 거부한다.

### 5. 잠금과 용량

| 작업 | 잠금 범위 |
| --- | --- |
| 계획 | 해당 변경 문서 |
| AI·파일 저장·테스트·stage·업무 커밋 | 해당 workspace의 실행/index/HEAD, 충돌하는 ref 별도 보호 |
| worktree 추가/제거·공유 ref 관리 | common-dir 관리 잠금, 짧은 구간 |
| 원본 반영·대상 브랜치 변경·보관 | 저장소별 통합/원본 잠금 |
| 브라우저 실행 | 기존 전역 실행 슬롯 1개 + 호스트 전용 검증 사본 소유, 원본 쓰기 점유 양도 없음 |

독립 A/B는 병렬 실행하고 A의 질문 대기가 B를 막지 않는다. 같은 공간의 AI 쓰기·수동 쓰기는 상호 배제한다. AI 검증 요청은 원본 쓰기 잠금을 재취득하거나 양도하지 않고 호스트 전용 사본에서 실행하여 자기 교착을 방지한다. 원본 AI 쓰기는 계속될 수 있으며 시작/종료 식별 불일치는 stale이다. 검증 사본 수정·정리와 소유 프로세스 중복 실행은 차단한다. 영속 실행 의도와 미확인 프로세스의 영향 범위를 보존한다. 잠금 순서는 통합 → 관리 → 정렬된 공간 순으로 고정하고 브라우저 슬롯 대기 중 저장소 잠금을 유지하지 않는다. 현재 브라우저 busy 요청 거부 정책을 유지하고 자동 실행 대기열을 새로 만들지 않는다.

용량은 전체·루트·업무·후보별 사용량, 드라이브 잔여와 집계 시각을 제공한다. 의존성/빌드/자료도 집계하며 링크를 따라가지 않는다. 공유 Git 객체·브라우저 바이너리는 공유분으로 분리해 이중 합산을 피한다. 확인 불가는 0이 아닌 미확인/부분 집계다. 원본·의존성 예상 크기를 별도 제시하며 최소 잔여 조건만으로 전체 준비 크기를 보장하지 않는다.

동시 업무 제한의 기본값은 3개이며 설정에서 조정할 수 있다. 준비/구현/검증 중인 활성 업무를 대상으로 하고 실행 또는 질문·승인 대기를 포함한다. 중단·비활성 공간은 실행 한도 대신 용량에 포함한다. 후보는 별도 저장소당 1개다. 설정 변경으로 한도가 줄어도 기존 실행을 종료하지 않고 다음 시작을 대기시킨다. 신규 준비 전 최소 잔여 용량 기본값은 5 GiB이며 설정에서 조정할 수 있다. 생성·복사·설치·빌드 전후 잔여를 재확인하며 미확인 또는 부족이면 새 준비를 차단한다. 검증 자료 보존 기본값은 14일이며 설정에서 조정할 수 있고, 기간 경과는 사용자 확인이 필요한 정리 제안 기준으로만 사용한다. 자동 삭제하지 않는다.

### 6. 통합 상태와 최신성

보드 단계와 별도로 `queued → preparing → conflicted/validating → ready → applying → applied`를 저장한다. 실패/취소/uncertain은 별도 기록하며 완료로 보지 않는다. 저장소당 활성 후보 1개, 사용자가 다음 업무를 선택한다.

업무 결과 staged/unstaged/untracked를 보여주고 선택 파일만 명시적 stage/커밋한다. 검증 대상 소스가 선택에서 빠져 남으면 통합을 막고 비소스 제외는 준비 정책으로 고정한다. 자동 `git add .`를 사용하지 않는다. 최신 대상 HEAD에서 임시 후보를 만들고 업무 결과를 병합한다. 원본과 업무 브랜치는 보존한다.

후보에 한해 기존 소스 편집·stage·해결 완료 동작을 제공한다. 원본/일반 업무에서 외부 merge/rebase를 발견하면 기존처럼 차단한다. 후보 충돌 해결과 소스 변경은 커밋하고 필수 검증을 다시 실행한다. 원본 대상 HEAD, workHead, 후보 commit·실제 소스 revision, planRevision, 검증 명령/시나리오/설정 버전을 묶어 근거를 저장한다. 실행 전후 파일을 재검사해 외부 편집도 탐지한다.

사용자 확정 시 대상 브랜치·HEAD·index·작업 트리·merge/rebase 상태와 후보 버전을 다시 검사한다. dirty 원본은 파일이 겹치지 않아도 차단한다. 대상이 다른 worktree에 체크아웃됐거나 원본이 지정 브랜치가 아니면 자동 전환하지 않는다. 최신성 불일치 시 후보 재생성·재검증을 요구한다. ff-only로 검증 후보를 반영하고 실제 HEAD 확인 뒤 applied를 저장한다. 반영 도중 오류는 자동 역조작 없이 실제 상태 조회로 복구한다. 앱 잠금 밖 외부 Git/파일 도구까지 완전히 잠글 수 없으므로 사전/사후 상태를 확인하고 불명확하면 차단한다.

종료가 증명된 과거 반영을 명시 재확인할 때는 원본의 브랜치·HEAD·index·파일이 저장된 후보와 정확히 일치하는지를 확인한다. 응답 유실 뒤 업무/후보 파일에 새 편집이 생겼다는 이유로 그 파일을 예전 내용으로 복원해야만 점유가 해제되는 상태를 만들지 않는다. 현재 업무/후보 상태를 새 관측 기준으로 고정해 관측 중 변경은 거부하고, 과거 입력과의 차이는 `sideChanged`로 별도 보존한다. 현재 후보 소유·HEAD·attempt/epoch·종료 근거와 intent CAS를 통과한 해당 의도만 종결한다. 이는 과거 적용 사실의 확인이며 새 파일의 검증 통과·추가 원본 반영·업무 완료를 의미하지 않는다. 새 반영의 사전 검사와 통상 반영 직후의 엄격한 보존 검사는 그대로 유지한다.

### 7. 기존 브라우저 검증과 연결

runner·정책·네트워크·프로세스 가드·런타임을 재사용하고 FileResults 직접 의존 부분을 공통 공간 resolver로 교체한다. 기존 시나리오 JSON과 고정 URL은 계속 지원한다. 고정 포트 충돌은 차단하며 자동 재배정으로 시나리오를 바꾸지 않는다. 필요하면 사용자가 검토한 테스트 설정의 포트만 변경한다. 13001~13003은 금지한다.

단일 `origin`을 환경에 저장한다. 프런트/API가 필요하면 신뢰된 테스트 서버 프록시를 사용하고 다른 localhost 포트·외부 API를 자동 허용하지 않는다. 등록 cwd는 선택 공간에서 검증한 하위 상대 경로이며 실제 실행 때 같은 상대 경로를 검증 사본 안에서 해석한다. 새 서버와 실행별 DATA_DIR/CONFIG_PATH를 사용하고 기존 서버·개인 인증·DESKTOP_TOKEN을 전달하지 않는다. 생성 환경·소스 revision과 테스트 빌드의 buildId를 연결하는 준비 검사를 추가한다. health 200만으로 최신 빌드를 증명하지 않으며 프로젝트의 테스트 명령이 빌드 출처 확인을 지원하지 않으면 준비 불가로 표시한다.

기존 `passed/failed/blocked/interrupted/stale`, 단계별 검사, 최소 하나의 expect, 소유 프로세스 종료, 자동 입력 재실행 금지를 유지한다. 결과에 대상 종류와 environmentId·후보 ID·commit·소스/계획/빌드/시나리오/설정 버전을 추가한다. 업무 통과를 후보 통과로 복사하지 않는다. 필수 여부는 사전에 검토한 계획을 따르고 실패 후 조용히 선택 검증으로 낮추지 않는다.

새 대화의 `browser_verification`과 기존 대화 CLI의 run/status/cancel만 유지한다. 임의 target/path를 AI 요청에 추가하지 않고 서버가 해당 업무의 현재 승인된 실행 컨텍스트에 묶는다. 후보로 전환하면 이전 처리 중 요청은 재사용하지 않고 uncertain/interrupted를 표시한다. 기존 `.tools/browser-verification/cli.cjs` 명령과 업무 아래 imagePath 호환을 유지하되 서버가 관리하는 자료 경로에 영속 증거를 기록하고 통로 파일은 정리 가능한 복제본으로 취급한다. 다른 업무/후보 결과를 읽거나 시나리오를 바꾸지 못하게 한다.

CLI는 신뢰하지 않는 요청 통로이며 서버가 요청을 발견한 업무만 대상으로 한다. 검증 실행기·런타임은 호스트가 선택하고 임의 경로/명령을 요청으로 받지 않는다. 호스트가 AI writableRoots와 겹치지 않는 전용 사본을 만들고 독립 파일만 복사한다. 링크·공유 파일·중첩 경계 또는 복사 중 변경은 차단한다. 원본 쓰기 중지를 주장하지 않으며 CLI 변조로 원본에서 검증하거나 중지 판정을 얻을 수 없다. 같은 대화 ID·질문 통로·소유 업무의 status/cancel은 보존하며 확인 실패를 이유로 AI turn 중단 방식이나 새 대화로 자동 전환하지 않는다. CLI 호환은 확인된 실행 컨텍스트에서 제공하고 수정 가능한 통로 파일 자체를 신뢰 경계로 삼지 않는다.

### 8. 복구·정리·화면

생성·병합·반영·제거 전에 의도를 영속 기록하고 재시작 후 DB, Git 등록, 실제 경로·HEAD·프로세스를 대조한다. threadId를 보존하며 공간 유실·분리 드라이브·소유 불일치 시 recovery-required로 차단한다. 새 루트나 원본으로 자동 대체하지 않는다. 취소는 실행을 멈추고 결과를 보존하며 applied 이후 취소를 자동 역병합으로 처리하지 않는다.

정리는 소유가 확인된 개별 공간의 상세 내역과 보존 기록을 먼저 표시하고 사용자 확인을 요구한다. 실행·브라우저·서버·질문·승인 대기·종료 불명확 상태를 차단한다. 미커밋·미반영 커밋·확인되지 않은 ignored 파일도 일반 정리를 막는다. 검토된 disposable 의존성/빌드/테스트 데이터만 제거 대상에 포함한다. Git 정상 worktree 제거 후 확인된 컨테이너만 정리하며 루트 재귀 삭제·강제 remove·일괄 prune를 하지 않는다. branch 제거는 별도 확인 범위에 명시하고 원격 ref를 변경하지 않는다.

완료 diff·요약 검증 결과·통합 커밋은 앱 데이터에 먼저 보존한다. 만료한 캡처는 사용자 확인 후 삭제하고 증거 만료를 표시한다. 보관은 원본에서 직렬 실행하고 명세 변경을 확인한다. 보관이 만든 미커밋 상태는 다음 통합 확정을 차단하며 통합 성공과 보관 실패를 구분한다.

설정 화면은 경로/용량/이전 루트/정리, 업무 상단은 종류/기준/실행 경로/복구, 검증 영역은 업무/후보 결과를 구분한다. 통합 패널은 대기·충돌·검증·반영 가능·완료·복구를 표시하고 소스 선택에 후보를 추가한다. 겹치는 변경 파일은 경고하되 병합 성공 판정으로 쓰지 않는다.

## Risks / Trade-offs

- 미커밋 코드가 많은 현재 저장소에서 워크트리가 실행에 필요한 최신 코드를 누락할 위험 → 제외 목록과 기준을 먼저 검토하고 사용자가 별도로 보존·정리한다. 이 업무가 자동 커밋하지 않는다.
- 공유 Git 메타데이터 훼손·외부 변경 경합 → 짧은 관리 잠금, 요청별 의도 기록, 상태 버전 비교와 실제 상태 복구.
- 경로 검사 이후 링크 교체·외장 드라이브 유실 → 생성/정리 직전 실경로·소유권 재검사, 실패 시 대체 실행 금지.
- 용량 집계 비용·불완전 추정 → 제한된 비동기 집계와 시각/부분 상태, 작업 전후 잔여 재확인.
- 오래된 빌드·다른 서버에서 잘못된 브라우저 통과 → 새 소유 서버, 단일 origin, buildId/환경 출처 검사, 후보별 재검증.
- 세션 코드와 운영 중 서버 버전 차이 → 코드 검증과 실제 배포 확인을 따로 기록하고 안전한 반영 전까지 가용 기능으로 선언하지 않는다.

## Migration Plan

초기 설정/경로 저장 → 공통 공간 모델과 복사 호환 → 생성/복구 → 실행 경로와 잠금 → 통합 후보 → 브라우저 연결 → 화면/정리 → 결합 검증 순으로 구현한다. 각 단계는 tasks.md의 선행 검증이 통과한 뒤 진행한다.

초기 구현 6/54개 완료 기록은 보존하고 1.6 실제 폴더 선택과 9.5 화면 검증의 미완료 상태를 유지한다. 사용자가 ‘검증 환경 준비 후 계속’을 선택했으므로 선행 검증을 보류한 채 그룹 2로 넘어가지 않는다. 최신 문서의 사용자 검토 완료와 별도 구현 재개 지시 후 검증 환경을 준비·확인하고 1.6을 포함한 그룹 1 검증을 통과한 다음 후속 구현을 진행한다. 기존 ACL 오류·내장 브라우저 미연결 기록은 유지하며 이번 계획 수정에서 재검증하거나 작업 경로 변경만으로 해소됐다고 판단하지 않는다. ACL 변경·샌드박스 해제·Edge 확장 검증으로 우회하지 않는다.

개발 검증은 프로젝트 전용 scripts/npm.ps1의 backend/frontend test:run 및 build를 사용한다. 실제 임시 Git 저장소에서 A/B 병렬 실행, A 반영 후 B 충돌·재검증, dirty 원본, 대상 변경, 생성/반영 중 장애, 중복 요청, 기존 복사 업무 완료/보관을 확인한다. 경로 변경 중 A 유지/B 신규 위치, 한글·공백·타 드라이브, 경계 우회, 용량 소진, 확인 후 정리와 삭제 후 완료 기록도 확인한다.

### 2026-10-29 검증 사본 실행 계약

호스트는 environmentId와 workId/threadId/turnId, sourceMutationVersion, 시나리오 digest, 원본 경로·소스 digest를 고정한다. 서버 데이터 영역 아래 무작위 독점 생성 컨테이너를 사용하고 원본/다른 실행 공간과 양방향 겹침을 거부한다. .git·운영 데이터·로그·개인 설정·인증 파일·수정 가능한 CLI 통로는 복사하지 않는다. 필요한 소스·독립 의존성·산출물은 독립 파일로 복사하고 링크/공유 하드링크는 거부한다. 복사 전후 원본과 복사본의 바이트·모드를 대조하며 불일치하면 실행기를 시작하지 않는다. 새 테스트 서버의 cwd는 사본으로 고정한다. 실행 후 원본 소스/계획·시나리오·세대 또는 사본 소스가 바뀌면 stale로 남긴다. 런타임 데이터·임시 파일은 사본 밖의 새 검증 전용 DATA_DIR로 격리한다. 종료가 확인된 사본만 고정 소유 컨테이너에서 정리하고 실패하면 보존·차단한다. 이는 악성 프로젝트 코드에 대한 OS 보안 샌드박스 보장이 아니며 파일 시스템 외부 접근 제한은 별도 실행 정책이다. 빌드 출처/후보 식별 확장은 그룹 7에서 연결한다.

### 구현 중 확인한 Windows Git 경로 하드가드

설치 Git 2.54.0.windows.1은 checkout 자식에 전달한 명시적 GIT_DIR 경로의 자체 길이 하드가드가 있으며 core.longpaths로 해제되지 않는다. 파일시스템 쓰기 검사 통과를 Git 경로 지원으로 간주하지 않는다. 신규 Git 공간의 예정 executionPath를 산출한 뒤 DB에 업무 경로·생성 의도를 저장하기 전에 해당 Git 실행 파일의 읽기 전용 `--git-dir=<예정경로>/.git rev-parse --git-dir` 검사로 확인된 하드가드 오류를 구분한다. 이는 전체 Git 기능 확인이 아니며 미생성 저장소의 존재 오류를 성공으로 표현하지 않는다. 숫자 길이 상수를 고정하거나 원본 저장소·전역 환경·ACL을 바꾸지 않는다. 미지원이면 경로를 고정하지 않아 사용자가 더 짧은 루트를 선택한 후 같은 업무로 다시 요청할 수 있다. 이미 생성된 공간의 경로와 복구 경계는 유지한다. 새 통합 후보 예약에도 같은 검사를 적용한다.
