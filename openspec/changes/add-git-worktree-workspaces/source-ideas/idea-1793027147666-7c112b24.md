# OpenSpecBoard 업무별 Git 워크트리 도입 계획

작성일: 2026-10-26
상태: 검토용 설계·단계별 도입 초안. 제품 코드 구현과 기존 업무 전환은 수행하지 않았다.

관련 작업: [브라우저 검증 권한 문제 해결](codex://threads/01a17865-215e-7541-968d-bd96e8d99b44). 2026-10-26 조회 시 전용 백그라운드 브라우저의 타당성·위험 검토까지 확인했으며, 구현 완료나 실제 검증 성공으로 간주하지 않는다. 이후 변경된 결정은 연동 착수 전에 다시 확인한다.

## 1. 목표와 현재 구조

목표는 여러 OpenSpec 업무를 동시에 구현하더라도 수정 내용이 섞이지 않고, 검토한 결과만 순서대로 프로젝트에 통합하는 것이다.

현재 구조에는 이미 격리가 있다.

- `backend/src/work/file-results.ts`: 구현 시작 시 프로젝트를 별도 폴더에 복사하고 시작 스냅샷을 저장한다. 원본 반영은 파일 해시로 충돌을 검사한다.
- `backend/src/work/work.service.ts`: 계획 → 사용자 검토 → 구현 → 검증 → 원본 반영 → 완료 → 보관 순서를 관리한다.
- `backend/src/projects/resolver.ts`: 원본과 업무 공간을 구분하며 linked worktree의 Git 공통 디렉터리도 인식한다.
- `backend/src/projects/coordinator.ts`: 원본 경로와 Git 공통 디렉터리에 걸친 잠금·미확인 작업 검사를 한다. 그대로 사용하면 독립 워크트리도 과도하게 서로 막을 수 있다.
- `backend/src/work/recovery.ts`: 업무 공간과 기존 대화를 확인하여 복구하며, 공간이 없을 때 원본에서 자동 실행하지 않는다.
- `backend/src/codex/codex.service.ts`, `backend/src/ai-tools/external-cli.adapter.ts`: 계획은 원본, 구현·검증은 업무 경로에서 실행한다.

따라서 폴더 복사를 Git 워크트리로 바꾸는 것과 함께 실행 경로, 잠금 범위, 통합 방식, 검증 근거를 연결해야 한다. 워크트리는 병합 충돌이나 기능 간 충돌을 자동으로 없애지 않는다.

## 2. 접근 방식 비교와 추천

| 방식 | 장점 | 한계 |
| --- | --- | --- |
| 기존 복사 격리 강화 | 변경 범위가 작고 비Git 프로젝트 지원이 쉽다 | 커밋·병합 이력이 없으며 충돌 해결을 직접 만들어야 한다 |
| 새 Git 업무부터 워크트리 적용 — 추천 | 기존 업무를 보존하면서 Git diff·커밋·병합을 활용한다 | 복사 방식과 워크트리 방식의 공존이 필요하다 |
| 모든 업무를 즉시 워크트리로 전환 | 구조를 한 번에 통일한다 | 진행 중 변경·세션·검증 기준을 옮기는 위험이 크다 |

Git 프로젝트의 새 구현 업무는 워크트리를 기본으로 사용한다. 기존 복사 업무는 완료할 때까지 기존 방식을 유지한다. 비Git·커밋 없는 저장소는 복사 방식임을 명확히 표시하며 자동 저장소 생성이나 초기 커밋을 하지 않는다. Git 프로젝트에서 워크트리 생성에 실패하면 실패 원인을 표시하며 복사 방식으로 조용히 전환하지 않는다.

## 3. OpenSpecBoard 사용자 흐름

기존 보드 단계는 유지하고 업무 공간과 통합 상태를 별도 속성으로 추가한다.

1. **계획·사용자 검토**: 기존 흐름을 유지한다. 계획 AI의 쓰기 범위는 해당 변경 문서 폴더로 제한한다. 다른 업무의 문서나 제품 코드를 수정할 수 없게 한다.
2. **구현 시작**: 기준 브랜치·커밋과 원본의 미커밋 변경 목록을 보여준다. 업무 워크트리를 준비하고 기존 대화의 실행 경로를 전환한다.
3. **구현·검증**: 추가 지시, 파일 편집, 테스트 모두 같은 업무 공간을 사용한다.
   브라우저 검증이 필요한 업무는 준비된 해당 공간의 테스트 서버에 연결한다. 원본의 기존 개발 서버를 대신 열어 검증하지 않는다.
4. **통합 요청**: 최신 계획 검토와 업무 검증 통과 후 사용자가 통합 대기열에 등록한다. 자동 반영하지 않는다.
5. **통합 미리보기**: 최신 대상 커밋과 업무 결과로 임시 통합 공간을 만들고 충돌과 통합 diff를 보여준다.
6. **통합 검증·반영**: 후보의 필수 검증이 통과하면 사용자가 확정한다. 대상 상태가 그대로인지 다시 검사하고 fast-forward로 반영한다.
7. **완료·보관**: 통합 근거와 사용자 완료 확인을 저장한다. OpenSpec 기준 명세 반영·보관은 기존 별도 동작을 유지한다.

검증 단계에 통합 패널을 추가한다. 업무 상태를 전부 새로 만들지 않고 `integration.status`를 따로 관리한다.

## 4. 업무 공간 생성과 기준 정책

- 공간 식별 단위는 `work.id`이며 OpenSpec 변경 하나에 연결한다. 재개·추가 지시는 같은 공간을 재사용한다.
- 새 공간의 저장 위치는 14절의 작업 전용 공간 설정으로 결정하고, 생성 당시 루트 ID·절대 경로를 업무에 고정 저장한다. 전역 설정 변경으로 기존 공간 경로를 다시 계산하지 않는다.
- 등록 저장소 루트와 Git 루트가 일치하는 프로젝트부터 지원한다. 중첩 저장소·submodule 작업은 지원 범위를 안내하고 자동 처리하지 않는다.
- 업무 브랜치는 `codex/work-<workId>`처럼 고유하게 생성한다. 같은 이름이 이미 있으면 소유 정보를 확인하며 타인의 브랜치를 재사용하거나 덮어쓰지 않는다.
- 기본 기준은 구현 시작 시 사용자가 선택한 로컬 브랜치의 커밋이다. 최초 값은 원본이 체크아웃한 브랜치이며 이후 업무에 저장한다. 원본이 detached HEAD이면 대상 브랜치 선택이 필요하다.
- 원본의 미커밋 제품 코드는 자동 복사하지 않는다. 변경 목록을 보여주고 제외된 기준으로 진행하거나 먼저 원본을 정리하도록 한다.
- 예외로 해당 업무의 검토된 `openspec/changes/<changeName>/` 문서와 보존 아이디어를 가져온다. 다른 업무의 미커밋 문서는 가져오지 않는다.
- 준비 전후 원본 HEAD·선택 문서 버전을 비교한다. 문서가 바뀌었으면 실행하지 않고 재검토를 요구한다.
- 가져온 업무 문서는 구현 기준 커밋으로 기록한다. 제품 변경 비교 기준은 이 커밋이며, 최종 통합 비교에는 원래 기준 커밋 이후 문서 변경도 포함한다.
- `.env`, 전용 Node 런타임 등 필요한 로컬 파일은 명시된 준비 정책만 복사한다. 운영 DB·로그·다른 업무 데이터는 제외한다. 의존성 폴더를 수정 가능한 junction이나 hardlink로 공유하지 않는다.
- 준비 완료 조건은 Git 등록, 업무 소유 식별, 문서 버전, 런타임·의존성 준비 결과의 확인이다. 실패 시 AI를 시작하지 않는다.

초기 버전에서 dirty 원본 전체 가져오기는 지원하지 않는다. 현재처럼 많은 미커밋 코드가 있는 개발 환경은 먼저 기준을 보존·정리한 뒤 전환한다.

## 5. 책임 분리와 저장 정보

| 구성 요소 | 책임 | 주요 연결 파일 |
| --- | --- | --- |
| `work/workspace.service.ts` — 신규 | 복사·워크트리 경로 선택, 생성·재사용·식별 확인 | `store.ts`, `file-results.ts`, `recovery.ts` |
| `work/worktree-manager.ts` — 신규 | 제한된 Git worktree 생성·조회·정리, 경로·저장소 소유 확인 | `projects/git-runner.ts`, `projects/git-metadata.ts` |
| `work/integration.service.ts` — 신규 | 통합 요청·후보·검증·확정·복구 | `work.service.ts`, `execution.service.ts` |
| `projects/coordinator.ts` — 변경 | 업무 공간 잠금과 저장소 관리·통합 잠금 구분 | Git API, AI 시작, 검증, 편집 |
| `work/file-results.ts` — 변경 | 변경 결과·완료 스냅샷 공통 제공, 기존 복사 반영 유지 | 업무 공간 서비스 |
| 기존 AI 어댑터 — 변경 | 계획·구현·검증 경로와 쓰기 범위 통일 | Codex 및 외부 CLI |

업무 공간 정보는 `kind(copy/git-worktree)`, `workId`, `executionPath`, `repositoryCommonDir`, `branch`, `baseCommit`, `workspaceBaselineCommit`, `sourcePlanRevision`, `status`를 저장한다. 필드 없는 기존 업무는 기존 기록으로 판별한다.

통합 정보는 요청 ID·요청 키, 대상 브랜치, `targetHead`, `workHead`, 검토 당시 파일 버전, 후보 경로·커밋, 상태, 충돌 파일, 검증 근거, 반영 커밋을 저장한다. 요청 키가 같고 내용이 다르면 거부한다. 재시도는 기존 작업을 조회하며 Git 명령을 무조건 반복하지 않는다.

`.git` 파일이 있는지만으로 공간을 신뢰하지 않는다. 정규화 경로, Git 공통 디렉터리, 실제 worktree 등록, 브랜치, 업무 식별 기록을 함께 확인한다.

## 6. 동시 실행과 잠금

잠금은 기존 공통 디렉터리 검사를 제거하는 방식으로 완화하지 않는다. 작업 종류에 따라 필요한 범위만 취득한다.

| 동작 | 잠금·제약 |
| --- | --- |
| 업무 A/B의 AI·테스트 | 서로 다른 공간에서 병렬 허용. 같은 업무의 AI·수동 편집·검증은 상호 배제 |
| 계획 문서 작성 | 해당 변경 문서 범위만 쓰기 허용. 같은 변경은 한 작업만 수정 |
| stage·업무 커밋 | 해당 공간의 index·HEAD와 업무 실행 상태를 잠금. 공유 ref 충돌은 별도 검사 |
| worktree 생성·제거, 브랜치·공유 ref 변경 | Git 공통 디렉터리 기준 짧은 관리 잠금 |
| 원본 통합·보관·대상 브랜치 변경 | 같은 저장소의 통합·원본 변경을 직렬화 |
| 종료 불명확 Git 명령 | 영향받는 공간 또는 공유 자원에 복구 차단을 유지 |

상주 세션 서버가 실행 소유권을 관리한다. 메모리 검사만으로 완료 처리하지 않고 작업 기록과 실제 Git 상태로 복구한다. 외부 도구의 파일·HEAD 변경도 버전 재검사로 탐지한다.

다른 업무가 질문·승인 대기 중이라는 이유만으로 독립 워크트리의 편집이나 테스트를 막지 않는다. 다만 공유 자원을 변경하는 작업은 계속 보호한다.

## 7. 통합 방식과 검증 최신성

- 기존 복사 업무의 `apply-changes`는 기존 방식으로 유지한다. 워크트리 업무는 기존 파일 복사 반영을 호출하지 않는다.
- 통합 요청 시 업무의 staged·unstaged·untracked 파일을 모두 미리 보여주고, 사용자 선택 범위로 결과 커밋을 만든다. 자동 `git add .`를 사용하지 않는다. 커밋 메시지는 한국어로 작성한다.
- 선택에서 제외된 소스 변경이 남으면 통합을 진행하지 않는다. 검증한 결과와 커밋 내용이 같아야 한다. 비소스 로컬 파일 제외는 준비 정책으로 명시한다.
- 통합 대기열은 저장소당 하나만 진행한다. 사용자가 다음 항목을 선택하며 FIFO 자동 병합은 하지 않는다.
- 임시 통합 워크트리에서 최신 대상 커밋을 기준으로 업무 브랜치를 병합한다. 원본과 업무 브랜치는 그대로 보존한다.
- 충돌은 후보 공간에서 해결한다. 초기 버전은 기존 소스 편집·Git 상태 화면을 활용하며 전용 3방향 병합 편집기는 만들지 않는다. 후보 전용 접근 ID로 경로를 해석한다.
- 충돌 해결 또는 후보 소스 변경 시 해당 검증 결과를 무효화하고 후보를 새로 커밋·검증한다.
- 통합 검증 근거는 후보 커밋과 실제 파일 버전, 검증 명령 버전에 묶는다. 업무 단독 검증과 구분한다.
- 필수 브라우저 검증이 있는 업무는 후보용 서버와 격리 데이터로 다시 검증한다. 업무 공간에서 통과한 브라우저 결과를 후보 결과로 복사하지 않는다. 브라우저 연결 대기·차단·미실행은 통과로 처리하지 않는다.
- 최종 반영 시 대상 브랜치·HEAD·index·파일 상태를 검사한다. 원본에 미커밋 변경이 있거나 다른 merge/rebase가 진행 중이면 반영하지 않는다. 자동 stash·reset·강제 덮어쓰기를 하지 않는다.
- 대상이 바뀌었다면 후보를 다시 만들고 재검증한다. 검사와 실제 반영 사이 변경도 실패로 처리하며 현재 상태를 다시 확인한다.
- 원본 대상 브랜치에 검증한 후보 커밋을 fast-forward로 반영하고 실제 HEAD를 확인한다. 다른 경로에 체크아웃한 대상 브랜치는 자동 이동·우회하지 않는다.
- 반영 성공 후 완료 증거를 저장한다. 이후 원본에서 다른 업무가 통합되어도 과거 완료 근거는 유지한다.

OpenSpec 보관은 대상 원본에서 직렬 실행하며 결과와 기준 명세 변경을 확인한다. 보관이 만든 미커밋 변경은 별도로 표시하고 사용자가 정리하기 전 다음 통합 확정을 막는다. 보관 실패를 통합 실패와 혼동하지 않는다.

## 8. 화면과 API

기존 `업무·AI·검증`, `소스·Git`, `프로젝트 원본 / 업무 공간` 동선을 유지한다.

- 업무 상단: `Git 업무 공간`, 기준 브랜치·커밋, 준비·실행·복구 상태.
- 변경 결과: 기존 원본 반영 버튼을 공간 종류에 따라 유지하거나 `통합 요청`으로 제공.
- 검증 영역: 업무 테스트와 통합 후보 테스트를 구분.
- 통합 패널: `대기 / 후보 준비 / 충돌 해결 / 검증 / 반영 가능 / 반영 완료 / 복구 필요` 표시.
- 프로젝트 화면: 업무별 변경 파일이 겹치면 관련 업무와 파일명을 경고. 경고는 병합 가능 판정으로 사용하지 않는다.
- 소스 화면: 기존 원본·업무 공간에 `통합 후보` 선택을 추가하고 후보 식별자로만 접근.
- 완료 업무: 공간을 정리한 뒤에도 저장된 diff·검증·통합 커밋 조회 유지.

API는 기존 `/api/work/:id` 하위에 workspace 조회·준비, integration 요청·조회·후보 생성·검증·확정·실제 상태 확인을 추가한다. 변경 요청은 요청 키와 검토 버전 토큰을 사용한다. 임의 절대 경로나 Git 명령을 클라이언트에서 받지 않는다.

## 9. 복구·정리·서버 운영

- 생성 명령 직전 의도를 기록하고, 재시작 뒤 DB·worktree 목록·실제 디렉터리를 대조한다. 준비 기록이 없다고 기존 경로를 재사용하지 않는다.
- 기존 `threadId`를 유지하고 확인된 공간에서만 재개한다. 공간을 잃으면 원본으로 자동 대체하지 않는다.
- 기존 복사 업무는 실행 중 자동 변환하지 않는다. 명시적 이전 기능은 후속 범위로 둔다.
- 통합 중 연결이 끊기면 반영 커밋과 대상 실제 HEAD를 조회한다. 성공 여부가 불확실하면 미확인 상태를 유지하고 새 반영을 막는다.
- 사용자 취소는 대기열·후보 실행을 멈추되 구현 공간과 작업 결과를 보존한다. 반영 이후 취소는 자동 역병합으로 처리하지 않는다.
- 최초 버전은 공간 수동 정리만 제공한다. 완료·보관, 미반영 커밋·미커밋·무시 파일, 실행 프로세스, 소유 정보를 검사하고 보존 대상을 안내한다. 확인 없는 강제 삭제·prune를 하지 않는다.
- Node/npm은 프로젝트 전용 런타임을 사용한다. 업무별 테스트 데이터·캐시·환경을 분리하며 공유 DB를 사용하지 않는다.
- 범용 개발 서버 자동 실행과 포트 할당 UI는 후속 범위다. 다만 백그라운드 브라우저 연동에 필요한 테스트 환경의 준비·식별·종료는 최초 연동 범위에 포함한다. 고정된 실행 파일·인자 배열을 갖춘 프로젝트별 검증 설정을 사용하고, 업무·후보별 포트와 데이터 경로를 분리한다. 서버가 자동화 준비를 지원하지 않으면 수동 준비 후 동일한 식별 검사를 거치며 임의 실행을 추정하지 않는다.
- 13003 세션 서버는 공통으로 유지한다. 코드 반영을 위한 세션 서버 재시작은 모든 실행·질문·승인 대기가 끝난 뒤 명시적으로 수행한다.

## 10. 구현 순서와 단계별 완료 조건

각 단계는 앞 단계가 통과한 뒤 진행한다. 이 도입 작업 자체도 공유 파일이 많으므로 여러 채팅에서 동시에 구현하지 않는다.

- [ ] **착수 전 — OpenSpec 변경·상세 실행 계획 확정**: 설계 확정 후 별도 OpenSpec 변경 `add-git-worktree-workspaces`에 proposal/design/specs/tasks를 작성한다. 개발 실행·세션·소스Git 관련 기존 명세와 모순을 정리하고, 아래 단계를 파일별 구현·테스트 작업으로 구체화한다.
- [ ] **연동 착수 전 — 브라우저 작업과 경계 확정**: 관련 채팅의 최신 설계·구현 상태를 다시 읽고 아래 13절의 환경·검증 결과 계약을 맞춘다. 전용 브라우저 허용 정책이 확정되기 전에는 이 계획만으로 실행 예외가 승인됐다고 간주하지 않는다.
- [ ] **1단계 — 공간 모델·기존 동작 보존**: `store.ts`, `file-results.ts`, `recovery.ts`에 공통 공간 추상화를 연결한다. `work-files.test.ts`, 기존 복구·실행 테스트로 복사 업무의 반영·완료·복구가 유지됨을 확인한다.
- [ ] **1단계 확장 — 작업 전용 공간 설정**: 14절의 설정 저장·검증·루트 등록과 UI를 구현한다. 신규 설정 서비스 `backend/src/work/workspace-settings.service.ts`, 설정 API용 `backend/src/work/workspace-settings.controller.ts`, UI용 `frontend/src/components/WorkspaceSettings.tsx`를 추가하고 `app.ts`, 기존 설정 화면, 업무 공간 서비스에 연결한다. 기존 `WORKSPACE_ROOT`의 적용 우선순위와 시작 환경 전달도 확인한다. 신규 공간 생성은 검증된 설정을 요구하며 기존 업무는 저장된 경로로 계속 동작해야 한다.
- [ ] **2단계 — Git 공간 생성·재사용**: 신규 workspace 서비스와 manager를 구현한다. 실제 임시 저장소 테스트로 기준 커밋, 해당 업무 문서만 가져오기, dirty 제품 코드 제외, 재시도·오인식·생성 실패 복구를 검증한다.

- [ ] **4단계 — 잠금 분리**: `projects/coordinator.ts`와 Git 호출부를 작업 종류별로 조정한다. A/B 동시 AI·검증 허용, 같은 업무 편집 차단, 공유 관리 작업 직렬화, 미확인 프로세스 차단을 테스트한다.
- [ ] **브라우저 연동 기반 — 테스트 환경 공급**: 2~4단계 이후 업무·후보 공간의 환경 ID, 코드 버전, 서버·빌드 출처, 격리 데이터, 실제 포트, 준비 상태를 제공하는 환경 관리 모듈을 추가한다. 실행 중 공간 변경 차단과 결과 최신성 검사를 구현한다. 브라우저 미구현 상태에서는 계약 테스트만 수행하고 실제 브라우저 검증으로 표시하지 않는다.
- [ ] **5단계 — 통합 후보·검증·확정**: 신규 integration 서비스를 추가한다. 깨끗한 병합, 동일 파일 충돌, 대상 변경, dirty 원본, 중복 요청, 반영 중 재시작과 통합 검증 실패를 실제 Git 저장소로 테스트한다. 이 단계 전에는 신규 워크트리 업무를 일반 사용자 기본값으로 활성화하지 않는다.
- [ ] **6단계 — UI와 기존 소스·Git 연결**: `WorkRoom.tsx`, `ChangeResults.tsx`, `ProjectWorkspace.tsx`, 관련 타입·API·번역을 수정한다. 후보 ID에 대한 서버 접근 검사를 추가한다. 버튼 활성 조건과 복구·충돌·오래된 검증 상태를 UI 테스트한다. 브라우저 작업과 같은 파일을 동시에 편집하지 않고 순차 반영한다.
- [ ] **7단계 — 완료·보관·수동 정리**: 완료 스냅샷과 통합 근거를 연결한다. 보관 후 미커밋 상태, 공간 삭제 후 결과 조회, 기존 복사 업무와 신규 업무 공존을 검증한다. `docs/PROJECT-WORKSPACE.md`, `docs/USAGE.md`, `docs/API.md`를 갱신한다.
- [ ] **8단계 — 명세 대조·실제 사용자 흐름 확인**: OpenSpec 명세와 구현 결과를 대조한다. 신규 기본값 활성화 전에 전체 통합 시나리오를 확인한다. 브라우저 연동 출시는 관련 작업의 정책 확정·실제 실행 검증·배포 확인 후 13절의 결합 시나리오까지 통과해야 한다.

후속 구현용 상세 실행 계획은 이 설계를 확정한 뒤 별도 작성한다. 제품 코드 구현, 자동 병합, 기존 업무 일괄 이전은 현재 요청 범위에 포함하지 않는다.

## 11. 검증 계획과 출시 기준

구현 시 명령은 저장소 전용 런타임을 사용한다.

```powershell
./scripts/npm.ps1 run test:run --workspace backend
./scripts/npm.ps1 run test:run --workspace frontend
./scripts/npm.ps1 run build --workspace backend
./scripts/npm.ps1 run build --workspace frontend
```

위 명령은 향후 구현 검증 계획이며 이번 문서 작성에서 실행·통과했다고 보고하지 않는다.

필수 사용자 시나리오:

1. 같은 프로젝트에서 업무 A/B를 동시에 구현해도 각 변경 결과에는 자기 업무 수정만 나타난다.
2. A 통합 뒤 B와 파일이 겹치면 B의 후보에서 충돌을 해결하고 최신 대상 기준 테스트를 다시 실행한다.
3. 원본에 미커밋 코드가 있어도 이를 업무에 몰래 가져오지 않으며, 최종 통합 확정은 차단한다.
4. 대기 중인 질문·승인과 threadId를 유지한 채 연결 복구가 가능하다.
5. 준비·병합·반영 중 장애 후 실제 상태 확인으로 복구하며 중복 반영하지 않는다.
6. 기존 복사 업무의 검토·검증·원본 반영·완료·보관이 유지된다.
7. 보관과 공간 정리를 마친 뒤에도 완료 당시 diff·검증·통합 커밋을 조회한다.

현재 이 채팅에서 실제 브라우저 검증을 수행할 때는 기존 사용자 지침에 따라 Codex 내장 브라우저만 사용한다. OpenSpecBoard 내부 검증은 관련 채팅에서 검토 중인 전용 백그라운드 브라우저에 연동하도록 설계한다. 전용 브라우저의 정책 예외와 구현이 확정되기 전에는 Codex 내장 브라우저에 프로그램이 접근할 수 있다고 가정하거나 전용 브라우저를 실행하지 않는다. 접근 불가·미연결은 미수행 또는 차단으로 표시한다. PC 제어, 개인 Edge 프로필, 별도 브라우저 MCP로 자동 대체하지 않는다.

## 12. 설계 자체 점검

- 공간 생성만 도입하고 통합 경로가 없는 상태를 기본값으로 배포하지 않는다.
- 현재 복사 격리가 존재한다는 전제로 변경 범위를 정했다.
- 보드 단계와 업무 공간·통합 상태를 분리했다.
- 기준 문서 커밋과 제품 변경 비교 기준을 구분했다.
- 업무 검증과 통합 후보 검증을 별도 근거로 정의했다.
- 공유 Git 메타데이터 보호와 독립 업무 병렬 실행을 함께 다뤘다.
- dirty 원본, 기존 업무, 비Git 프로젝트, 보관 후 변경, 재시작 복구 정책을 명시했다.
- 자동 병합·일괄 이전·자동 포트 관리·전용 병합 편집기는 후속 범위로 분리했다.
- 브라우저 검증용 환경의 포트 배정·준비·종료는 범용 포트 관리 UI와 구분하여 연동 필수 범위로 포함했다.
- 브라우저 관련 별도 작업의 현재 검토 상태와 미확정 정책을 명시하고, 코드·서버 일치와 데이터 격리를 연결 조건으로 삼았다.
- 작업 전용 공간 설정과 위치 변경을 신규 공간 생성 정책에 연결하고, 원본·운영 DB·기존 업무 경로를 보호하도록 정의했다.

## 13. 브라우저 검증 권한 작업과의 연동

### 13.1 확인한 방향과 적용 조건

관련 채팅에서 검토한 방향은 OpenSpecBoard 내부 라이브러리와 전용 Chromium을 이용한 백그라운드 검증이다. PC 마우스·키보드나 창 포커스를 점유하지 않고, 정해진 시나리오 실행부터 시작하며 초기 동시 검증은 1개로 제한하는 제안이다. 이 문서는 그 방향을 연동 대상으로 삼으며 채택·정책 변경·구현 완료를 대신 선언하지 않는다.

워크트리의 핵심 기능은 브라우저 구현이 완료되기 전에도 개발·단위 검증할 수 있다. 브라우저가 필요한 업무의 최종 완료는 실제 검증을 기다리며, 브라우저가 필요 없는 업무까지 일괄 중단하지 않는다. 필수 검증 여부는 사전 검토한 업무별 검증 계획으로 정하고, 실패 후 필수 항목을 조용히 선택 항목으로 바꾸지 않는다.

### 13.2 책임과 파일 변경 경계

| 담당 범위 | 소유 책임 |
| --- | --- |
| 워크트리 작업 | 업무·후보 경로와 코드 버전 식별, 테스트 서버·빌드의 출처 확인, 데이터·포트 분리, 실행 중 공간 변경 방지, 통합·완료 조건 |
| 브라우저 작업 | 브라우저 실행·배포, 컨텍스트 격리, 시나리오 실행·판정, 허용 주소 통제, 테스트 인증, 캡처·로그 보호, 브라우저 프로세스 중단·복구 |
| 공동 접점 | 환경·결과 형식, 서버 준비 확인, 인증 전달 경계, 검증 최신성, 상태 UI, 기존 대화의 도구 호환성 |

브라우저 쪽의 권한·배포·시나리오 러너를 이 변경에서 중복 구현하지 않는다. 공통 접점인 `backend/src/codex/codex.service.ts`, `backend/src/work/execution.service.ts`, `backend/src/work/store.ts`, `backend/src/work/testing-instructions.ts`, `backend/src/app.ts`, 업무 컨트롤러와 `frontend/src/components/WorkRoom.tsx`는 구현 직전 변경 내용을 대조하고 순차 반영한다. 담당 경계를 문서화한 것만으로 다른 채팅에 작업 지시가 전달된 것은 아니다.

### 13.3 검증 환경 계약 초안

브라우저에 임의 경로나 사용자가 입력한 URL을 바로 전달하지 않는다. 서버가 등록·확인한 `environmentId`를 기준으로 접근한다. 실제 필드명은 브라우저 쪽과 연동 착수 시 확정한다.

환경 정보에 필요한 내용:

- `environmentId`, `workId`, `workspaceId`, 대상 종류 `work/integration`, 후보일 때 `integrationId`.
- `commit`, 미커밋·untracked 소스까지 포함한 `sourceRevision`, `planRevision`, `buildId`, 검증 설정 버전.
- 서버가 확인한 허용 origin 목록, 프로세스 식별 정보, 준비 상태, 테스트 데이터 식별자, 만료 시각.
- 인증은 비밀 값 대신 서버 내부에서만 해석하는 테스트 인증 참조를 사용한다. 실운영 `DESKTOP_TOKEN`을 시나리오·AI 입력·URL·캡처 로그에 넣지 않는다. 테스트 환경의 좁은 인증 경로는 브라우저 작업에서 제공한다.

서버 health 200만으로 준비 완료로 인정하지 않는다. 실행 cwd·빌드 출처와 환경의 코드 버전을 대조하고, 검증 중인 서비스 응답도 빌드·환경 식별과 연결한다. 기존 서비스가 차지한 포트에 연결되면 중단한다. 등록된 검증 환경이 식별 확인을 지원하지 않으면 브라우저 자동 검증 준비 불가로 표시한다.

여러 서버가 필요한 프로젝트는 프런트엔드뿐 아니라 API 서버와 데이터 경로도 같은 환경에 묶는다. 같은 localhost의 다른 업무 포트는 기본 허용하지 않는다. 페이지 이동·API·리디렉션·팝업·필요한 실시간 연결의 허용 범위는 환경 목록에서 파생하고 브라우저 서비스가 강제한다.

### 13.4 실행·결과·잠금 계약

검증 요청은 `runId`, 요청 키, 환경 ID, 시나리오·버전, 시작 시 소스 버전으로 식별한다. 초기에는 브라우저 실행 슬롯 1개를 공유하되 업무별 대기 항목과 결과는 분리한다. 실행 대기 중 저장소 전체 잠금을 잡지 않는다.

브라우저가 해당 환경을 점유한 동안 같은 업무의 AI·파일 편집·공간 정리와 후보 재생성을 막는다. 브라우저를 소유한 프로세스나 종료 여부를 확인할 수 없으면 해당 환경의 점유를 유지하고 복구 상태를 표시한다. 실행 전후 소스·빌드 버전을 재검사해 외부 수정도 탐지한다.

결과는 `passed / failed / blocked / interrupted / uncertain`을 구분하고, 실행 전 상태는 `queued / preparing / running`으로 제공한다. 결과에 실제 소스·빌드·시나리오 버전, 검사 항목별 판정, 시작·종료 시각과 증거 참조를 기록한다. 증거 파일은 업무·실행별 데이터 폴더에 저장하고 권한·보존 기간을 적용한다.

클릭 성공이나 캡처 생성만으로 통과시키지 않는다. 저장 시나리오는 새로고침 후 값 유지 등 사전 조건을 판정하며, 실패 시 쓰기 동작을 무조건 반복하지 않는다. UI·네이티브 알림 등 별도 범위는 실제 검사한 방식과 한계를 표시한다.

브라우저 재시작·앱 재연결 시 실행 기록을 조회하고, 프로세스와 환경의 실제 상태를 확인한다. 요청을 자동 재실행하거나 성공으로 추정하지 않는다. 환경 정리는 브라우저·서버 종료 확인 후 자신이 소유한 프로세스와 테스트 데이터만 대상으로 한다.

브라우저 결과의 최신성은 환경 ID가 같다는 사실만으로 인정하지 않는다. 소스·계획·빌드·시나리오·검증 설정 버전이 모두 맞아야 한다. 통합 대상 HEAD가 바뀌어 후보를 다시 만들면 이전 후보의 브라우저 통과도 무효화한다.

### 13.5 결합 검증 시나리오와 출시 순서

| 시나리오 | 합격 조건 |
| --- | --- |
| 업무 A/B가 같은 경로의 코드를 각자 수정 | 각 테스트 서버·데이터·브라우저 컨텍스트·증거가 분리되고 브라우저 실행만 순서대로 진행 |
| 원본 서버가 이미 실행 중 | 수정 전 원본 화면을 업무 검증으로 사용하지 않고 대상 불일치 감지 |
| 포트 재사용 또는 API 연결 오류 | 업무 환경과 다른 프런트·API 조합을 준비 검사에서 차단 |
| A 통합 후 B 후보 생성 | 최신 원본을 포함한 B 후보 서버에서 브라우저 시나리오를 새로 실행 |
| 검증 중 코드·시나리오 변경 | 앱 내부 변경은 차단하고 외부 변경은 결과 무효 또는 중단으로 판정 |
| 개인 PC에서 다른 앱 사용 | 포커스·입력 간섭 없이 실제 렌더링·캡처·검증 완료 |
| 저장 실패 또는 잘못된 값 주입 | 검증기가 실패를 정확히 판정하며 정상 흐름의 통과와 모두 입증 |
| 인증 만료·금지 주소 이동 | 준비 실패 또는 차단으로 표시하며 인증 우회나 통과 처리 없음 |
| 검증 중 중단·재시작·연결 단절 | 요청 중복 실행 없이 실행·환경 소유권을 복구하고 결과 상태를 정확히 보존 |
| 설치·무설치 배포본 | 개발 도구 없는 환경에서 브라우저·테스트 서버·캡처·종료 확인 |

출시 순서는 **워크트리 공간·환경 식별 준비 → 별도 브라우저 작업의 정책·인증·실행·배포 확인 → 두 기능 연결 → 위 결합 시나리오 검증 → 브라우저 자동 검증 활성화**로 정한다. 워크트리 코어의 출시 조건과 브라우저 연동의 출시 조건은 구분하며, 필수 브라우저 검증을 수행하지 못한 업무는 완료 처리하지 않는다.

## 14. 작업 전용 공간 위치 설정과 용량 관리

### 14.1 설정 화면과 적용 시점

프로그램의 기존 설정 화면에 **작업 전용 공간** 항목을 추가한다. 작업 공간은 앱 업무 DB와 분리하며, 드라이브 여유 공간에 맞춰 사용자가 저장 위치를 지정할 수 있어야 한다.

- 현재 적용 경로, 설정 출처, 경로 사용 가능 여부, 드라이브 잔여 용량을 표시한다.
- 데스크톱에서는 폴더 선택을 제공하고, 네이티브 선택기를 사용할 수 없는 실행 방식에서는 프로그램 실행 호스트의 절대 경로 입력을 제공한다. 웹 클라이언트 PC의 경로로 오해하지 않도록 안내한다.
- **경로 검사 → 저장** 순서로 진행한다. 검사 결과에는 정규화된 최종 경로와 생성할 관리 하위 폴더를 표시한다.
- 최초 신규 격리 공간 생성 전에 설정을 안내한다. 기본 후보를 제안할 수 있으나 사용자가 확인하지 않은 경로에 신규 공간을 자동 생성하지 않는다.
- 설정 변경은 새 업무 공간과 새 통합 후보에 적용한다. 진행 중·질문 대기·승인 대기 업무를 중단하거나 서버를 재시작하지 않는다.
- 기존 공간 이동 기능은 최초 범위에서 제외한다. 사용자가 탐색기로 옮긴 공간은 경로·Git 연결 확인이 필요한 복구 상태로 표시한다.

### 14.2 경로 정책과 저장

- 적용 우선순위는 **명시적 `WORKSPACE_ROOT` 환경 설정 → 저장된 사용자 설정 → 최초 설정 안내**로 정한다. 환경 설정이 있으면 UI에 환경 설정으로 고정됐음을 표시하고 사용자 설정 편집을 막는다. 설정 화면에서 보이는 경로와 생성 서비스가 실제 사용하는 경로는 같아야 한다.
- 새 설정은 기존 애플리케이션 설정 저장 체계에 별도 키로 저장하며, 다른 프로젝트·도구 설정을 보존한다. 버전 토큰으로 동시 저장을 검사하고 파일을 원자적으로 교체한다.
- 기존 설정 API와 호환성을 확인해 다른 설정 저장 시 공간 설정이 유실되지 않게 한다. 별도 설정 서비스는 기존 저장 체계를 공유하며 중복된 독립 설정 파일을 만들지 않는다.
- 설정 루트마다 영속적인 `rootId`와 앱 데이터 프로필 소유 식별자를 등록한다. 경로를 바꿔도 이전 루트의 등록 기록은 남겨 기존 업무와 용량·정리 화면에서 조회한다.
- 업무에는 `rootId`, `workspaceId`, 생성 당시 절대 경로를 기록한다. 브라우저 환경은 이 ID를 참조하고 루트 변경으로 인증·결과·캡처 경로를 재배정하지 않는다.
- `WORKSPACE_ROOT`를 설정한 실행 방식은 시작 스크립트·데스크톱·상주 세션에 같은 값이 전달되는지도 검증한다. 새 저장 설정은 상주 서버 재시작 없이 다음 생성 시 읽는다.

경로는 서버에서 검사한다. 절대 로컬 경로만 초기 지원하며 존재하는 상위 경로부터 실제 경로를 확인한다. UNC·네트워크 경로는 초기 지원하지 않는다. 원본 프로젝트, Git 관리 영역, 앱 운영 데이터·설정·설치 영역과 같거나 어느 한쪽이 다른 쪽을 포함하는 경로는 거부한다. 드라이브 루트 자체를 작업 공간으로 사용하지 않는다.

심볼릭 링크·junction·reparse point를 통한 경계 우회와 Windows 대소문자·상대 경로 표기 차이를 검사한다. 검사 후 실제 생성·정리 시에도 다시 확인한다. 쓰기·읽기·삭제 권한은 고유한 검사 파일로 확인하고 검사 파일만 제거한다. 권한 문제를 해결하려고 시스템 ACL이나 보안 설정을 바꾸지 않는다.

사용자가 선택한 기존 폴더의 파일은 건드리지 않는다. 그 안에 앱 프로필별 전용 관리 하위 폴더를 만들고 소유 식별을 기록한다. 다른 프로필의 관리 공간은 소유권을 가져오거나 자동 정리하지 않는다.

### 14.3 디렉터리 구조

예시 구조는 다음과 같다. 화면에 표시하는 프로젝트 이름과 별개로 디렉터리에는 고유 ID를 사용한다.

```text
선택한 작업 공간 루트/
  openspecboard-<profileId>/
    identity.json
    projects/<projectId>/
      works/<workspaceId>/
        identity.json
        project/                # Git 워크트리 또는 기존 복사 방식
        runtime-data/           # 테스트 DB·캐시
        artifacts/<runId>/      # 캡처·검증 로그
      integrations/<candidateId>/
        identity.json
        project/
        runtime-data/
        artifacts/<runId>/
```

Git worktree의 실제 경로는 `project/`에 해당한다. 식별 정보와 테스트 자료는 소스 밖에 두어 커밋이나 제품 diff에 섞이지 않게 한다. 운영 `work.sqlite`, 앱 설정, 장기 보존 완료 기록은 기존 앱 데이터 경로에 남기며 작업 공간 정리 대상에서 제외한다. 정리 전에 필요한 diff·검증 근거를 장기 보존 저장소에 확정한다. 캡처 삭제 시에는 증거 만료를 표시하고 남아 있는 것처럼 링크하지 않는다.

전용 브라우저 바이너리는 업무별로 복사하지 않고 브라우저 작업이 관리하는 공통 버전별 캐시를 사용한다. 업무별 브라우저 프로필·데이터·증거는 격리하며 공통 바이너리 정리는 해당 작업의 참조·실행 검사를 따른다.

### 14.4 용량 표시와 생성 제한

- 전체·루트별·업무별 사용량과 드라이브 잔여 용량, 마지막 집계 시각을 표시한다. 의존성·빌드 결과·테스트 자료도 집계한다.
- 집계는 요청 시 또는 백그라운드에서 제한된 범위로 수행하고, 링크를 따라가거나 앱 화면을 장시간 막지 않는다. 확인하지 못한 용량은 0으로 표시하지 않고 미확인·부분 집계로 표시한다.
- 새 업무 공간은 구현 시작 때 만들고 계획 단계에서는 만들지 않는다. 재개할 때 같은 공간을 재사용한다.
- 초기 정책은 **동시 구현·검증 업무 3개, 저장소별 활성 통합 후보 1개, 신규 공간 준비 전 최소 잔여 용량 5 GiB**를 기본값으로 하며 설정에서 조정할 수 있게 한다. 업무 한도 초과는 시작 대기로 표시하고 미완료 공간을 삭제하지 않는다. 기존 중단 공간도 용량에 포함한다.
- 최소 잔여 용량은 필요한 전체 크기를 보장하지 않는다. 원본 크기·준비할 의존성의 추정치를 표시하고 복사·의존성 설치·빌드 전후 용량을 재확인한다. 용량 부족으로 준비가 실패하면 준비 실패 기록과 실제 잔여 파일을 남겨 복구·정리 대상으로 표시한다.
- 검증 자료 보존 기간의 기본값은 14일로 제안한다. 최초 버전은 만료 자료·완료 공간의 정리 제안과 사용자 확인 후 정리를 제공하며 무단 자동 삭제하지 않는다.

### 14.5 정리 조건과 예외

- 정리 화면은 소유가 확인된 공간만 목록에 표시하고 삭제할 소스 공간·의존성·테스트 자료와 보존할 기록을 구분한다.
- AI·검증·서버·브라우저 실행, 질문·승인 대기, 종료 불명확 상태의 공간은 정리하지 않는다.
- 미커밋 파일·미반영 커밋·확인되지 않은 무시 파일이 있는 공간은 일반 정리를 차단한다. 단순히 업무가 완료됐다는 이유만으로 강제 삭제하지 않는다.
- Git 워크트리는 Git 등록을 확인하고 정상 worktree 제거 절차를 사용한다. 루트 전체를 재귀 삭제하거나 강제 제거·일괄 prune하지 않는다.
- 드라이브 분리·권한 변경·경로 유실 시 기존 업무는 복구 필요로 표시한다. 새 기본 경로로 자동 재생성하거나 원본에서 실행하지 않는다.
- 기본 경로 변경 이후에도 이전 루트의 개별 공간을 정리할 수 있다. 루트 등록 해제는 참조 업무·후보가 없음을 확인한 뒤 제공한다.

### 14.6 필수 검증 시나리오

| 시나리오 | 합격 조건 |
| --- | --- |
| 최초 경로 선택 후 앱 재실행 | 설정이 유지되고 신규 업무가 표시된 위치에 생성됨 |
| `WORKSPACE_ROOT`가 설정됨 | 환경 설정 우선 적용과 UI 편집 제한이 일치함 |
| 공백·한글 경로 또는 다른 로컬 드라이브 | 공간 생성·Git 작업·검증·정리까지 정상 동작함 |
| 원본·운영 DB·설치 영역 또는 경계 우회 경로 선택 | 서버가 거부하며 기존 파일을 수정하지 않음 |
| 권한 없는 경로·읽기 전용·용량 미확인 | 이유를 표시하고 설정·생성을 성공으로 보고하지 않음 |
| 잔여 용량 부족 또는 동시 실행 한도 초과 | 생성 차단·시작 대기를 구분하고 기존 업무를 보존함 |
| A 실행 중 기본 경로 변경 후 B 시작 | A의 경로·대화·질문·브라우저 환경은 유지되고 B만 새 루트 사용 |
| 같은 설정을 두 화면에서 변경 | 오래된 저장을 거부하고 최신 설정을 안내함 |
| 이전 루트의 완료 공간 정리 | Git 등록과 공간을 정상 정리하고 완료 기록·앱 DB는 유지됨 |
| 진행 중·미반영·외부 소유 공간 정리 요청 | 서버가 차단하고 다른 폴더나 공통 캐시를 삭제하지 않음 |
| 실제 드라이브 분리 또는 생성 중 용량 소진 | 실패·복구 상태를 보존하고 다른 경로로 자동 대체하지 않음 |
