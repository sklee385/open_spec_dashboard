# Spec Delta

## Purpose

검토된 계획과 명시한 Git 기준에서 업무별 독립 워크트리를 준비하고, 최신 대상과 결합한 통합 후보를 검증하여 사용자 확정으로만 순차 반영하며 장애 뒤 실제 상태를 복구한다.

## ADDED Requirements

### Requirement: 업무 공간 종류와 안전한 생성
시스템은 새 Git 업무에 고유 업무 브랜치와 워크트리를 제공하고 기존 복사 업무의 경로·동작을 유지해야 한다(SHALL). 비Git·초기 커밋 없는 프로젝트는 복사 방식을 표시하고 Git 준비 실패를 조용히 복사 방식으로 바꾸거나 저장소를 자동 생성해서는 안 된다(MUST).

#### Scenario: 새 Git 업무와 재개
- **WHEN** 검토 후 사용자가 구현 시작 또는 기존 업무 재개를 요청한다
- **THEN** 새 업무만 검사된 루트에 준비하고 재개는 기존 공간의 실제 Git 등록·공통 디렉터리·브랜치·소유권을 확인해 재사용한다

#### Scenario: 기존 이름이나 준비 실패
- **WHEN** 다른 소유의 브랜치·경로가 존재하거나 Git 준비가 실패한다
- **THEN** 덮어쓰지 않고 실패·복구 상태를 표시하며 원본 실행을 시작하지 않는다

### Requirement: 기준 커밋과 해당 업무 문서 보존
시스템은 구현 시작 때 사용자가 확인한 로컬 기준 브랜치·커밋과 검토된 해당 변경 문서·보존 아이디어만으로 업무를 준비해야 한다(MUST). 미커밋 제품 코드와 다른 업무 문서를 자동 수입하지 않고 생성 전후 기준과 문서 버전을 확인해야 한다(MUST).

#### Scenario: 미커밋 원본에서 준비
- **WHEN** 원본에 다른 제품 코드나 다른 업무 문서의 미커밋 변경이 있다
- **THEN** 제외 목록을 보여주고 사용자 확정 정책에 따라 제외 후 진행하거나 원본 정리 전 준비를 차단하며 자동 커밋·stash하지 않는다

#### Scenario: 준비 중 계획 또는 기준 변경
- **WHEN** 문서·원본 HEAD·선택 브랜치 tip이 준비 전후 달라진다
- **THEN** 구현을 시작하지 않고 기준 재확인과 문서 재검토를 요구한다

#### Scenario: 두 가지 비교 기준
- **WHEN** 가져온 업무 문서가 업무 기준 커밋에 기록된다
- **THEN** 제품 변경은 문서 기준 이후로 표시하고 최종 통합 diff에는 원래 기준 이후의 해당 문서 변경도 포함한다

#### Scenario: 로컬 준비 파일
- **WHEN** 런타임·환경 파일·의존성이 필요하다
- **THEN** 검토된 준비 정책만 적용하고 운영 DB·로그·다른 업무 데이터와 비밀값 커밋을 제외하며 수정 가능한 링크로 의존성을 공유하지 않는다

### Requirement: 통합 요청과 후보
시스템은 업무 검증과 최신 계획 검토 후 사용자의 통합 요청으로 저장소당 활성 후보 하나를 준비해야 한다(SHALL). 사용자가 다음 업무와 커밋 파일 범위를 선택하고 후보는 최신 대상과 업무 결과를 결합해야 한다(MUST).

#### Scenario: 선택 결과와 검증 일치
- **WHEN** 사용자가 staged·unstaged·untracked 목록을 보고 결과 파일을 선택한다
- **THEN** 선택 범위만 커밋하고 검증 대상 소스가 제외된 채 남으면 통합을 막으며 원본·업무 브랜치를 후보 병합으로 수정하지 않는다

#### Scenario: 통합 순서와 충돌
- **WHEN** A 반영 후 B의 통합 후보에서 동일 파일 충돌이 발생한다
- **THEN** 사용자가 선택한 B 후보에서 충돌을 표시하고 해결·커밋·재검증할 수 있게 하며 자동 순서 병합하지 않는다

### Requirement: 후보 검증 근거와 사용자 확정
시스템은 대상 HEAD·업무 HEAD·후보 커밋·실제 소스·계획·명령 및 시나리오 버전에 묶인 필수 검증을 통과한 후보만 사용자 확정으로 원본에 반영해야 한다(MUST). 업무 단독 통과와 미실행·차단 결과를 후보 통과로 대체해서는 안 된다(MUST).

#### Scenario: 후보나 대상 변경
- **WHEN** 충돌 해결·수동 수정·대상 또는 업무 HEAD 변경이 발생한다
- **THEN** 이전 검증을 과거 결과로 남기고 최신 후보 커밋과 필요한 전체 검증·브라우저 검증을 다시 요구한다

#### Scenario: 최종 반영
- **WHEN** 사용자가 검증된 후보 반영을 확정한다
- **THEN** 원본의 대상 브랜치·HEAD·index·파일 상태·진행 작업과 후보 버전을 다시 확인하고 ff-only로 반영한 실제 HEAD를 확인해 기록한다

#### Scenario: dirty 원본 또는 다른 worktree의 대상
- **WHEN** 원본에 미커밋 변경이나 merge/rebase가 있거나 대상 브랜치가 다른 경로에 체크아웃돼 있다
- **THEN** 반영을 차단하고 자동 stash·reset·브랜치 전환·강제 덮어쓰기·원격 push를 하지 않는다

### Requirement: 실행 의도와 불확실 상태 복구
시스템은 생성·병합·반영·제거의 의도와 요청 키를 영속 기록하고 장애 뒤 실제 Git·경로·프로세스 상태를 대조해야 한다(MUST). 결과 불명 요청을 자동 반복하거나 성공으로 추정해서는 안 된다(MUST).

#### Scenario: 응답 유실과 재시도
- **WHEN** 반영 뒤 응답이 끊기거나 같은 요청 키로 재시도한다
- **THEN** 기존 요청과 실제 대상 HEAD를 조회해 결과를 확인하고 같은 키의 다른 내용을 거부하며 중복 반영하지 않는다

#### Scenario: 취소와 공간 유실
- **WHEN** 사용자가 취소하거나 기존 공간을 확인할 수 없다
- **THEN** 결과와 대화 ID를 보존하고 자동 역병합·새 위치 재생성·원본 대체 실행을 하지 않는다

### Requirement: 반영 완료와 보관 구분
시스템은 반영 증거·사용자 완료 확인·OpenSpec 보관 결과를 구분해 저장해야 한다(SHALL). 보관은 원본에서 직렬 실행하고 보관이 만든 미커밋 변경을 다음 통합 전 검사해야 한다(MUST).

#### Scenario: 반영 후 보관 실패
- **WHEN** 반영은 성공했지만 보관이 실패하거나 미커밋 명세 변경이 남는다
- **THEN** 반영 성공 근거를 유지하고 보관 오류와 다음 통합 차단 이유를 따로 표시하며 완료·보관을 자동 확정하지 않는다
