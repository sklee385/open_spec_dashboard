# Spec Delta

## MODIFIED Requirements

### Requirement: 업무별 변경 격리
시스템은 구현·재개·검증을 업무별 독립 실행 공간에서 수행하고 해당 업무 공간의 기준 대비 변경만 표시해야 한다(MUST). 원본 프로젝트나 다른 업무의 병행 변경, 구현 시작 전에 이미 존재한 변경을 해당 업무 변경으로 포함해서는 안 된다(MUST). 새 Git 업무는 선택 커밋과 해당 업무 검토 문서 기준을, 기존 복사 업무는 기존 스냅샷을 사용해야 한다(SHALL). 실행 공간을 복구할 수 없으면 원본에서 대신 실행해서는 안 된다(MUST).

#### Scenario: 다른 업무의 병행 변경
- **WHEN** 업무 A와 B가 같은 원본 프로젝트에서 각각 구현을 진행한다
- **THEN** A의 목록과 전후 내용에는 A의 실행 공간에서 발생한 차이만 표시한다
- **AND** B나 원본에서 발생한 동일 파일 및 다른 파일의 수정은 A 결과에 섞이지 않는다

#### Scenario: 기존 미커밋 변경
- **WHEN** 구현 시작 전 원본에 기존 변경이 있다
- **THEN** 복사 업무는 이를 초기 상태로 보존하고 새 Git 업무는 사용자 확정 기준 정책으로 제품 변경을 제외 또는 준비 차단하며 기존 변경을 새 업무 차이로 표시하지 않는다

#### Scenario: 재개 공간 누락
- **WHEN** 업무 전용 실행 공간이 없거나 다른 업무의 공간으로 식별된다
- **THEN** 실행·검증을 차단하고 복구 필요를 안내한다

#### Scenario: 기존 공유 폴더 업무
- **WHEN** 기존 업무의 기록에 격리된 실행 기준이 없다
- **THEN** 시스템은 업무별 귀속 기록 없음으로 표시하고 공유 폴더 차이를 이 업무만의 결과로 확정하지 않는다

#### Scenario: 같은 업무의 실행 경로
- **WHEN** 사용자가 추가 지시·수동 편집·검증·대화 재개를 요청한다
- **THEN** 저장된 같은 업무 공간과 대화 ID를 유지하고 기본 루트 변경으로 경로를 다시 계산하지 않는다

### Requirement: 업무 변경의 원본 반영
시스템은 업무 완료 요청과 구분되는 사용자의 별도 원본 반영 요청으로 검증된 업무 변경만 반영해야 한다(SHALL). 복사 업무는 경로별 시작 기준 또는 반영 결과를 비교하고 워크트리 업무는 최신 대상과 통합 후보의 검증·사용자 확정 후 ff-only 반영을 사용해야 한다(MUST). 충돌·반영 실패·미완료 상태에서는 자동 덮어쓰기와 업무 완료를 막고 복구 상태를 제공해야 한다(MUST).

#### Scenario: 완료 요청과 원본 반영 구분
- **WHEN** 사용자가 원본 반영을 요청하지 않은 상태에서 업무 완료를 요청한다
- **THEN** 시스템은 자동 반영하지 않고 별도 원본 반영이 필요하다고 안내한다

#### Scenario: 서로 다른 파일 반영
- **WHEN** 복사 업무 A의 변경을 반영하고 원본의 다른 파일에는 B의 변경이 있다
- **THEN** A의 변경 경로만 반영하고 B의 파일은 유지한다

#### Scenario: 같은 파일 반영 충돌
- **WHEN** 복사 업무의 기준 이후 원본의 같은 파일이 다른 내용으로 변경되었다
- **THEN** 충돌 경로를 표시하고 자동 덮어쓰기와 완료 처리를 차단한다

#### Scenario: 부분 반영 후 중단
- **WHEN** 원본 반영 도중 실패하거나 서버가 재시작한다
- **THEN** 시스템은 반영 기록으로 복구·재시도 상태를 제공하며 전체 반영과 결과 저장을 확인하기 전 완료로 표시하지 않는다

#### Scenario: 워크트리 업무 반영
- **WHEN** 워크트리 업무의 원본 반영을 요청한다
- **THEN** 기존 파일 복사 반영을 호출하지 않고 통합 후보 생성·필수 재검증·사용자 확정 경로를 제공한다

## ADDED Requirements

### Requirement: 계획과 운영 반영의 명시적 경계
시스템은 계획 AI의 쓰기를 해당 변경 문서로 제한하고 사용자 검토·구현 지시 전 제품 코드 구현을 시작해서는 안 된다(MUST). 코드 작성·검증 성공과 실제 운영 서버 반영 여부를 구분해야 한다(SHALL).

#### Scenario: 문서 준비와 목록 조회
- **WHEN** 계획 문서 생성·질문 목록 조회·OpenSpec 검증을 마쳤다
- **THEN** 이를 문서 검토 완료·구현 허가·원본 반영·완료·보관으로 자동 처리하지 않는다

#### Scenario: 실행 중인 세션 서버
- **WHEN** 새 세션 코드의 빌드·회귀 검증이 성공했지만 실행 중 서버에 반영되지 않았다
- **THEN** 운영 미반영을 따로 표시하고 실행·질문·승인 대기 중 세션 서버를 재시작하지 않는다
