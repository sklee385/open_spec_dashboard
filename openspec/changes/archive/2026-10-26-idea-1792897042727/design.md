# Design

## Context

동기는 `proposal.md`의 Why를 따른다. 사용자는 화면 내 알림과 Windows 알림을 함께 선택했고, 복구된 `closed_browser_scope` 질문에는 **Edge 완전 종료도 포함**이라고 답했다. 문서에 추가한 알림 소리 요구도 함께 반영한다.

현재 구현에는 `WorkStore.attention()`과 `GET /api/work/attention`, 앱 공통 대기 목록, IndexedDB 중복 방지 및 업무·질문 이동이 있다. Windows 알림은 프런트엔드의 `new Notification(..., { silent: true })`로 생성한다. 따라서 현재 코드는 브라우저 종료 후 수신과 알림음 요구를 충족하지 않는다. 기존 검증 기록은 이전 범위의 증거로 보존한다.

업무·질문은 독립된 세션 서버와 SQLite에 저장되고 일반 웹 서버는 게이트웨이 역할을 한다. 알림을 위해 실행 중인 세션 서버를 자동 재시작하지 않는다.

## Goals / Non-Goals

**Goals:** Edge가 종료되어도 같은 사용자 세션의 서버가 질문을 감지하여 Windows 알림·기본 알림음을 요청한다. 알림 클릭 시 Edge를 열어 정확한 질문에 이동하고 기존 응답·검토 흐름을 유지한다.

**Non-Goals:** 외부 Push 서비스, Windows 서비스의 Session 0 실행, PC 부팅 시 자동 실행 등록, 로그아웃·서버 종료 중 전송, 별도 음원·반복 독촉, 질문 대리 응답은 추가하지 않는다.

## Decisions

### 브라우저와 독립된 전달 주체

세션 서버에 알림 전달 서비스를 추가한다. 서버 부트스트랩 시 기존 질문 상태 복구·만료 처리가 끝난 뒤 대기 요청을 즉시 조회하고, 조회·발행 처리가 끝난 뒤 5초 간격으로 다시 확인한다. 사용 설정이 켜져 있으면 현재도 `pending`인 요청만 네이티브 어댑터로 전달한다. 처리 직전 상태를 재확인하여 이미 응답·만료된 요청을 새로 알리지 않는다.

서버 안의 반복 실행은 하나만 유지하고 종료 시 타이머와 도우미 프로세스를 정리한다. 알림 실패는 Codex 실행·질문 응답·게이트웨이 연결에 전파하지 않는다. 브라우저의 포커스·탭 수·실행 상태는 이 서비스의 발행 조건이 아니다.

열린 탭 기반 발행은 Edge 종료 요구를 충족하지 못한다. Web Push는 추가 전달 인프라·구독과 브라우저 백그라운드 동작에 의존하므로 이번 로컬 앱에서는 사용하지 않는다. 별도 상주 앱 대신 이미 업무를 소유하는 세션 서버가 전달을 소유한다.

### Windows 어댑터·기본 알림음·사용 설정

Windows 데스크톱 토스트 API를 호출하는 로컬 도우미를 사용한다. Windows PowerShell과 WinRT 호출을 경계가 좁은 어댑터로 감싸며, 서버는 셸 명령을 조합하지 않고 고정된 도우미 경로·인자와 표준 입력 JSON으로 요청한다. 텍스트와 URI는 XML에 안전하게 넣고, 질문 원문·실행 명령·경로·사용자 답변을 토스트나 도우미 로그에 포함하지 않는다.

도우미는 제품 전용 AUMID `OpenSpecBoard.Notifications`와 프로토콜 활성화를 지원하는 사용자 범위의 시작 메뉴 바로가기·필요 등록 정보를 준비한다. 다른 앱의 알림 ID를 빌려 쓰지 않는다. 등록 실패·미지원 Windows·비대화형 세션은 오류 상태로 표시하고 화면 내 목록을 유지한다. 등록·해제는 제품이 생성한 항목만 대상으로 하며 시스템 정책·ACL·다른 앱 설정을 변경하지 않는다.

토스트에는 업무명과 답변 필요/승인 필요만 표시하고 기본 시스템 알림음 `ms-winsoundevent:Notification.Default`를 한 번 요청한다. 무음 강제 설정은 제거하고 별도의 브라우저 오디오 재생은 추가하지 않는다.

사용자는 순차 검토의 `review_notification_sound` 질문에서 “네, 기본 알림음으로 진행”을 선택했다. 알림음은 Windows 기본 소리를 한 번 사용하며, 음소거·방해 금지·앱별 알림 차단·오디오 장치 설정을 우회하지 않는다. OS가 소리를 차단한 상황을 음향 출력 성공으로 보고하지 않는다.

사용자는 복구된 `review_initial_notification_setting` 답변에서 “처음부터 켜짐”을 선택했다. 저장된 설정이 없는 최초 제품 시작은 알림 사용을 켜짐으로 초기화하고, 세션 서버가 사용자 범위 등록·활성화를 시도한다. 이미 저장된 켜짐·꺼짐은 우선하며, 사용자가 끈 설정을 재시작 시 자동으로 다시 켜지 않는다.

`GET /api/notifications/settings`에서 저장된 사용 의도 `enabled`, 현재 실제 발행 가능 여부 `effectiveEnabled`, 대시보드 주소·등록 상태·최근 오류를 조회한다. `effectiveEnabled`는 읽기 전용으로, 사용 설정·지원 환경·등록 성공·유효한 주소 조건을 모두 충족해야 참이다. 등록이나 주소 확인에 실패하면 사용 의도는 유지하되 실제 발행을 중단하고 실패 원인을 표시한다. 설정상 켜짐을 실제 활성화·전달 성공으로 보고하지 않는다. 다음 제품 시작이나 사용자의 명시적 켜기 동작에서 등록·주소 조건을 다시 확인한다.

`PUT /api/notifications/settings`는 사용자의 명시적 켜기·끄기·주소 수정 동작을 저장한다. 설정은 `DATA_DIR/notifications.json`에 원자적으로 보존하여 브라우저·서버 재시작 후 유지한다. 최초 제품 시작의 기본값 생성 외에는 조회나 브라우저 접속만으로 저장된 사용 의도를 바꾸지 않는다.

브라우저 `Notification.requestPermission()`을 사용하지 않는다. 화면은 Windows의 제품별 알림 설정을 확인하는 안내를 제공한다. 사용자가 앱의 알림을 끄면 새 네이티브 발행은 중단하고 화면 내 목록은 유지한다. 이미 OS에 제출한 알림의 취소를 보장하지 않는다.

### 화면 내 대기 목록과 조회

기존 `GET /api/work/attention` 계약과 정렬을 유지한다. 응답은 `workId`, `sourceId`, `changeName`, `title`, `questionId`, `kind`, `createdAt`, `status: pending`을 포함하며 한 요청의 여러 질문을 한 건으로 센다. `sending`, `recovering`, `uncertain`, `answered`, `expired`는 대기 수에서 제외한다. 업무명은 원본 아이디어 제목, 없으면 변경명을 사용한다.

공통 알림 관리자는 최초 즉시, 조회 완료 후 5초 간격과 포커스·연결 복귀에 갱신한다. 조회는 겹치지 않게 하고 실패 시 마지막 목록과 연결 오류를 표시한다. 새 요청의 화면 내 안내는 유지하지만 브라우저가 Windows 알림을 직접 만들지 않는다. 네이티브 설정·등록 오류도 목록과 별도로 표시한다.

### 채널별 중복 방지와 장애 처리

Windows 알림 발행 권한은 브라우저 IndexedDB에서 서버 SQLite로 옮긴다. 기존 `records` 저장소에 `native-notification` 종류와 `(workId, questionId)`에서 만든 고유 키를 사용한다. 일반 `record()`의 덮어쓰기 대신 원자적 신규 삽입으로 발행 권한을 확보한다. 발행 시도 기록은 `claimed`, `submitted`, `failed`, `uncertain`을 구분하고 프로세스 재시작 뒤에도 보존한다. OS API 수락을 실제 표시·청취 완료로 해석하지 않는다.

키를 확보한 뒤 OS를 호출하여 요청당 자동 발행 시도를 최대 한 번으로 제한한다. 제출 결과 불명·직전 프로세스 종료 때도 무조건 재발행하지 않으며, 대기 목록과 실패·확인 필요 상태로 누락 가능성을 드러낸다. 사용 설정을 껐다 켜거나 브라우저 데이터를 지워도 같은 서버 기록을 재설정하지 않는다. 최초 활성화 시 아직 발행 기록이 없는 현재 대기 요청은 한 번 알린다.

사용자는 복구된 `review_notification_retry_policy` 답변에서 “한 번만 시도”를 선택했다. Windows가 수락하지 않았음이 확실한 전송 실패도 자동 재시도하지 않는다. `failed` 또는 `uncertain`을 저장하고 화면에 실패·확인 필요 상태와 대기 목록을 유지한다. 사용 설정 변경·서버 재시작으로 이미 시도한 요청의 발행 권한을 되돌리지 않는다. 최초 포함 최대 3회 시도하는 대안은 채택하지 않는다.

제품 등록·주소 조건을 확인하는 절차와 요청별 OS 발행 시도는 구분한다. 선행 조건이 충족되지 않아 아직 발행 권한 확보와 OS 호출을 시작하지 않은 요청은 조건 충족 후 최초 한 번을 시도할 수 있다. 이미 발행 권한을 확보한 요청을 등록 재확인을 이유로 다시 제출하지 않는다.

화면 내 일시 안내만 기존 IndexedDB의 고유 키를 사용한다. 이 저장소의 오류는 화면 안내·오류 표시로 처리하되 서버 Windows 알림을 중단시키지 않는다. 여러 탭이나 새 프로필이 화면을 열어도 네이티브 알림 발행 주체는 서버 하나다.

### 웹 호환 모드의 Edge 실행과 업무·질문 직접 연결

최초 제품 시작의 대시보드 주소는 배포 설정 `OPENSPEC_DASHBOARD_URL`을 우선하고, 지정하지 않으면 현재 `scripts/start.ps1`의 기본 프런트엔드 주소인 `http://127.0.0.1:13001/`을 사용한다. 이후에는 저장한 주소를 우선한다. 이 기본값으로 브라우저 첫 접속 전에도 등록·활성화를 준비할 수 있다. 다른 포트로 실행할 때는 배포 설정 또는 화면의 주소 수정 동작으로 실제 주소를 지정하며, 접속한 브라우저 주소를 기존 설정에 자동 덮어쓰지 않는다.

주소는 로컬 `http` 또는 `https`의 `localhost`, `127.0.0.1`, `[::1]`만 허용하고 사용자 정보·기존 쿼리·프래그먼트는 거부한다. 유효하지 않은 배포·저장 주소는 오류로 표시하고 임의의 다른 주소로 조용히 대체하지 않는다. 포트는 설정한 대시보드 주소를 사용하며 13001로 고정하지 않는다.

토스트는 프로토콜 활성화 URI에 설정된 대시보드 주소와 인코딩된 `workId`, `questionId`만 넣는다. `microsoft-edge:`를 통해 Edge가 종료된 경우에도 해당 URL을 새 탭으로 연다. 일반 Windows 기본 브라우저 설정을 바꾸거나 Edge 실행 파일 위치를 추측하지 않는다. 사용자 클릭 없이 창을 자동으로 열지 않는다. 프로토콜 활성화는 알림을 생성한 탭이나 짧게 살아 있는 콜백 프로세스에 의존하지 않게 하여 알림 센터에서 나중에 누른 경우도 지원한다.

프런트엔드 `App`은 최초 상태 복원 전에 두 식별자를 함께 검사한다. 직접 연결 요청이 있으면 저장된 최근 업무를 먼저 열거나 업무 생성·대화 재연결을 하지 않고, 최신 업무·변경 조회로 대상을 확인한다. 화면 내 알림과 같은 이동 함수를 호출하여 대화 영역의 대상 요청에 스크롤·포커스를 이동한다. 현재 업무 화면이 로딩한 요청보다 알림이 앞선 경우에도 최신 상세 갱신 후 판정한다.

완료·만료 요청이면 해당 업무에서 현재 상태와 기존 복구 경로를 표시하고 자동 응답·승인·복구를 하지 않는다. 잘못된 식별자·삭제된 프로젝트·업무는 오류를 표시하고 다른 업무로 대체하지 않는다. 같은 탭의 화면 내 이동 전에는 문서·메시지·답변 초안을 저장하고, 저장 실패 시 현재 화면을 유지한다. 새 Edge 탭으로 여는 경우 기존 탭의 초안을 덮어쓰지 않는다.

직접 연결 처리 성공 후 URL의 알림 인자만 제거하여 후속 조작이 동일 요청 이동을 반복하지 않게 한다. 링크 입력을 명령이나 파일 경로로 사용하지 않는다.

## Risks / Trade-offs

- 사용자 세션·OS 설정에 따른 표시·음향 제한 → 설정 및 오류를 화면에서 구분하고 실제 Windows에서 수동 확인한다. OS 차단을 우회하지 않는다.
- 발행 권한 확보 후 프로세스 종료 → 중복 방지를 우선하여 자동 재시도하지 않는다. 대기 목록과 확인 필요 상태를 보존한다.
- 서버 종료·PC 절전 → 실행 중 수신만 범위에 포함한다. 재개 후 현재도 유효한 미발행 대기 요청만 확인한다.
- 사용자 범위 등록의 환경 차이 → 제품 고유 등록을 사용하고 해제·실패 테스트를 수행한다. 관리자 권한이나 전역 설치를 요구하지 않는다.
- 대시보드 주소 변경·게이트웨이 중단 → 주소를 수정할 수 있게 하고 링크 실패 시 원인을 안내한다. 새 세션 서버를 임의 생성하지 않는다.

## Migration Plan

화면 내 목록과 기존 업무·질문 레코드는 유지한다. 네이티브 설정·등록·서버 발행을 추가하고, 브라우저 Windows 알림 생성과 권한 요청을 제거하는 작업을 함께 배포하여 중복 채널을 만들지 않는다. SQLite는 기존 레코드 종류를 확장하며 테이블 구조는 변경하지 않는다. 브라우저의 과거 발행 이력은 OS 전달 성공의 증거로 가져오지 않는다. 최초 제품 시작은 기본 켜짐으로 등록·활성화를 시도하며, 등록·주소 조건을 만족하면 미발행 대기 요청을 한 번 알릴 수 있음을 안내한다. 저장된 꺼짐 설정은 유지한다.

모든 실행·답변·승인 대기가 해소된 뒤 세션 서버를 명시적으로 재시작한다. 기존 대화를 자동 종료하거나 코드 변경 때 세션 서버를 watch로 재시작하지 않는다. 되돌릴 때는 네이티브 전달을 먼저 끄고 기존 업무·질문 기록을 보존한다. 사용자가 등록 해제를 요청하면 제품 전용 바로가기·등록만 제거한다.

최종 문서 검토와 구현 전환은 `proposal.md`에 기록한 사용자 확인 원칙을 따른다. 알림 설정 변경·항목 조회·문서 검증이나 이전 구현의 체크·테스트 결과로 새 범위의 완료를 판단하거나 문서 검토 완료·구현 시작을 자동 처리하지 않는다.

## Desktop activation revision

사용자는 `desktop_notification_activation` 질문에서 추천안을 선택했다. 데스크톱 알림은 `openspecboard://attention?workId=...&questionId=...`만 사용한다. Electron 사용자 범위 프로토콜 등록과 기존 단일 인스턴스 잠금을 공유한다. 실행 중·트레이·최소화 상태는 기존 창을 복원하며, 프로그램이 종료된 경우 이미 받은 알림 클릭으로 재실행한다. 완전 종료 동안 새 알림 전달은 제공하지 않는다.

데스크톱 모드는 임시 서버 포트와 `x-desktop-token`을 링크에 담지 않는다. 메인 프로세스가 고정 스킴·attention 호스트·식별자 두 개만 검증한다. 최초 실행은 신뢰한 내부 origin에 두 식별자를 붙여 최근 업무 복원 전에 처리한다. 실행 중에는 대시보드 전용 제한된 preload로 식별자만 전달한다. 등록된 메인 프레임이 초기 링크 처리를 마쳐 준비되기 전에는 전달을 보류한다. 앱은 기존 공통 이동을 사용해 최신 업무·질문을 확인하고 초안 저장 실패 시 현재 화면을 유지한다. 이동을 위한 새로고침·재연결·답변·승인은 하지 않는다.

웹 호환 모드는 이전 Edge 링크를 유지한다. 데스크톱 모드는 `OpenSpecBoard.DesktopNotifications`와 별도 사용자 바로가기를 사용해 웹 등록을 덮어쓰지 않는다. 앱 프로토콜 등록 실패 시 enabled 의도를 유지하되 실제 발행을 비활성화한다. 데스크톱 화면에는 브라우저 주소 입력을 숨기며 앱 연결 상태를 안내한다. 발행 기록은 유지하며 과거 Edge 토스트나 이미 시도한 질문을 자동 재발행하지 않는다. 이 절은 앞선 Edge 전용 이동 설명의 데스크톱 실행 부분을 대체한다.

- [Electron: 앱 전용 링크와 단일 인스턴스 처리](https://www.electronjs.org/docs/latest/tutorial/launch-app-from-url-in-another-app)
