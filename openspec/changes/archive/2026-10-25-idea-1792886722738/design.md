# Design

## Context

동기와 범위는 `proposal.md`, 동작 계약은 검토 완료된 `specs/dashboard-localization/spec.md`를 따른다. 사용자는 지원 언어가 없을 때 영어를 표시하는 것으로 결정했다.

설계 수립 당시 프런트엔드는 React·TypeScript 기반이며 번역 기반이 없었다. `main.tsx`에서 바로 앱을 렌더링하고, 화면별 상수와 JSX에 한국어·영어 문구가 섞여 있었다. `lib/utils.ts`의 상대 시간은 영어를 조합하고 오래된 날짜는 브라우저 기본 로캘을 사용했다. `IdeaDetailModal`도 로캘 없이 날짜를 표시했다.

`ErrorBoundary`는 클래스 컴포넌트다. 설계 수립 당시 `WorkRoom`은 사용자 메시지를 표시 이름인 `나`와 비교하여 스타일을 정하고, 제품이 생성한 한국어 문장을 AI 요청에 포함했다. 기존 테스트도 한국어 접근성 이름을 조회했으므로 환경에 따른 차이를 방지하기 위해 언어 설정을 명시할 필요가 있었다.

이 설계에 따른 구현·자동 검증 이력은 `tasks.md`에 기록되어 있다. 사용자는 browser-use 커넥터의 예외 허용 대신 Microsoft Edge 직접 검증을 선택했으며, 최신 복구 답변에서 질문에 명시된 모든 항목의 직접 확인·통과를 알렸다. 이를 사용자 수행 근거로 기록하고 있으며 에이전트의 실화면 확인으로 표현하지 않는다. 현재는 결과를 반영하는 계획 문서 재검토 단계이며, 제품 코드 수정과 브라우저 도구 실행은 하지 않는다.

## Goals / Non-Goals

**Goals:**

- 언어 선택, 번역, 날짜·수량 표시를 공통 경계로 모아 모든 화면이 동일한 결과를 사용한다.
- 표시용 번역을 API 값·업무 분기·AI 요청과 분리한다.
- 언어별 화면과 번역 누락을 기존 Vitest·Testing Library 환경에서 재현 가능하게 검증한다.

**Non-Goals:**

- 백엔드 오류 코드 체계, 저장 데이터 형식, 업무 실행 서비스의 재설계.
- 수동 언어 선택, 언어 저장, 실행 중 브라우저 언어 변경 감지.
- 문서·대화·명령 출력의 자동 번역이나 화면 언어에 따른 AI 요청 변경.

## Decisions

### 1. 공통 번역 모듈과 React Context

`frontend/src/i18n/`에 언어 감지, 영어·한국어 사전, 번역 함수와 Context를 둔다. 화면에서는 공통 훅으로 선택 언어와 번역 기능을 사용하고, 순수 유틸리티에는 언어를 인자로 전달한다. 사전은 앱과 함께 동기적으로 로드한다.

화면마다 언어 조건문을 두는 방식은 누락과 표현 불일치를 늘린다. 외부 번역 라이브러리는 현재 두 언어·브라우저 자동 선택 범위에서 필요한 기능보다 의존성과 설정이 커지므로 추가하지 않는다. 향후 언어 확대는 이 모듈 경계에서 재검토할 수 있다.

### 2. 렌더링 전 언어 확정

`main.tsx`에서 언어를 한 번 감지하고, `document.documentElement.lang`을 설정한 뒤 Provider로 앱을 감싸 렌더링한다. 첫 화면과 로딩 안내가 다른 언어로 잠깐 나타나는 것을 방지한다.

감지는 브라우저 정보 읽기와 순수한 언어 선택 로직을 분리한다. `navigator.languages`가 존재하고 비어 있지 않으면 그 목록만 순서대로 탐색한다. 없거나 비어 있을 때만 `navigator.language`를 사용한다. 태그를 소문자로 정규화하고 기본 언어가 `ko` 또는 `en`인지 확인한다. 지원 언어가 없거나 정보 접근에 실패하면 `en`이다. 모듈을 불러오는 것만으로 브라우저 전역을 읽지 않도록 하여 테스트와 오류 처리를 단순하게 유지한다.

실행 중 언어 변경 구독이나 로컬 저장은 하지 않는다. 새로고침 때 같은 초기화 경로를 다시 실행한다.

### 3. 번역 키와 값의 계약

영어 사전의 키를 기준으로 한국어 사전의 동일한 키 집합을 타입과 테스트로 검증한다. 키는 `common`, `header`, `kanban`, `ideas`, `settings`, `workRoom` 등 기능별로 구분하고, 고정 식별자와 표시 문구를 분리한다. 화면 문장을 여러 조각으로 연결하지 않고 완성된 문구 단위로 번역한다.

변수가 있는 항목은 타입이 있는 인자를 받는 메시지 함수로 표현한다. 영어 개수 안내는 단수·복수 문구를 구분하고 숫자 표기는 선택 언어의 `Intl.NumberFormat`을 사용한다. 삽입한 이름은 그대로 보존하고 React 텍스트로 출력하여 HTML로 해석하지 않는다.

한국어 항목이 실행 시 누락되면 같은 키의 영어 항목을 사용한다. 영어 기준 키 자체의 누락과 잘못된 인자 호출은 타입 검사 및 검증 실패로 처리한다. 영어 대체 동작을 위한 누락 테스트는 완전한 정식 사전과 분리한 테스트 데이터로 수행한다.

### 4. 화면 연결과 동작 식별자 분리

| 영역 | 적용 방식 |
| --- | --- |
| 헤더·모바일 메뉴·검색·정렬·칸반 | 표시 상수를 번역 키로 바꾸고 상태 값과 정렬 값은 유지한다. |
| 명세·상세·아이디어·설정 | 제목·버튼·입력 예시·안내·툴팁·접근성 이름을 번역하고 콘텐츠는 원문으로 렌더링한다. |
| 업무 공간 | 탭·단계·연결·충돌·검증·OpenSpec 제품 안내를 번역하고 작업 식별자와 요청 값은 유지한다. |
| 오류 화면 | 공통 제품 안내와 재시도 버튼을 번역하고 원본 오류 상세는 보존한다. |
| 공용 UI | 기본 닫기 이름 등 기본 제공 문구도 사전으로 연결한다. |

`WorkRoom`의 대화 정리 결과는 `user`·`assistant` 같은 내부 역할과 표시 이름을 구분한다. 스타일과 동작은 내부 역할로 판별하고 `나`·`Me`는 렌더링에만 사용한다. 탭·상태·정렬 분기도 번역한 문자열로 비교하지 않는다.

제품에서 생성하는 AI 요청용 문장, 문서 경로, 서버로 전송하는 명령과 인자는 화면 번역과 분리하여 기존 값을 유지한다. 클릭 후 대화 입력란에 준비하는 요청 문구도 AI 지시이므로 언어 선택에 따라 바꾸지 않는다.

### 5. 클래스 오류 경계와 비컴포넌트 코드

Provider를 기존 `App` 내부의 `ErrorBoundary`보다 위에 둔다. 클래스형 `ErrorBoundary`는 Context를 직접 소비하여 제목과 재시도 문구를 번역한다. 기존 사용자 정의 fallback의 props 계약은 유지한다. 오류 상세인 `error.message`는 원문으로 표시한다.

API 도우미와 비동기 처리에서 발생한 서버 오류를 번역 대상으로 다시 해석하지 않는다. 프런트엔드가 자체 생성하는 기본 오류는 번역 키 또는 안정적인 내부 구분값으로 전달하고 화면에서 번역한다. 문자열 내용 비교로 오류 종류를 추정하지 않는다. 백엔드 응답 형식은 변경하지 않는다.

### 6. 날짜·상대 시간 포맷

날짜 유틸리티는 선택 언어를 명시적으로 받아 `Intl.DateTimeFormat`을 사용한다. `IdeaDetailModal`의 직접 날짜 변환도 같은 경로로 모은다. 한국어는 `ko-KR`, 영어는 `en-US`를 표시 로캘로 사용하고 시간대 옵션은 지정하지 않아 기존 브라우저 시간대 의미를 유지한다.

상대 시간은 기존의 1분 미만·1시간 미만·1일 미만·7일 미만·그 이후 날짜 표시 경계를 유지한다. 1분 미만은 번역 사전의 ‘방금 전’ 문구를 사용하고 분·시간·일은 `Intl.RelativeTimeFormat`으로 표시한다. 계산과 테스트에서 기준 시각을 고정할 수 있게 한다. 날짜 형식 변경으로 원본 타임스탬프를 변환하여 저장하지 않는다.

### 7. 검증 경계

- 순수 언어 선택 테스트: 목록 순서, 지역 태그와 대소문자, 지원 언어 건너뛰기, 목록 부재·빈 목록, 단일 언어, 영어 기본값, 브라우저 정보 접근 실패.
- 번역 테스트: 두 사전의 키 일치, 영어 대체, 변수 값 보존, 개수 0·1·2, 번역 키나 미치환 값의 노출 방지.
- 표시 테스트: 초기 로딩과 HTML `lang`, 고정한 시각의 날짜·상대 시간 경계, 한국어·영어 주요 화면과 접근성 이름, 오류 경계.
- 업무 회귀 테스트: 원문 콘텐츠, API 상태 값, 사용자 메시지 스타일, 저장 충돌·초안 보존·메시지 전송과 AI 요청 값 유지. 기존 한국어 테스트는 테스트용 Provider에서 `ko`를 명시하고 영어 검증은 `en`을 명시한다. 브라우저 감지는 별도 테스트로 다룬다.
- 구현 후 프런트엔드 테스트·타입 검사·빌드·린트를 실행한다. 두 언어의 데스크톱·모바일 줄바꿈과 버튼 접근성은 최신 결정에 따라 사용자가 Microsoft Edge에서 직접 확인한다. 에이전트는 `tasks.md`의 기준에 따른 사용자 결과를 기록하며, 확인받기 전에는 브라우저 검증 미실시로 남긴다. browser-use 커넥터로 대신 확인하지 않는다.

## Risks / Trade-offs

- [여러 화면에 흩어진 고정 문구 누락] → JSX뿐 아니라 화면별 상수, 기본 오류, 공용 UI의 접근성 이름을 점검하고 두 언어의 대표 화면 테스트로 보완한다.
- [번역한 문자열을 업무 판별에 사용] → 역할·상태·정렬·작업 식별자를 유지하고 렌더링 단계에서만 번역한다.
- [영어 대체로 한국어 누락을 놓침] → 사전 완전성 검증을 실패 조건으로 유지한다.
- [긴 영어 문구의 모바일 배치 문제] → Edge에서 실제 좁은 화면을 확인하고 필요한 범위의 줄바꿈을 조정한다.
- [원문 서버 오류·AI 대화가 화면 언어와 혼재] → 명세에 정한 원문 보존 경계를 유지하고 주변 제품 안내만 번역한다.
- [사용자 정의 번역 계층 유지 비용] → 감지·사전·포맷·Context로 책임을 제한하고 범용 번역 엔진으로 확장하지 않는다.

## Migration Plan

언어 선택과 공통 번역 모듈을 먼저 구현한 뒤 화면·오류·날짜 표시를 연결하고 검증한다. 최종 배포에서는 두 언어 사전과 번역 적용 화면을 함께 제공한다. 데이터 마이그레이션과 백엔드 배포 순서 의존성은 없다.

회귀가 있으면 프런트엔드 변경과 함께 배포된 정적 파일을 이전 버전으로 되돌린다. 언어 설정을 저장하지 않으므로 별도 데이터 복구나 저장소 정리는 필요하지 않다.

제안서·명세·설계·작업 목록에 따른 구현과 사용자 직접 검증을 마쳤으며, 복구된 `final_implementation_review` 답변에서 사용자의 최종 검토 완료·업무 완료 승인을 확인했다. 기존 린트 문제 43건과 번들 크기 경고를 포함한 결과를 검토받았고, 상세 근거는 `tasks.md`에 기록했다. 이번에는 승인 이력만 반영하며 제품 코드를 수정하지 않는다. 추가 구현이 필요해지면 그 전에 사용자 문서 검토와 명시적 구현 지시를 다시 받는다. 변경 보관은 별도 요청 전까지 진행하지 않는다.
