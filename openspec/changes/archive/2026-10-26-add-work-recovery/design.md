# Design

## Context

원인은 proposal.md를 참고한다. 현재 `CodexService.resume`은 격리 공간 여부를 구분하도록 수정됐지만, 배포된 앱의 안내는 일반적인 재연결 버튼과 오류 문자열에 의존한다. 실제 재현 업무는 `baseline`만 있고 `executionPath`와 `isolated-baseline`이 없는 기존 공유 폴더 업무였다. 다른 Codex가 같은 대화를 소유하면 원래 ID의 재연결도 거절된다. 수동 복구 시 업무 단계의 임시 변경과 대화 점유 해제가 필요했으며, 제품 기능에서는 단계 변경이나 DB 직접 수정이 필요 없어야 한다.

## Goals / Non-Goals

**Goals:** 사용자가 업무 화면에서 원인을 구분하고 같은 대화로 안전하게 복구하며, 원래 업무 단계와 사용자 초안을 유지한다.

**Non-Goals:** 손상된 격리 공간의 내용을 재구성하거나 다른 Codex의 점유를 강제로 해제하지 않는다. 사용자 검토와 구현 시작을 대신하지 않는다.

## Decisions

### 1. 기존 재연결 경로를 확장한다

‘업무 복구’ 안내와 버튼이 기존 POST `/api/work/:id/reconnect`를 사용한다. GET 업무 응답에 복구 가능 여부·상태 코드·후속 동작을 추가한다. 진단은 파일 존재와 식별 검증 및 저장된 상태만 확인하며 Codex 실행을 시작하지 않는다. 복구 요청 시 저장된 최신 상태를 다시 확인한다. 실행·연결·질문·승인 대기 업무의 동시 재연결은 차단한다.

대안은 별도 복구 API를 만드는 방식과 오류 상태를 초기화하는 방식이다. 기존 API 확장은 중복 잠금·대화 복원 로직을 줄인다. 단순 초기화는 실제 연결 여부를 보장하지 못하므로 사용하지 않는다.

### 2. 격리 이력이 있는 업무는 엄격하게 검사한다

`executionPath` 또는 `isolated-baseline`이 있으면 기존 식별 검증을 통과한 경로만 사용한다. 두 정보가 모두 없는 기존 업무는 등록된 원본 프로젝트 경로로 대화만 복원한다. 기준 기록이 있는데 실행 경로가 없으면 손상으로 분류하며 원본 경로로 대체하지 않는다. 복구 과정에서 단계, reviewedVersion, 문서, 질문 답변을 변경하지 않는다.

### 3. 실패 원인과 재시도를 같은 화면에 제공한다

`legacy-workspace`, `workspace-unavailable`, `thread-in-use`, `session-restarted`, `thread-unknown`, 일반 연결 실패를 구분한다. 기존 공유 폴더 업무에는 대화 복구가 가능하다는 설명을, 실제 격리 손상에는 파일 복구 필요 안내를, 대화 점유에는 다른 Codex에서 해당 대화를 닫은 뒤 다시 시도하라는 안내를 제공한다. 복구 중 버튼을 비활성화하고 성공 시 최신 업무를 다시 읽어 오래된 오류를 제거한다. 서버의 원시 오류는 원인 확인이 가능하도록 보존하되 안내를 중복 표시하지 않는다. 한국어·영어를 지원한다.

### 4. 성공과 실패를 이력으로 남긴다

기존 재연결 이벤트에 복구 방식과 결과 코드를 기록한다. 같은 대화 ID를 유지하고 thread/start·turn/start를 호출하지 않는다. 실제 연결 성공 후에만 연결 오류를 지운다. 실패 시 재시도할 수 있고 작성 중인 대화·문서 초안은 유지한다.

## Risks / Trade-offs

- 파일 상태가 진단 후 바뀔 수 있음 → 복구 직전에 경로와 상태를 재검증한다.
- 오래된 앱과 새 앱이 서로 다른 서버를 사용할 수 있음 → 설치형·무설치판 모두 버전을 올리고 실제 산출물에 수정본이 들어 있는지 확인한다.
- 다른 Codex의 점유 → 앱은 강제 보관·종료하지 않고 사용자가 점유를 정리한 뒤 재시도하도록 한다.
- 손상 공간은 버튼만으로 복구 불가 → 가짜 성공이나 원본 프로젝트 덮어쓰기 없이 구체적인 제한을 안내한다.

## Migration Plan

DB 스키마 변경 없이 배포한다. 회귀 테스트·전체 빌드·격리 앱의 화면 검증 후 v0.1.3 설치 파일, blockmap, latest.yml, 무설치 ZIP, portable.json을 생성한다. 기존 릴리스를 덮어쓰지 않고 지정 GitHub 저장소의 새 태그·초안에 올려 파일 크기·해시·메타데이터와 소스 커밋을 확인한 뒤 게시한다. 기존 배포 소스와 작업 중인 변경을 구분하여 검증한 배포 소스만 커밋한다. 현재 앱은 사용자 질문·승인·실행을 중단하지 않는다. 문제 발생 시 새 버전을 최신 배포로 안내하지 않고, 기존 사용자 데이터와 설치 폴더 백업을 보존해 수동 복원한다.
