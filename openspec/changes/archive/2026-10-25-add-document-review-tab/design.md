# Design

## Context

동기는 proposal.md를 따른다. DetailModal은 Proposal / Specs / Tasks / Design을 표시하며 실제 주 작업 화면인 WorkRoom은 문서 편집과 질문·답변을 관리한다. WorkService는 문서 버전 해시와 경로 제한을 제공하고 LegacyService는 파일 변경을 SSE로 알린다. 별도의 검토 항목 저장소는 없다.

## Goals / Non-Goals

**Goals:** 두 화면에서 동일한 추출 결과를 제공하고 문서 변경·저장 충돌·미저장 편집 보호와 함께 동작한다.

**Non-Goals:** 자연어 의미 추론, 항목별 승인 워크플로, 질문 저장소 통합, 기존 문서 일괄 수정.

## Decisions

### 1. Markdown 안의 명시적 규약을 기준으로 한다

일반 목록 항목의 시작에 `[review:confirm]`, `[review:assumption]`, `[review:decision]`, `[review:choice]` 중 하나를 붙인다. 예: `- [review:confirm] 비회원도 조회할 수 있는지 확인`. 여러 줄 본문은 해당 목록 항목의 하위 블록으로 포함한다. 코드 블록·인라인 코드·HTML 주석 안의 문자열은 추출하지 않는다. Markdown 구문 트리의 목록 항목과 원문 위치를 이용한다.

본문에서 의미를 추론하는 방법은 결과가 재현되기 어렵고, 별도 JSON 문서는 원문과 동기화해야 하므로 채택하지 않는다. 기존·수동 문서도 규약을 사용하면 동일하게 처리하며, 규약 없는 문서는 항목 없음으로 남긴다. 생성 AI의 계획 작성 지침과 사용자 안내에 규약을 추가하고 이전 문서에 소급 표기를 자동 삽입하지 않는다.

### 2. 조회 시 계산하고 승인 상태를 추가하지 않는다

공통 추출 서비스를 만들고 변경 상세에서 사용하는 `GET /api/changes/:id/review-items`와 업무 화면의 `GET /api/work/:id/review-items`가 같은 서비스를 사용한다. 기존 매개변수 계약을 변경하지 않는 추가 경로다. 결과는 `items`, `documentVersions`, `errors`를 포함한다. 항목은 `path`, `startLine`, `endLine`, `kind`, `text`와 문서 버전 기반 식별자를 갖는다. 식별자는 UI용이며 영속 승인 키가 아니다. 문서 경계 검증은 기존 within 및 허용 문서 목록을 재사용한다.

별도 DB에 항목을 복제하지 않아 문서 삭제·이름 변경 뒤 잔여 항목이 남지 않는다. 일부 읽기 실패는 `errors`로 명시하며 경로 자체가 잘못된 요청은 거부한다.

### 3. 원문 이동과 갱신

문서별·원문 순서로 그룹화하고 종류를 한국어 배지로 표시한다. 선택 시 DetailModal은 해당 문서 탭과 위치로 이동하고 WorkRoom은 기존 문서 이동 보호를 거쳐 에디터 위치로 이동한다. 문서 버전이 달라지면 목록을 다시 불러온 후 위치를 결정한다. 기존 SSE와 문서 저장 성공 알림에 재조회를 연결한다. 요청 실패 시 오류·재시도를 표시하고 이전 목록은 최신 결과로 오인하지 않게 표시한다.

## Risks / Trade-offs

- 명시적 표기가 없는 검토 항목은 표시되지 않음 → 빈 상태에 규약과 예제를 안내하고 생성 지침을 통일한다.
- 편집으로 줄 번호가 바뀜 → 항목에 문서 버전을 포함하고 원문 이동 전 버전을 대조한다.
- 두 화면에서 동작이 달라질 위험 → 추출 서비스와 표시 컴포넌트를 공유하고 원문 이동만 화면별로 연결한다.

## Migration Plan

1. 추가 API와 추출 서비스를 배포한 뒤 두 화면과 생성 지침을 연결한다. 문서·DB 마이그레이션은 없다.
2. 규약 없는 기존 문서, 코드 예제, 파일 수정, 접근 실패 및 미저장 초안을 테스트한다.
3. 회귀 시 새 탭과 추가 API를 되돌린다. 문서의 표기는 일반 Markdown 텍스트로 보존된다.
