# Design

## Context

문제와 기능 범위는 `proposal.md`를 따른다. 현재 폴더는 OpenSpec 설정·아이디어만 있는 상태이며 앱 소스와 Git 저장소가 없다. `127.0.0.1:13000`은 별도로 설치된 `openspec-ui.exe`가 서비스한다. 기존 서버 API로 프로젝트 등록과 아이디어 조회·생성·수정을 확인했다.

참고 원본은 React/TypeScript/Tailwind 프런트엔드와 Rust/Axum 백엔드, 파일 감시·SSE로 구성된다. 원본 `backend/src/main.rs`에는 프로젝트·아이디어·변경 조회 라우트가 있고, `parser.rs`는 OpenSpec 파일에서 상태를 계산한다. 세션 관리·일반 문서 저장·Codex 실행은 새로 추가할 영역이다. 현재 설치된 Codex는 `0.163.0-alpha.11.2`이며 app-server 명령과 프로토콜 스키마 생성 명령을 제공한다. 실행·인증 연동 자체는 아직 검증하지 않았다.

## Goals / Non-Goals

**Goals:**
- 업무 식별자, 프로젝트 경로, OpenSpec 변경, Codex 대화 식별자의 연결을 영속화한다.
- 같은 업무의 대화·질문·문서·실행 결과를 하나의 화면에서 다루고 재접속으로 맥락이 끊기지 않게 한다.
- Markdown/YAML을 OpenSpec 문서의 기준으로 유지하고 실행 상태와 검증 근거를 별도로 관리한다.

**Non-Goals:**
- Codex 이외 도구를 고르는 UI나 범용 다중 공급자 계층은 만들지 않는다.
- 단계마다 새 Codex 대화를 만들거나 자동으로 대화를 분기하지 않는다.
- 기존 설치 프로그램과 다른 프로젝트의 소스를 이번 계획 단계에서 교체하지 않는다.

## Decisions

### 1. React UI 재사용과 NestJS 백엔드 구현

사용자 지정에 따라 백엔드는 NestJS/TypeScript로 구현한다. 원본 React/TypeScript 프런트엔드를 현재 프로젝트의 `frontend/`에 도입하고 NestJS 서버는 `backend/`에 구성한다. 원본 서버는 API와 파일 형식의 참고 자료로 사용하며 새 앱 실행에 Rust나 Cargo를 요구하지 않는다. 구현 시 원본 커밋·출처와 재사용 코드의 MIT 라이선스를 기록하고 기존 OpenSpec 파일을 보존한다.

React UI를 재사용하고 기존 API의 경로·상태 코드·응답 필드·오류 형식을 NestJS로 이식하여 UI 변경 범위를 줄인다. 프로젝트 설정 파일과 아이디어 frontmatter, 변경·작업 통계·명세 파싱을 원본 데이터 예제로 검증한다. Rust 서버 유지안은 사용자 지정으로 제외하고, 프런트엔드 전면 재작성이나 별도 실행 서버 추가는 초기 범위에 필요하지 않아 채택하지 않는다.

NestJS의 Controller는 DTO 검증과 HTTP 응답을, Service는 업무 로직을 담당한다. 프로젝트·아이디어·OpenSpec 파일·업무·Codex·문서·검증·이벤트를 기능 모듈로 분리하고 저장소와 프로세스 연결은 Provider로 주입한다. Node.js 파일 API로 읽기·저장을 수행하고 파일 감시 이벤트를 중복 정리한 뒤 SSE로 전달한다. SSE 구독 해제가 Codex 실행을 종료하지 않도록 연결 수명과 업무 실행 수명을 분리한다. 서버 종료 시에는 감시자·SSE·자식 프로세스·저장소를 정리하고 다음 시작에 업무를 복원한다.

| 구성 | 책임 | 주요 의존성 |
| --- | --- | --- |
| React 보드·OpenSpec 모듈 | 프로젝트·아이디어·변경 표시와 TypeScript 파일 파싱·상태 계산 | 기존 API 계약, OpenSpec 파일 |
| 업무 서비스 | 업무 전환, 단계·검토·완료 조건, 중복 요청 제어 | 저장소, OpenSpec 명령 래퍼 |
| Codex 연결 | 프로세스·요청·이벤트·대화 복원·질문 응답 | 로컬 Codex app-server |
| 문서 서비스 | 경계 검사, 버전 비교, 원자 저장, 변경 이력 | 파일 시스템 |
| 실행·검증 서비스 | 실행 상태, 변경 파일, 검증 결과와 최신성 | Codex 이벤트, 파일 상태 |
| 작업 화면 | 대화·질문, 문서 편집, 실행 결과를 같은 업무로 표시 | 업무 API, SSE |

### 2. 하나의 업무는 하나의 영속 Codex 대화

NestJS의 Codex Service가 Node.js `child_process.spawn`으로 `codex app-server`를 실행하고 stdio JSON 메시지로 연결한다. 실행 파일과 인자를 분리하고 셸 해석을 사용하지 않으며 Windows에서는 숨김 실행 옵션을 적용한다. 초기 연결을 완료한 뒤 새 업무에만 대화를 생성하고 반환된 대화 ID를 즉시 저장한다. 단계가 바뀔 때 같은 대화에 후속 턴을 추가한다. 서버 재시작 시 저장된 대화 ID로 복원한다. UI가 보는 업무 세션은 앱의 영속 레코드이며 프로세스 수명이나 한 번의 턴과 다르다.

공식 문서의 `thread/start`, `thread/resume`, `turn/start`를 기본 흐름으로 사용한다. 고정된 모델명을 지정하지 않고 사용 가능한 Codex 기본 설정을 따른다. 설치된 버전의 생성 스키마에 맞춰 필드와 지원 기능을 확인한다. 셸 명령으로 매번 독립 실행하는 방법은 대화 유지와 질문 응답 요구를 충족하기 어렵기 때문에 채택하지 않는다.

대화 생성 요청의 결과를 받기 전에 연결이 끊겼다면 새 대화 생성을 자동 재시도하지 않는다. 생성 중·복구 필요 상태로 남겨 생성 결과를 대조한다. 단계 전환과 후속 실행에서 `thread/start`가 다시 호출되지 않는 것을 테스트한다. 인증 오류나 복원 실패 시 기존 ID를 보존하고 재시도하며 새 대화로 대체하지 않는다.

### 3. 업무 상태는 SQLite, 문서는 원본 파일

서버가 사용하는 로컬 데이터 디렉터리에 SQLite 저장소를 두고 다음 정보를 관리한다. 문서 본문 전체를 데이터베이스와 파일에 이중 기준으로 저장하지 않는다. Git이 없는 프로젝트도 지원하며 코드 차이 기준은 업무 시작 시 파일 스냅샷, Git이 있으면 기준 커밋과 파일 상태를 함께 기록한다.

| 데이터 | 주요 값 |
| --- | --- |
| 업무 | ID, 프로젝트 ID·정규 경로, 변경명, 출처 아이디어, 단계, 실행 상태, Codex 대화 ID |
| 요청 | 멱등 키, 동작, 상태, 결과 ID; 전송 결과 불명확 상태 포함 |
| 이벤트 | 업무 ID, 증가하는 순번, 종류, 턴·항목 ID, 표시 내용 |
| 질문·결정 | 질문 ID, 요청 ID, 필수 여부, 답변·전달 상태, 반영 문서·버전 |
| 문서 이력 | 경로, 저장 전후 해시, 저장 주체, 시각, 이전 내용 참조 |
| 실행·검증 | 턴 ID, 실행 상태, 명령·종료 상태·출력, 대상 파일 해시, 판정 |
| 검토 | 계획 문서 해시 집합과 사용자 검토 시각 |

단계는 아이디어 구체화·계획 작성·계획 검토·구현·검증·완료·보관으로 구분한다. 실행 상태는 유휴·실행 중·답변 대기·승인 대기·중단·실패·복구 필요로 따로 관리한다. 기존 보드의 상태 계산을 완료 판정으로 사용하지 않는다. 체크박스가 모두 체크되어도 검증·사용자 확인이 없으면 업무 완료가 아니다.

### 4. 통합 화면과 API

보드의 업무를 열면 상단에 단계와 다음 동작을 표시하고, 대화·확인 질문, 문서 편집·미리보기, 실행·코드 차이·검증 결과 영역을 제공한다. 좁은 화면은 같은 업무 내 탭으로 표시한다. 단계마다 별도 채팅 화면을 열지 않는다.

문답은 전체 흐름에 걸쳐 제공한다. 사용자는 AI가 먼저 질문하지 않아도 언제든 질문·수정 의견을 입력하고 현재 문서 또는 결과물에 연결할 수 있다. AI 초안이나 구현 결과가 나오면 결과 확인 → 질문·답변·수정 요청 → 반영 결과 확인을 같은 세션에서 반복한다. 구현 중 요청은 기존 실행 잠금·지시 대기열 규칙을 따르고 완료 검토 중 수정은 필요한 재검토·재검증으로 돌아간다. 문답과 결과 생성 자체는 구현 시작 또는 최종 완료 확인을 대신하지 않는다.

업무에 관련된 OpenSpec 정보는 다음 CLI 계약을 연결한다. 기능 유무는 실행 버전에서 확인하며 실패나 미지원을 빈 정상 결과로 표시하지 않는다. 전역 설정·스키마 편집·저장소 관리 전체를 초기 UI에 포함하지 않는다.

| 화면 정보·동작 | OpenSpec 연결 |
| --- | --- |
| 산출물 상태·의존성·차단 원인 | `status --change <name> --json` |
| 다음 작성 단계·작성 지침·구현 또는 보관 지침 | `instructions <artifact-or-action> --change <name> --json` |
| 적용 워크플로·산출물 구성 | `schemas --json` 및 변경 상태 |
| 기준 명세·변경 명세·요구사항 차이 | `list --specs`, `show --type spec`, `show --type change --deltas-only --json`, `show --type change --diff` |
| 문서 검증·오류 위치 | `validate <name> --strict` |
| 프로젝트·명세 관계 진단 | `doctor --json`와 `context --json` |
| 명세 반영·보관 | 같은 대화의 OpenSpec 작업 흐름과 보관 명령; 실행 결과와 파일 변경 확인 |

CLI의 상태·검증은 문서 구조와 명세 관계에 관한 결과이며 코드 테스트의 성공을 뜻하지 않는다. 문서에 관한 질문이나 수정 요청은 이 결과와 대상 파일을 현재 대화에 전달한다.

다음 API는 제안 계약이며 기존 API와 함께 제공한다.

| 동작 | 계약 |
| --- | --- |
| 아이디어 전환·업무 열기 | 업무 생성은 출처 아이디어 ID와 멱등 키를 받고 기존 업무를 재사용한다 |
| 대화·단계 동작 | 업무 ID로 메시지·계획 작성·검토·구현·중단·재개 요청을 받는다 |
| 질문·승인 응답 | 업무 ID와 서버 요청 ID를 검증하고 이미 해결된 요청을 거부한다 |
| 문서 읽기·저장 | 본문과 해시 버전을 반환하고 저장은 기준 버전을 요구한다 |
| 실행 결과·검증·완료 | 결과와 관련 파일 버전을 반환하고 완료 조건을 서버에서 검증한다 |
| 이벤트 구독 | 업무 ID와 마지막 순번 이후 이벤트를 SSE로 보내고 연결 복구 시 중복을 제거한다 |

사용자 입력은 셸 문자열로 합치지 않는다. Codex 및 OpenSpec 실행은 명령과 인자 배열을 분리한다. 로컬 전용 주소에 바인딩하고 쓰기 API의 Origin을 검증한다. 프로젝트 경로는 등록된 루트로 고정하며 문서 서비스는 실경로와 심볼릭 링크를 검사한다.

### 5. 질문과 답변은 실제 Codex 요청에 대응

지원 버전의 사용자 입력 요청을 질문 카드로 변환하고 원래 요청 ID로 답변한다. 설치 버전의 실험적 스키마에서 확인한 `dynamicTools`로 최초 대화에 `ask_user`를 등록해 문서를 쓸 수 있는 기본 모드에서도 모든 단계의 질문을 지원한다. `item/tool/call` 응답은 `contentItems`·`success` 형식을 따른다. 내장 `item/tool/requestUserInput`도 처리한다. 요청 기능이 지원되지 않으면 연결 오류를 표시하며 임의로 지원한다고 처리하지 않는다. 일반 대화에서 발생한 질문에는 같은 대화의 후속 메시지로 답변할 수 있다.

사용자 답변은 먼저 저장하고 전송 결과를 기록한다. 결과가 불확실하면 자동 재전송하지 않고 서버 요청 상태를 확인한다. 앱의 영속 질문 ID와 일시적인 프로토콜 요청 ID를 구분한다. 프로세스 재시작으로 요청이 무효가 되면 미답변 질문을 보존하고 같은 대화에 재질문을 요청한다. 뒤늦은 응답을 새 요청에 대신 적용하지 않는다.

결정된 내용을 문서에 반영했는지는 변경 파일과 저장 해시로 확인한다. Codex 권한 승인과 요구사항 답변은 서로 다른 동작으로 유지한다. 지원 프로토콜을 넘어 승인 규칙을 우회하지 않는다.

### 6. 문서 저장과 동시 수정

문서 작성·수정은 대화와 편집기를 함께 사용하는 반복 과정이다. 수정 요청과 답변에 대상 문서 경로·기준 해시를 연결하고 반영 후 변경 내용과 최신 버전을 보여준다. 사용자가 의견을 더 내면 같은 대화에서 수정을 계속하며, 최신 버전의 문서 검토 완료와 구현 시작을 명시적으로 선택해야 구현으로 전환한다.

문서 읽기 시 해시 버전을 함께 반환하고 저장 직전 다시 읽어 비교한다. 버전이 다르면 충돌 응답을 반환하고 UI에서 최신 파일과 미저장 초안을 비교한다. 저장은 임시 파일 작성 후 교체하며 실패 시 원본을 유지한다. 파일 감시 이벤트가 오면 편집기가 깨끗한 경우에만 자동 갱신한다.

미저장 편집이 있으면 AI 수정 요청 전에 저장·폐기·요청 취소를 선택하게 한다. 저장된 최신 문서 경로와 해시를 같은 Codex 대화에 전달한다. 구현 이후 계획이 수정되면 기존 검토를 무효화한다. 이미 실행 중인 작업은 충돌 가능성을 표시하고 추가 실행 및 완료는 재검토 전까지 막는다.

### 7. 실행·검증·보관

업무마다 실행 잠금을 두고 중복 실행을 막는다. 추가 지시는 지원되는 실행 중 지시 기능을 사용하거나 표시된 대기열에 넣는다. 중단은 현재 턴에 요청하고 중단 확인 전에는 재개하지 않는다. 이벤트 누락이나 프로세스 종료 시 실제 Codex 상태를 확인하여 실행 상태를 복구하고 결과가 불명확하면 복구 필요로 표시한다.

검증 항목은 프로젝트에서 확인한 실제 명령과 명세 시나리오로 구성한다. 코드·명세 해시와 실행 결과를 연결하고 변경 시 과거 검증을 무효화한다. 성공 이벤트 자체를 검증 통과로 간주하지 않는다. 문서 검토·필수 질문·작업 목록·검증 최신성·사용자 완료 확인을 검사한 뒤 완료 처리한다. 명시적 보관 요청은 OpenSpec CLI로 수행하고 반환 상태 및 파일 결과를 확인한다.

### 8. 이번 아이디어의 승격

이 변경의 계획 검증이 끝나면 현재 목표 원본 4개를 `source-ideas/`로 이동하여 보존하고, 보드에서 하나의 Todo로 표시되게 한다. 출처 ID는 제안서에도 기록한다. 후속 도구 선택 아이디어는 `openspec/ideas/`에 남긴다. 이는 이번 계획 자료의 이동이며, 향후 제품의 업무 세션 기능이 이미 구현되었다는 의미는 아니다.

## Risks / Trade-offs

- Codex 버전에 따른 프로토콜 차이 → 설치 버전 스키마와 기능 확인, 미지원 기능의 명시적 오류, 어댑터 계약 테스트.
- 질문·실행 요청 도중 연결이 끊겨 결과 불명확 → 멱등 키·전달 상태·기존 대화 대조, 자동 중복 실행 금지.
- 수동 편집과 AI 쓰기의 경쟁 → 해시 기반 충돌 처리, 초안 보존, 파일 감시 및 재검토 상태.
- 로컬 실행의 파일 접근 범위 → 등록 프로젝트 실경로 고정과 Codex 기본 실행 제한·승인 연동.
- 원본 보드와 업무 완료 판정의 차이 → 기존 읽기 상태와 업무 검증 상태를 분리하여 표시.
- Rust에서 TypeScript로 이식하면서 발생할 파싱·응답 차이 → 기존 설정·Markdown/YAML 예제를 고정한 API 계약 및 회귀 테스트로 확인.
- 통합 범위가 큼 → 작업 목록의 단계별로 통합하되 마지막에 동일 세션 전체 흐름을 실제 확인.

## Confirmed Review Decisions

- 2026-10-24 사용자 확인: 아이디어부터 검증·완료 검토까지 모든 단계에서 AI와 문답하며 문서 또는 결과물을 수정한다.
- 단계 전환·새로고침·서버 재시작 후에도 같은 Codex 대화를 유지한다.
- 문서 검토 후 사용자가 구현 시작을 결정하고 검증 결과 확인 후 최종 완료를 결정한다.
- 작업 화면에 업무와 관련된 OpenSpec 진행 정보·명세 비교·검증·진단을 추가한다.
- 초기 범위는 Codex 기본 사용·NestJS 백엔드·React UI 재사용을 유지한다. AI 도구 선택과 Markdown 뷰어 고도화는 별도 후속 아이디어로 남아 있다.

## Migration Plan

1. 구현 시작 후 원본 커밋을 고정하여 React 프런트엔드를 도입하고 NestJS 백엔드를 생성한다. 기존 OpenSpec 자료를 보존하며 원본 서버는 계약·파일 파싱의 참고 자료로 사용한다.
2. 별도 개발 포트와 별도 테스트 저장소로 기능을 구현·검증한다. 13000의 기존 설치본은 유지한다.
3. 프로젝트 설정을 복사해 읽기 호환성을 확인하고, 실제 Codex로 동일 대화의 전체 흐름을 검증한다.
4. Microsoft Edge의 사용자 설치 ChatGPT 확장으로 UI 검증을 수행한다. 연결 불가 시 미검증으로 보고한다.
5. 새 앱 전환 전 설정·SQLite·OpenSpec 파일을 백업한다. 문제 발생 시 새 앱을 중지하고 기존 설치본으로 되돌린다. AI가 변경한 코드와 문서는 명시적 검토 없이 자동 되돌리지 않는다.
