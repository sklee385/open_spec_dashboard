# Design

## Context

동기는 proposal.md를 따른다. `ExecutionService.baseline()`은 최초 구현 시작 시 기준을 한 번 저장하고 `changes()`는 매번 현재 폴더와 비교한다. Git HEAD는 부가 정보로만 저장된다. 스냅샷은 심볼릭 링크와 `.git`, `.data`, `.reference`, `.tools`, `.logs`, `.idea-trash`, `node_modules`, `dist`, `.nuxt`, `.output`, `*.tsbuildinfo`를 제외하고, 200,000바이트 미만이며 NUL이 없는 파일만 텍스트를 저장한다. `tasks.md` 체크박스 표시는 해시 계산에서 정규화한다.

`WorkRoom` 결과 탭과 `FileChange`·`FileDiff`에 목록, 줄 단위 차이, 문맥 펼치기, 전체 코드 보기가 이미 있다. 따라서 새 diff 도구보다 저장 수명과 데이터 의미를 보완한다. 현재 파일 부재와 수집 불가가 모두 `null`로 표현되어 구분이 필요하다.

## Goals / Non-Goals

**Goals:** 업무 실행을 분리해 다른 업무의 변경을 제외하고, 완료 결과를 재시작·보관 이후에도 재현하며, 수집 실패와 빈 변경을 명확하게 구분한다.

**Non-Goals:** Git 조작, 충돌 자동 병합, 도구별 작성자 판별, 바이너리 렌더링, 과거 완료 결과 추정 복원.

## Decisions

- 완료 시점 보존은 사용자 선택이다. 최초 구현 시작 직전 기준과 사용자 완료 확인 시점의 결과를 보존한다. 현재 파일 비교 방식은 과거 결과가 바뀌고, Git 커밋 비교 방식은 미커밋·Git 미사용 프로젝트를 별도로 처리해야 하므로 채택하지 않는다.
- 기존 결과 탭과 `FileDiff`를 확장해 검증 결과와 함께 보여준다. 이번 순차 검토의 ‘기존 결과 탭 유지’ 답변을 제안서와 동일하게 반영한다.
- 복구된 사용자 결정은 ‘이 업무 변경만 표시’이다. 공유 프로젝트의 기간 차이를 업무 결과로 사용하는 초안을 폐기한다.
- Git 유무와 미커밋 변경을 동일하게 다루기 위해 구현 시작 직전 프로젝트의 독립 복사본을 업무별 관리 폴더에 만든다. 기준 생성 전의 기존 변경은 초기 상태에 포함되며 업무 변경으로 표시하지 않는다. Git worktree는 Git 없는 프로젝트와 미커밋 파일 처리가 달라 채택하지 않고, 파일명·Codex 도구 이벤트만으로 필터링하는 방법은 셸 명령 및 동일 파일의 병행 수정을 구분할 수 없어 채택하지 않는다. 업무 전용 복사본 방식은 앞선 `revised_plan_review` 답변에 따라 유지한다.
- 계획 대화는 원본 위치를 유지하고, 구현·재개·검증은 해당 업무 전용 폴더에서 수행한다. 기존 Codex 대화의 실행 위치를 안전하게 바꿀 수 없는 경우 실행을 중단하고 복구를 요구하며 원본 폴더에서 대신 실행하지 않는다. 구현 시점의 계획 버전과 전용 폴더의 계획 버전을 대조하고 계획 변경 시 기존 재검토 절차를 적용한다. 앞서 검토한 업무별 실행 격리의 동작을 유지한다.
- 원본 반영은 사용자가 결과를 확인한 뒤 별도로 요청한다. 사용자는 이번 순차 검토에서 ‘별도 반영 요청’을 선택했다. 업무 변경 경로에 한해 기준 해시와 원본 해시를 비교하며, 원본이 기준 또는 반영하려는 결과와 같을 때만 추가·수정·삭제한다. 충돌 시 경로를 안내하고 완료를 막는다. 서로 다른 파일의 병행 변경은 유지한다. 원본 전체를 복사본으로 교체하지 않는다.
- 기존 수집 제외 규칙과 텍스트 크기 한도, tasks 체크박스 정규화를 유지한다. 사용자는 이번 순차 검토에서 ‘기존 규칙 유지’를 선택했다. 결과 화면에 제외 범위와 정규화 규칙을 안내한다. 규칙 변경은 이번 범위에 포함하지 않는다.
- 새 저장 결과는 버전, 업무 ID, 시작·종료 시각, 수집 정책 버전, 파일별 경로·상태·전후 해시·내용·가용성 이유를 갖는다. 파일 부재, 텍스트 존재, 바이너리, 크기 제한, 과거 기록으로 원인 불명을 구분한다. 동일한 파일은 완료 결과에 중복 저장하지 않는다.
- 원본 경로와 실행 경로를 별도로 저장한다. 관리 폴더는 원본의 수집 트리 밖에 두고 심볼릭 링크·하드링크로 원본 파일을 공유하지 않는다. 실행 권한은 업무 폴더를 기준으로 제한한다. 의존성·전용 런타임은 전용 폴더에서 준비하며, 원본으로 빠지는 링크나 준비 실패 시 실행을 차단한다. 전용 폴더가 없거나 식별 정보가 다르면 원본으로 대체하지 않는다.
- 완료 요청은 기존 계획 검토·미답변 질문·작업 목록·검증 조건을 그대로 확인한다. 종료 스냅샷을 한 번 수집하고 그 상태에 대해 검증 신선도를 확인한 뒤, 완료 결과 기록과 업무 완료 상태를 동일한 SQLite 트랜잭션으로 확정한다. 실패 시 둘 다 반영하지 않는다. 재시도는 업무별 고정 기록 키로 중복 결과를 방지한다.
- 실행 중에도 업무 전용 폴더만 비교하며 ‘현재 변경’으로 구분한다. 완료·보관 상태에서는 저장된 결과만 읽는다. 결과가 없는 과거 완료 업무는 기록 없음으로 처리한다. 이전 공유 폴더 기준은 업무 귀속 근거로 사용하지 않는다. 이미 구현 중인 기존 업무는 격리 기록 없음으로 표시하고 명시적 전환 전까지 이 업무만의 결과 확정을 막는다.
- 원본 반영은 경로별 백업과 반영 저널로 복구 가능하게 수행하고, 쓰기 직전 원본을 재확인한다. 부분 실패는 완료로 처리하지 않고 반영된 경로와 복구 상태를 안내한다. 재시작 시 저널로 복구하고, 반영 이후 업무 결과가 바뀌면 다시 검증·반영해야 한다. 검증한 전용 폴더 결과, 원본 반영 결과, 완료 저장 결과의 해시가 같아야 완료한다. 파일 반영과 SQLite 저장은 단일 트랜잭션이 아니므로 별도 단계로 처리한다.
- 완료 결과 조회는 프로젝트 폴더를 다시 읽지 않는다. 보관이나 폴더 이동에도 저장 결과와 업무 ID 연결을 유지한다. 저장된 텍스트는 기존 React 텍스트 렌더링으로 표시한다.

## Risks / Trade-offs

- 복사 용량과 실행 환경 준비 비용 증가 → 업무별 독립 복사본을 재사용하며 원본에 대한 링크 공유를 금지한다. 완료 결과 저장 전에 작업 폴더를 정리하지 않는다. 자동 삭제는 이번 범위에 포함하지 않는다.
- 같은 파일의 병행 수정 → 반영 시 충돌을 표시하고 자동 병합·덮어쓰기를 금지한다. 동일 폴더의 직접 수정과 업무 실행을 분리한다.
- 스냅샷 수집 중 외부 수정 → 수집 전후 파일 메타데이터·해시 변화를 검사하고 불안정하면 완료를 확정하지 않는다. 외부 프로세스와 원자적인 전체 폴더 캡처까지 보장하지는 않는다.
- 저장 용량 증가 → 완료 결과는 변경 파일만 저장하고 기존 내용 제한을 유지한다. 저장 실패를 빈 변경으로 반환하지 않는다.
- 과거 데이터에 시각·내용 미수집 이유 없음 → 기존 기준은 보존하고 알 수 없는 값은 ‘기록 없음’으로 표시한다. 이력이 없는 완료 업무는 복구된 것처럼 제시하지 않는다.
- nullable 내용 오해 → 파일 존재와 가용성 필드를 분리하고 비교 불가인 쪽을 빈 문자열로 diff하지 않는다. 실제 빈 파일과 추가·삭제 파일은 정상 비교한다.

## Migration Plan

새 기록 종류와 버전, 원본・실행 경로, 격리 기준, 반영 저널을 추가하며 기존 기록은 읽기 호환한다. 과거 공유 폴더 기록은 귀속을 보장하지 못하므로 이 업무만의 완료 결과로 표시하지 않는다. API는 기존 `changes` 필드를 유지하면서 출처·시각·가용성·격리 여부·반영 상태를 확장한다. 롤백 시 새 기록과 작업 폴더를 삭제하지 않고 진행 중 반영을 복구한 뒤 실행을 중단한다. 구버전에서는 업무별 격리와 고정 결과 보장이 사라지므로 배포 문서에 표시한다.

검증은 두 업무의 서로 다른 파일·동일 파일 변경, 원본 선행 미커밋 변경, 실행·재개·검증 위치, 반영 충돌·중단·복구, 완료 후 파일 변경・재시작・보관, Git 미사용, 수집 및 저장 실패, 반복 완료 요청, 빈 파일과 내용 미수집, 기존 기록 호환을 포함한다. 사용자의 후속 지시에 따라 화면 검증은 브라우저 대신 OpenSpecBoard Windows 앱에서 수행한다.
