# Design

## Context

대상은 사용자가 확인한 현재 OpenSpecBoard다. 사용자의 최신 지시에 따라 Windows x64만 배포 대상으로 하며 macOS와 Edge 화면 검증은 제외한다. 배포 저장소는 현재 Git 원격 저장소 `sklee385/open_spec_dashboard`다. 동기는 [proposal.md](proposal.md)를 참고한다. 사용자는 최신 계획 문서를 검토하고 구현 시작을 명시적으로 지시했다. 구현과 검증 결과는 별도 사용자 검토를 받아야 한다.

현재 React/Vite 화면은 13001, Node API 게이트웨이는 13002, 대화·질문을 소유하는 별도 세션 서버는 13003을 사용한다. `backend/src/work/store.ts`는 `node:sqlite`와 `DATA_DIR`를 사용한다. 설정은 `LegacyService`의 `CONFIG_PATH`로 지정한다. `OpenSpecService`는 설치된 OpenSpec CLI를 `process.execPath`로 실행하며 `runtime.ts`는 개발 저장소의 `.tools/node-runtime`을 찾는다. 따라서 창만 감싸는 것으로 설치형 실행이 완성되지 않는다.

## Goals / Non-Goals

**Goals:**
- 기존 React 화면과 업무 API를 재사용하고 설치 후 필요한 프로세스를 앱이 준비한다.
- 버전별 실행 파일과 영속 데이터를 분리하고 기존 웹 환경과 공존한다.
- 업무를 보호하는 종료·업데이트 경계를 하나로 관리한다.

**Non-Goals:**
- 웹 개발 서버를 설치형 앱의 실행 요건으로 삼지 않는다.
- 앱 업데이트로 Codex나 외부 AI CLI, 사용자 프로젝트를 교체하지 않는다.
- 강제 업데이트, 자동 다운그레이드와 범용 DB 롤백 엔진은 제공하지 않는다.

## Decisions

### 데스크톱 실행 계층

- Electron + electron-builder + electron-updater를 권장 구성으로 둔다. Windows NSIS 설치 및 업데이트 산출물을 사용한다.
  - 현재 React와 Node 코드를 재사용하고 GitHub Releases 배포에 연결한다.
  - Tauri + Node 보조 프로세스는 Rust 및 별도 런타임 관리가 추가된다. 웹 실행기는 기존 서버 의존이 남는다.
  - 이후의 구현 작업 분해는 Electron 권장안을 전제로 하며 다른 선택이면 관련 문서를 함께 수정한다.
- Windows x64 사용자별 설치를 배포 대상으로 한다.
- Windows 트레이 상태 아이콘을 제공한다. 창 닫기는 백그라운드로 숨기며 명시적 종료는 업무 유휴 상태에서만 허용한다.
- 최소 OS는 사용자 답변에 따라 선택 런타임의 지원 범위로 정한다. Electron 45.0.0과 동봉 Node 24.15.0 기준 Windows 10 이상 x64를 대상으로 한다. 최소 OS에서의 실제 검증과 지원표 기준 범위는 구분한다.

메인 프로세스는 창·트레이·단일 인스턴스·서비스 수명·업데이트를 관리한다. 렌더러에는 Node를 노출하지 않고 `contextIsolation`, sandbox, 최소 preload API를 적용한다. IPC 발신자와 입력을 검증하고 임의 파일/셸 실행 인터페이스를 만들지 않는다. 외부 이동은 제한된 시스템 브라우저 열기로 처리한다.

업데이트 IPC는 소유 업데이트 창의 정확한 메인 프레임과 로컬 페이지 URL을 모두 확인한다. 같은 URL이어도 하위 프레임은 허용하지 않는다. preload는 상태·확인·설치의 고정된 세 채널만 노출하며 임의 채널·파일·명령을 전달하지 않는다. 인증 헤더는 앱 출처 필터와 대시보드 WebContents ID로 한정한다.

### 런타임과 통신

앱에 Windows x64 Node 실행 파일, 백엔드 빌드 및 OpenSpec CLI의 실행 의존성을 동봉한다. `node:sqlite` 지원을 Windows 패키지 상태에서 검증한다. AI CLI는 사용자의 설정된 실행 경로·인증을 사용하고 미준비 상태를 표시한다. 앱 업데이트가 외부 CLI를 자동 교체하지 않는다.

정적 프런트 빌드는 앱 전용 로컬 게이트웨이가 제공하고 `/api`와 스트리밍은 앱 전용 세션 서버에 전달한다. 같은 출처로 화면을 제공하여 현재 API 접근 구조를 재사용한다. 두 서버는 loopback의 앱 전용 가용 포트를 사용한다. 포트 예약은 실제 bind로 확정하고 기존 13001~13003 서비스는 재사용·종료하지 않는다.

프로세스 실행 경로와 작업 디렉터리는 절대 경로로 전달한다. OpenSpec CLI에는 동봉한 Node를 사용하며 Electron 실행 파일을 Node로 잘못 실행하지 않는다. readiness 확인 후 창을 표시하고 자식 시작 실패 시 앱 소유 자식만 정리한다. 세션 서버 장애 시 자동으로 중복 생성하지 않고 기존 프로세스·저장소 소유를 확인한 후 복구한다.

앱마다 생성한 접근 비밀로 API와 스트리밍 요청을 인증한다. 비밀은 외부 페이지·URL·로그에 노출하지 않는다. Origin 제한도 유지하며 기존 웹 개발 경로와 충돌하지 않게 앱 모드에서 적용한다.

### 영속 저장과 기존 환경 이전

앱의 사용자 데이터 디렉터리에 `DATA_DIR`, 설정 파일과 로그 경로를 절대 경로로 지정한다. 설치 파일과 압축 리소스는 읽기 전용으로 취급한다. 프로젝트 미등록 상태를 지원하며 설치 경로를 기본 업무 프로젝트로 생성하지 않는다. 같은 프로필의 앱은 단일 인스턴스와 세션 소유 잠금으로 보호한다.

세션 소유 잠금은 정규화된 데이터 경로의 해시로 선택한 loopback 30000~48999 포트의 배타적 bind를 사용한다. 같은 데이터나 다른 앱과 충돌하면 시작을 차단하며 포트를 빼앗거나 다른 잠금 포트로 우회하지 않는다. 앱 화면과 세션 API는 별도의 가용 포트를 사용한다. 부모 앱이 비정상 종료되어도 세션 소유자가 살아 있으면 새 소유자를 만들지 않는다.

- 기존 웹 환경의 자동 가져오기는 최초 범위에서 제외하고 프로젝트 경로를 앱에서 다시 등록하는 방식을 제안한다.
- 웹 환경의 `.data`·설정·대화 DB는 그대로 보존된다. 기존 업무 이력을 앱에서도 이어야 한다면 서버 정지 후 DB와 설정을 함께 이전하는 별도 절차를 계획에 추가해야 한다.

### 업데이트 상태 및 설치 경계

- 자동 확인·다운로드 후 사용자가 “업데이트하고 재시작”을 선택하면 모든 업무가 유휴 상태일 때 설치한다.
- 자동 확인 주기는 앱 시작 시와 실행 중 4시간마다, 수동 확인과 오류 재시도도 제공한다.

상태는 확인 중·최신·다운로드 중·설치 준비·업무 종료 대기·설치 전환·실패로 구분한다. 조회 실패를 최신 상태로 처리하지 않는다. 개발 실행에서는 실제 업데이트 설치를 비활성화한다.

업데이트 선택은 GitHub 공개 latest 정식 릴리스와 플랫폼별 메타데이터를 사용한다. 앱은 태그 `v<버전>` 일치와 현재 OS·아키텍처의 정확한 산출물 이름을 다운로드 전에 검증한다. 호환 파일이 없거나 다른 플랫폼 파일이 섞이면 오류로 차단하며 라이브러리의 대체 파일 선택을 허용하지 않는다. 기존 라이브러리의 최소 OS 지원 판정은 유지한다.

종료·설치 준비 전에 기존 화면의 beforeunload 문서 보호를 확인한다. 미저장 문서나 확인 실패 시 서버를 종료하지 않고 저장·재시도를 안내한다. 이 확인에는 앱이 소유한 고정된 화면 검사만 사용하며 사용자 입력 스크립트나 임의 실행 API를 노출하지 않는다.

앱 종료·업데이트 설치·시작 실패 복구는 메인 프로세스의 공통 종료 준비 잠금을 사용한다. 준비 전에 소유 토큰을 얻으며 해당 토큰을 가진 요청만 종료·백업·취소를 수행한다. 서버 잠금 설정 후 준비 응답을 받지 못하면 같은 소유 요청이 서버 취소를 시도한다. 취소까지 실패하면 게이트웨이의 요청 차단을 유지하고 명시적 재시도를 허용한다. 다른 요청의 취소가 기존 소유자의 잠금을 풀어서는 안 된다.

설치 요청 시 세션 서버가 모든 업무의 실행·연결·질문·승인 상태와 처리 중 요청을 확인한다. 유휴 상태 판정과 신규 실행 수락 차단을 같은 설치 전환 잠금에서 처리한다. 불명확한 상태는 설치를 보류한다. 종료 실패 시 설치하지 않고 가능한 서비스는 재개하며 오류를 표시한다. 잠금 확보와 종료 준비가 끝나면 DB를 정상 종료하고 일관된 백업을 만든 뒤 앱 소유 서버만 종료하여 설치기로 넘긴다. SQLite 실행 중 파일을 단순 복사하지 않는다. 기본 종료 시 자동 설치는 끈다.

### GitHub 배포

- 릴리스 저장소는 사용자가 지정한 현재 프로젝트의 Git 원격 저장소 `sklee385/open_spec_dashboard`로 명시한다. 원본 UI 저장소는 사용하지 않는다.
- 이 저장소는 공개 저장소이다. 
- 2026-10-26 사용자는 개인용 앱으로 인증서 없는 GitHub 업데이트를 진행하라고 지시했다. 개인용 배포 패키지는 Authenticode 서명 없이 업데이트를 활성화한다. 개발 실행과 일반 로컬 검사 패키지는 비활성화하며 `--personal-update` 또는 CI의 `--release`로 배포 의도를 명시한다.
- 빌드 정책에 개인용 모드·고정 저장소·업데이트 활성 여부를 넣고 패키징된 앱만 이를 사용한다. 알 수 없는 정책·다른 저장소는 업데이트를 활성화하지 않는다. NSIS의 인증서 배포자 검증은 끄되 HTTPS GitHub 피드, 정확한 버전/파일 선택, SHA-512 다운로드 검증과 SHA-256 게시 검증은 유지한다. 저장소나 계정이 침해되면 해시와 파일을 함께 바꿀 수 있으므로 해시를 배포자 인증으로 간주하지 않는다.

GitHub Actions의 Windows 빌드는 명시적 버전 태그, 앱 버전, 대상 Windows x64 및 저장소 일치를 확인한다. 테스트·빌드·패키징 후 Windows 설치 파일, `latest.yml` 및 필요한 부속 산출물을 같은 버전의 초안 릴리스에 모은다. 기존 파일을 덮어쓰지 않으며 필수 산출물 일관성과 검증 설정 확인 후 정식으로 게시한다. 게시에는 CI의 `GITHUB_TOKEN`만 사용하고 앱에 내장하지 않는다. 서명 비밀은 요구하지 않는다. owner/repo는 `sklee385/open_spec_dashboard`로 명시하고 upstream repository 필드에서 추론하지 않는다. 패키징·업데이트·릴리스 검사·CI 구성은 Windows x64 전용으로 유지한다.

`desktop/publish.cjs`는 태그 push의 저장소·버전·토큰과 EXE·EXE.blockmap·메타데이터를 먼저 검사한다. 인증된 릴리스 전체 목록에서 기존 태그가 있으면 중단하고, 새 초안에 세 파일을 덮어쓰기 없이 업로드한다. 업로드 후 전체 페이지에서 태그가 같은 초안이 정확히 하나인지 확인하고 파일 목록·크기·완료 상태·GitHub SHA-256 digest 및 로컬 재해시를 모두 검증한 뒤 게시한다. 조회·업로드·검증 실패 시 게시하지 않고 초안을 자동 삭제하지 않는다. 실패 후 재실행 절차는 운영 문서에 기록한다.

## Risks / Trade-offs

- 설치 용량 증가 → 현재 코드를 재사용하는 이점과 비교하고 설치 크기를 배포 기록에 남긴다.
- 런타임·CLI 경로 차이 → 공백·한글 경로 및 시스템 Node 없는 설치 환경에서 검증한다.
- 업데이트 설치와 새 업무 요청의 경합 → 서버의 설치 전환 잠금과 전체 업무 상태 확인으로 보호한다.
- 새 버전 시작 실패 → 설치 전 일관된 백업과 이전 설치본을 보존하고 데이터 호환성을 확인하여 수동 복구한다. 이전 버전으로 무조건 DB를 열지 않는다.
- OS 종료·전원 장애 → 기존 영속 이벤트와 재연결 절차를 이용한다. 활성 프로세스의 무중단 보존을 보장하지 않는다.

## Migration Plan

1. 검토 표기 항목을 문답으로 정리하고 사용자가 전체 문서를 검토한다. 명시적 구현 시작 지시 전 제품 코드를 수정하지 않는다.
2. 기존 웹 개발 경로와 별도로 데스크톱 실행 및 패키징을 구현한다.
3. Windows에서 격리한 사용자 데이터로 첫 설치·재실행·업무 복구·기존 서버 공존을 검증한다. 실제 Windows 앱의 화면·트레이·업데이트를 확인하며 Edge 화면 검증은 수행하지 않는다.
4. 테스트용 두 버전으로 다운로드·오류·설치 보류·유휴 설치 및 데이터 보존을 검증한다.
5. 개인용 업데이트가 활성화된 새 설치 파일을 한 번 수동 설치한 뒤 이후 GitHub 업데이트를 사용한다. 저장소·버전·필수 산출물 검증 실패 시 게시를 중단하고 기존 앱을 유지한다.
