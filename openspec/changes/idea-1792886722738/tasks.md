# Tasks

`specs/dashboard-localization/spec.md`와 `design.md`를 기준으로 한다. 모든 체크 항목은 현재 미착수 상태다. 사용자는 `next_phase` 질문에서 ‘구현 시작’을 선택했으며, 연결 종료 후 같은 대화에 복구된 답변으로 해당 결정을 확인했다. 다만 후속 지시에 따라 제품 코드는 구현하지 않고, 아래 계획 문서의 사용자 재검토를 먼저 받는다. 각 그룹은 구현 착수 후 필요한 테스트를 함께 작성·실행하고 다음 그룹으로 진행한다.

## 1. 언어 선택과 번역 기반

- [ ] 1.1 `frontend/src/i18n/`에 브라우저 정보 읽기와 순수 언어 선택 로직을 분리한다. 목록 우선순위, 지역 태그·대소문자, 지원 언어 건너뛰기, 빈 목록·목록 부재 시 단일 언어 사용, 지원 언어 부재·정보 접근 실패 시 영어 선택을 단위 테스트로 검증한다.
- [ ] 1.2 영어 기준 키와 동일한 한국어 키를 갖는 기능별 사전, 타입이 있는 변수 메시지와 번역 함수를 구현한다. 키 일치, 한국어 누락 시 영어 대체, 변수 값 보존, 개수 0·1·2의 표현과 번역 키·미치환 값 미노출을 테스트하고 타입 검사로 잘못된 키·인자 사용을 확인한다.
- [ ] 1.3 React Context·공통 훅을 만들고 `main.tsx`에서 언어를 확정한 뒤 HTML `lang` 설정과 Provider 연결을 수행한다. 초기 로딩부터 선택 언어가 적용되고 새 초기화 시 브라우저 설정을 다시 읽는 것을 테스트하며 언어 저장과 실행 중 변경 구독이 추가되지 않았음을 확인한다.
- [ ] 1.4 테스트에서 `ko` 또는 `en`을 명시하는 렌더링 도우미를 마련하고 기존 컴포넌트 테스트에 적용한다. 기존 한국어 테스트가 브라우저 기본 언어와 무관하게 통과하고 언어 감지 테스트는 별도로 실행되는지 확인한다.

## 2. 날짜·수량과 오류 표시

- [ ] 2.1 `lib/utils.ts`의 날짜·상대 시간에 언어 인자를 적용하고 `Intl.DateTimeFormat`·`Intl.RelativeTimeFormat`으로 표시한다. 고정한 시각에서 1분·1시간·1일·7일 경계 전후와 두 언어 출력을 검증하고 기존 브라우저 시간대 의미가 유지되는지 확인한다.
- [ ] 2.2 `IdeaCard`·`IdeaDetailModal` 등 날짜 표시 호출부를 공통 포맷으로 연결한다. 생성·수정 시각과 상대 시간이 두 언어로 표시되며 원본 타임스탬프가 바뀌지 않는지 렌더링 테스트로 검증한다.
- [ ] 2.3 클래스형 `ErrorBoundary`가 Context를 소비하여 기본 안내와 재시도 버튼을 번역하도록 한다. 두 언어의 오류 화면·재시도, 원문 오류 상세와 기존 사용자 정의 fallback props 유지 여부를 테스트한다.
- [ ] 2.4 `App.tsx`·`hooks/useApi.ts`·화면별 요청 처리의 제품 기본 오류를 안정적인 내부 구분값으로 표시 계층에 전달한다. 제품 안내는 번역되고 서버 자유 형식 오류는 원문으로 남으며 기존 응답 처리 의미가 유지되는지 실패 응답 테스트로 확인한다.

## 3. 보드·명세·아이디어·설정 화면

- [ ] 3.1 `Header`·`SearchBar`·`SortDropdown`·`KanbanBoard`·`ChangeCard`의 표시 상수와 문구를 두 언어 사전에 연결한다. 헤더·모바일 메뉴·검색·정렬·상태·개수·로딩·빈 화면을 렌더링 테스트로 확인하고 상태·정렬 식별자와 필터 동작이 유지되는지 검증한다.
- [ ] 3.2 `SpecsView`·`DetailModal`의 제품 제목·탭·버튼·안내를 번역한다. 두 언어 표시와 문서 본문·문서 경로 원문 보존을 테스트한다.
- [ ] 3.3 `IdeaCapture`·`IdeaCard`·`IdeaDetailModal`의 문구·입력 예시·안내를 번역한다. 두 언어의 작성·상세 화면과 저장 동작을 테스트하고 이름·본문·사용자 입력 및 전송 데이터가 유지되는지 검증한다.
- [ ] 3.4 `SettingsModal`의 문구·성공 및 기본 실패 안내·입력 예시를 번역한다. 두 언어 렌더링과 기존 설정 조회·수정·오류 시 복구 동작을 테스트하며 소스 이름·경로·저장 값이 유지되는지 확인한다.
- [ ] 3.5 공용 UI의 기본 닫기 이름을 포함하여 앞선 화면의 `aria-label`·보조 텍스트·툴팁을 번역한다. 언어별 접근성 이름으로 버튼과 입력란을 조회하는 테스트를 실행하고 기본 닫기 동작을 확인한다.

## 4. 업무 공간과 실행 원문 보존

- [ ] 4.1 `WorkRoom` 대화 정리 결과의 내부 역할을 표시 이름과 분리한다. 두 언어에서 사용자·AI 메시지 구분과 스타일이 동일하고 대화 원문이 보존되는지 테스트한다.
- [ ] 4.2 업무 공간의 단계·탭·상태·연결·대화 입력·질문 제출·문서 저장·충돌 안내를 번역한다. 두 언어 접근성 이름과 안내를 검증하고 기존 저장 충돌·초안 보존·이동 차단·메시지 전송 테스트를 통과시킨다.
- [ ] 4.3 검증 계획·명령 입력·검증 결과·OpenSpec 결과의 제품 고정 문구를 번역한다. 두 언어 표시와 함께 명령·인자·실행 출력·서버 오류·OpenSpec 원본 결과가 변경되지 않는지 테스트한다.
- [ ] 4.4 AI 질문·답변 선택지와 제품이 생성하는 AI 요청 문구를 화면 번역에서 분리한다. 한국어 콘텐츠를 영어 화면에서 표시하고 질문 응답·문서 수정 요청·결과 기반 요청을 준비·전송하여 원문과 기존 요청 데이터가 유지되는지 테스트한다.

## 5. 통합 검증과 사용자 검토

- [ ] 5.1 명세의 각 시나리오를 구현과 기존 그룹의 테스트에 대조하고 전체 대상 사전의 키 일치와 남은 제품 고정 문구를 확인한다. 통합 화면에서 언어 혼재가 원문 보존 대상에 한정되는지 점검하고 확인 결과를 이 항목에 기록한다.
- [ ] 5.2 `npm run test:run --workspace frontend`, `npm run build --workspace frontend`, `npm run lint --workspace frontend`를 실행한다. 타입 검사 포함 빌드·전체 프런트엔드 테스트·린트 결과와 기존 문제 유무를 이 항목에 기록한다.
- [ ] 5.3 사용자 설치 ChatGPT 확장을 통한 Microsoft Edge에서 한국어·영어 및 미지원 언어 기본값, 새로고침 후 언어 적용, 데스크톱·모바일 배치와 버튼 접근성을 확인한다. 접근 불가 시 이 항목을 완료 처리하지 않고 미검증 사유와 남은 확인 범위를 기록한다.
- [ ] 5.4 구현·자동 검증·브라우저 검증 결과와 남은 제한을 사용자에게 제시하고 최종 검토 결과를 이 항목에 기록한다. 사용자 검토 완료 확인 후에만 이 항목을 완료 처리한다.

## Workflow follow-up

- 이 작업 목록을 포함한 계획 문서는 사용자 검토 대상이다. 문서 작성이나 OpenSpec 검증 통과만으로 구현 시작·업무 완료로 처리하지 않는다.
- ‘구현 시작’ 선택은 확인되었지만 현재는 구현 전 문서 재검토 대기 상태다. 사용자가 `proposal.md`, `specs/dashboard-localization/spec.md`, `design.md`, `tasks.md`를 재검토하고 구현 진행을 확인한 후 `openspec-apply-change` 절차로 구현한다. 이번 답변 복구와 문서 갱신만으로 제품 코드를 수정하지 않는다.
- 구현·검증·사용자 검토를 마친 뒤 사용자가 보관을 요청하면 변경 보관 절차를 진행한다.
