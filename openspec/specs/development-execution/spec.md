# development-execution Specification

## Purpose

사용자가 업무 화면에서 Codex의 실제 개발 실행과 추가 지시, 검증 결과 및 완료 처리를 확인할 수 있게 하여 개발 전 과정에서 외부 도구로 이동해야 하는 불편을 해소한다.

## Requirements

### Requirement: 명시적 구현 시작
시스템은 필요한 OpenSpec 계획 문서의 준비 및 사용자 검토 완료 후 구현 시작 동작을 제공해야 한다(SHALL). 문서 생성 또는 아이디어 전환만으로 구현을 시작해서는 안 된다(MUST).

#### Scenario: 준비된 계획에서 구현 시작
- **WHEN** 사용자가 준비된 문서를 검토하고 구현 시작을 선택한다
- **THEN** 시스템은 연결된 프로젝트에서 기존 Codex 대화를 사용하여 구현을 실행한다

#### Scenario: 계획이 준비되지 않은 상태
- **WHEN** 필요한 계획 문서가 없거나 재검토가 필요한 상태에서 구현 시작을 요청한다
- **THEN** 시스템은 실행하지 않고 필요한 문서 또는 검토 상태를 표시한다

### Requirement: 실행 상태와 결과의 실시간 표시
시스템은 실행 중 메시지·도구 진행 상황·수정 파일·명령 결과를 업무 화면에 제공하고 성공·실패·중단 상태를 구분해야 한다(SHALL).

#### Scenario: 명령 실패
- **WHEN** 개발 중 실행한 명령이 실패한다
- **THEN** 시스템은 종료 상태와 오류를 표시하고 업무를 성공이나 완료로 자동 처리하지 않는다

### Requirement: 추가 지시와 중단 후 재개
시스템은 같은 업무에서 추가 지시를 전달하고 실행을 중단하거나 이후 재개할 수 있게 해야 한다(SHALL). 동일 업무에서 서로 충돌하는 실행을 동시에 시작해서는 안 된다(MUST).

#### Scenario: 실행 중 추가 지시
- **WHEN** 사용자가 진행 중인 업무에 추가 지시를 입력한다
- **THEN** 시스템은 같은 대화의 실행에 지시를 전달하거나 대기열에 넣고 처리 상태를 표시한다

#### Scenario: 중단 후 재개
- **WHEN** 사용자가 실행을 중단한 뒤 다시 진행을 요청한다
- **THEN** 시스템은 기존 변경 파일과 같은 대화를 유지한 채 후속 작업을 실행한다

### Requirement: 검증 근거와 완료 판정
시스템은 검증 항목마다 통과·실패·미검증 상태 및 실제 실행 결과를 제공해야 한다(SHALL). 모든 작업 완료, 미답변 필수 질문 없음, 계획 재검토 없음, 필수 검증 통과와 사용자 완료 확인을 충족해야 업무를 완료로 처리한다(MUST).

#### Scenario: 검증 실패 또는 미검증 존재
- **WHEN** 코드 작성이 끝났지만 필수 검증이 실패하거나 실행되지 않았다
- **THEN** 시스템은 완료 처리를 막고 남은 검증과 같은 세션에서의 수정·재검증 동작을 제공한다

#### Scenario: 최종 확인 후 완료
- **WHEN** 모든 완료 조건이 충족되고 사용자가 결과를 확인하여 완료를 선택한다
- **THEN** 시스템은 완료 상태와 근거를 저장하고 OpenSpec 보관 동작을 제공한다

### Requirement: 변경 이후 검증 무효화
시스템은 검증 후 관련 코드나 명세가 변경되면 기존 검증을 과거 결과로 표시하고 새 필수 검증을 요구해야 한다(MUST).

#### Scenario: 검증 통과 후 코드 추가 수정
- **WHEN** 통과한 검증 이후 코드가 다시 수정된다
- **THEN** 시스템은 이전 통과를 최종 완료 근거로 사용하지 않고 재검증 필요 상태를 표시한다

### Requirement: 보관 결과 확인
시스템은 사용자가 완료된 변경의 보관을 요청하면 OpenSpec 보관과 기준 명세 반영 결과를 확인해야 한다(SHALL). 실패 시 완료 상태와 보관 실패를 구분하고 재시도를 제공해야 한다(MUST).

#### Scenario: 보관 중 오류
- **WHEN** 완료된 업무를 보관하는 과정에서 OpenSpec 명령이 실패한다
- **THEN** 시스템은 보관 완료로 표시하지 않고 오류와 재시도 기능을 제공한다

### Requirement: Codex 준비 상태와 실행 경계
시스템은 Codex 설치·인증·연결 오류를 표시하고 복구 후 같은 업무를 재개할 수 있어야 한다(SHALL). 실행 위치는 연결된 프로젝트로 제한하고 Codex의 권한 승인 절차를 UI에 전달해야 한다(MUST).

#### Scenario: 인증 또는 연결 문제
- **WHEN** Codex를 사용할 수 없어 실행 요청을 처리하지 못한다
- **THEN** 시스템은 준비 필요 상태를 표시하고 업무와 기존 대화 연결을 유지한다

### Requirement: 완료 변경 결과 보존
시스템은 업무 전용 실행 공간의 최초 구현 시작 직전 상태와 사용자 완료 확인 시 상태의 차이를 업무별로 보존해야 한다(SHALL). 기존 완료 조건, 검증된 결과의 원본 반영 성공을 충족한 경우에만 결과와 완료 상태를 함께 확정해야 하며(MUST), 저장 실패 시 완료 처리해서는 안 된다(MUST).

#### Scenario: 완료 이후 파일 수정
- **WHEN** 사용자가 업무를 완료한 뒤 다른 작업으로 프로젝트 파일을 수정한다
- **THEN** 완료 업무에서 조회하는 변경 목록과 내용은 완료 시점의 저장된 결과를 유지한다

#### Scenario: 저장 실패와 재시도
- **WHEN** 완료 결과 저장이 실패한다
- **THEN** 시스템은 실패 이유를 표시하고 완료 상태를 유지하지 않으며 재시도를 제공한다
- **AND** 재시도 성공 시 하나의 완료 결과와 완료 상태를 함께 확정한다

#### Scenario: 재개와 서버 재시작
- **WHEN** 구현을 중단·재개하거나 완료 후 서버를 재시작한다
- **THEN** 최초 시작 기준과 저장된 완료 결과는 각각 유지된다

### Requirement: 업무별 변경 파일과 차이 조회
시스템은 업무 결과에서 추가·수정·삭제 파일 목록과 선택한 파일의 변경 줄, 전후 줄 번호, 추가·삭제 구분을 제공해야 한다(SHALL). 변경 없음과 기록 없음은 구분해야 하며(MUST), 완료·보관 업무에서도 업무 식별 정보와 비교 시각을 표시해야 한다(SHALL).

#### Scenario: 추가 수정 삭제 파일 검토
- **WHEN** 저장된 완료 결과에 추가·수정·삭제 파일이 있다
- **THEN** 시스템은 파일 경로와 상태를 표시하고 선택한 파일의 저장된 전후 내용을 줄 단위로 비교한다
- **AND** 변경 문맥 펼치기와 전체 전후 내용 조회를 제공한다

#### Scenario: 변경 없음
- **WHEN** 유효한 시작·종료 기록의 파일 차이가 없다
- **THEN** 시스템은 변경된 파일이 없다고 표시한다

#### Scenario: 보관 후 조회
- **WHEN** 사용자가 보관된 업무의 변경 파일을 조회한다
- **THEN** 시스템은 보관 과정의 파일 이동으로 결과를 재계산하지 않고 완료 당시 결과를 보여준다

### Requirement: 비교 한계와 과거 기록 안내
시스템은 파일 부재와 내용 수집 불가를 구분하고 바이너리·크기 제한 등 비교 불가 이유를 표시해야 한다(SHALL). Git 없이도 동일한 파일 비교를 지원해야 한다(SHALL). 시작 또는 완료 기록이 없는 과거 업무를 현재 파일로 재구성해 완료 결과처럼 표시해서는 안 된다(MUST).

#### Scenario: Git 없는 프로젝트
- **WHEN** Git이 없는 프로젝트에서 구현 시작과 완료 결과를 저장한다
- **THEN** 파일 스냅샷으로 동일한 목록과 비교 기능을 제공한다

#### Scenario: 일부 파일 내용 미수집
- **WHEN** 수정 파일의 한쪽 내용이 바이너리 또는 크기 제한으로 수집되지 않았다
- **THEN** 시스템은 해당 파일의 변경 상태와 비교 불가 이유를 표시하고 누락 내용을 빈 파일로 처리하지 않는다

#### Scenario: 저장 기록 없는 과거 업무
- **WHEN** 과거 완료 업무에 시작 기준 또는 완료 결과가 없다
- **THEN** 시스템은 완료 당시 기록이 없어 비교할 수 없다고 표시한다

### Requirement: 업무별 변경 격리
시스템은 구현·재개·검증을 업무별 독립 실행 공간에서 수행하고 해당 업무 공간의 기준 대비 변경만 표시해야 한다(MUST). 원본 프로젝트나 다른 업무의 병행 변경, 구현 시작 전에 이미 존재한 변경을 해당 업무 변경으로 포함해서는 안 된다(MUST). 실행 공간을 복구할 수 없으면 원본에서 대신 실행해서는 안 된다(MUST).

#### Scenario: 다른 업무의 병행 변경
- **WHEN** 업무 A와 B가 같은 원본 프로젝트에서 각각 구현을 진행한다
- **THEN** A의 목록과 전후 내용에는 A의 실행 공간에서 발생한 차이만 표시한다
- **AND** B나 원본에서 발생한 동일 파일 및 다른 파일의 수정은 A 결과에 섞이지 않는다

#### Scenario: 기존 미커밋 변경
- **WHEN** 구현 시작 전 원본에 기존 변경이 있다
- **THEN** 시스템은 이를 초기 상태로 보존하며 해당 업무가 새로 만든 차이로 표시하지 않는다

#### Scenario: 재개 공간 누락
- **WHEN** 업무 전용 실행 공간이 없거나 다른 업무의 공간으로 식별된다
- **THEN** 실행·검증을 차단하고 복구 필요를 안내한다

#### Scenario: 기존 공유 폴더 업무
- **WHEN** 기존 업무의 기록에 격리된 실행 기준이 없다
- **THEN** 시스템은 업무별 귀속 기록 없음으로 표시하고 공유 폴더 차이를 이 업무만의 결과로 확정하지 않는다

### Requirement: 업무 변경의 원본 반영
시스템은 업무 완료 요청과 구분되는 사용자의 별도 원본 반영 요청으로 검증된 업무 변경만 반영해야 한다(SHALL). 해당 경로의 원본이 시작 기준 또는 반영 결과와 다르면 충돌로 표시하고 자동 덮어쓰기를 금지해야 한다(MUST). 반영 실패·미완료 상태에서는 업무 완료를 막고 복구 상태를 제공해야 한다(MUST).

#### Scenario: 완료 요청과 원본 반영 구분
- **WHEN** 사용자가 원본 반영을 요청하지 않은 상태에서 업무 완료를 요청한다
- **THEN** 시스템은 자동 반영하지 않고 별도 원본 반영이 필요하다고 안내한다

#### Scenario: 서로 다른 파일 반영
- **WHEN** 업무 A의 변경을 반영하고 원본의 다른 파일에는 B의 변경이 있다
- **THEN** A의 변경 경로만 반영하고 B의 파일은 유지한다

#### Scenario: 같은 파일 반영 충돌
- **WHEN** 업무의 기준 이후 원본의 같은 파일이 다른 내용으로 변경되었다
- **THEN** 충돌 경로를 표시하고 자동 덮어쓰기와 완료 처리를 차단한다

#### Scenario: 부분 반영 후 중단
- **WHEN** 원본 반영 도중 실패하거나 서버가 재시작한다
- **THEN** 시스템은 반영 기록으로 복구·재시도 상태를 제공하며 전체 반영과 결과 저장을 확인하기 전 완료로 표시하지 않는다

### Requirement: 격리 결과의 범위 안내
시스템은 업무별 실행 공간의 차이를 제공한다는 사실과 수집 제외 범위를 안내해야 한다(SHALL). 격리 근거 없는 과거 기록을 업무별 변경으로 확정해서는 안 된다(MUST).

#### Scenario: 비교 범위 확인
- **WHEN** 사용자가 업무의 변경 파일 결과를 조회한다
- **THEN** 업무 식별 정보와 격리 여부, 기준 시각, 수집 제외 범위를 확인할 수 있다
